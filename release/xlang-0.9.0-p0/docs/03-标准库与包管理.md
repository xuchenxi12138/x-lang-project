# 03 · 标准库与包管理

> 标准库的分层原则、网络/OS/数据库模块设计、包管理器的完整规范。
> 核心约束：标准库**不携带**任何重依赖，数据库驱动走包生态。

---

## 1. 分层模型

```
┌─────────────────────────────────────────┐
│ L4 应用生态（第三方包、ORM、Web 框架、UI 组件）│  不在标准库范围
├─────────────────────────────────────────┤
│ L3 面向任务（http server、json、db、crypto、│  std 内的「可选」模块
│     log/span、dataframe、ml、ui、gpu）     │
├─────────────────────────────────────────┤
│ L2 通用设施（fs、net、process、time、      │  std 主体
│     rand、regex、collections、sync）      │
├─────────────────────────────────────────┤
│ L1 数值与语言基础设施（math、linalg、      │  std.core
│     complex、ndarray、format、str）      │
├─────────────────────────────────────────┤
│ L0 无 OS 依赖（mem、ptr、slice、          │  可 freestanding 使用
│     atomic、asm、layout）                 │  ← 这一层必须能编进 x-os
└─────────────────────────────────────────┘
```

**[裁决]** L0 必须能在无 libc、无 OS、无分配器环境下编译（`--freestanding --no-alloc`）。这是 x-os 复用同一语言的前提，也是让语言能进入内核/嵌入式的唯一门槛。

L0 与 L1 的边界必须划清：**L0 不含任何需要分配的东西**。`std.mem` 提供 `Allocator` 接口但不提供默认实现；`std.collections` 在 L2 因为它需要分配。这条边界让内核能只用 L0。

**L3 的定位说明**：`dataframe`/`ml`/`ui`/`gpu` 是「重模块」，只在需要时链接。它们不违反「标准库不背重依赖」原则，因为：

- 不引入第三方 C 库（GPU 绑定除外，且可选）。
- 按符号粒度链接，不用就不进二进制。
- 可被 `--exclude-module` 完全排除。

### 2.2 `std.dataframe`（数据分析主场）

列式数据 + 编译期列名检查。**这是 X 相对 pandas/polars 的核心差异：列名拼错是编译错误，不是运行时异常。**

```x
import std.dataframe as df

// 1. Schema 由结构体定义，读取时一次性完成类型转换
@derive(FromCsv)
struct SaleRow {
    @col("order_id") id:    Int,
    @col("date")     date:  Date,
    @col("sku")      sku:   String,
    @col("qty")      qty:   Int,
    @col("price")    price: Float,
    @col("note")     note:  String?,      // 可空列 → Option
}

// 读取：类型转换失败会指出具体行号与列名，并给出行文本
let sales = DataFrame.load[SaleRow]("sales.csv")

// 2. 列引用在编译期校验（df.qty 而非 df["qty"]）
let revenue = sales.qty * sales.price          // Int * Float：DataFrame 列算子定义提升规则
sales.qty                                       // 类型：Column[Int]
revenue                                         // 类型：Column[Float]

// 3. 过滤、分组、聚合——全部强类型
let big = sales.filter(|r| r.qty > 100)
let byMonth = sales.groupBy(|r| r.date.month())
                   .agg(
                       revenue: sum(r -> r.qty * r.price),
                       orders:  count(),
                       avgQty:  mean(r -> r.qty),
                   )

// 4. 连接（键类型必须匹配，否则编译错误）
let products = DataFrame.load[ProductRow]("products.csv")
let joined = sales.join(products, on: |s, p| s.sku == p.sku)

// 5. 缺失值：三值逻辑，不是 NaN 哨兵
let filled = sales.note.fillNull("(无备注)")
let onlyNull = sales.filter(|r| r.note.isNull())

// 6. 输出
sales.toCsv("out.csv")
byMonth.toParquet("out.parquet")
println(sales.describe())
```

**编译期列检查的实现**：`DataFrame.load[SaleRow]` 返回 `DataFrame[SaleRow]`，字段访问 `df.qty` 由泛型参数 `SaleRow` 在编译期解析为列索引。拼错时报错：

```

   |
```

### 2.3 `std.ml`（AI 建模与推理）

```x
import std.ml as ml

// 张量：形状进类型（编译期检查矩阵维度）
let x = Tensor[Float, 3, 224, 224].zeros()
let w = Tensor[Float, 224, 1000].randn() * 0.01
let y = x.flatten(1) @ w                    // [3,224,224] → [3,224] @ [224,1000] → [3,1000]
// let z = x @ w                            // 编译错误：224x224 与 224x1000 不匹配（带形状诊断）

// 自动微分：@differentiable 编译期生成反向函数，无运行时 tape
@differentiable
fn loss(w: Tensor[Float], x: Tensor[Float], y: Tensor[Float]) -> Float {
    let pred = x @ w
    ((pred - y) ** 2).mean()
}

let g = grad(loss)(w, x, y)                 // 编译期生成，与手写反向传播同速
w = w - lr * g

// 动态图模式（研究/调试用，慢 2~3 倍但可逐步）
tape {
    let pred = x @ w
    let l = ((pred - y) ** 2).mean()
    l.backward()
}

// 推理：加载 ONNX，形状编译期确定
let model = ml.Model.load("resnet50.onnx")
let input = Tensor[Float, 1, 3, 224, 224].fromImage("cat.jpg")
let out = model.run(input)                  // AOT 编译的推理循环，无解释开销
```

**为什么 `@differentiable` 优于 PyTorch 的 tape**：

| 维度 | tape（PyTorch） | `@differentiable`（X） |
|---|---|---|
| 每算子开销 | 记录 tape 节点 ~100 ns | 0（编译期生成） |
| 图级优化 | 有限（需 TorchScript） | 完全（编译器看得到整图） |
| 内存峰值 | tape 保存所有中间值 | 编译器按需保留（重计算优化） |
| 调试 | 好 | 中（生成代码可读性差） |

两者都提供，`@differentiable` 用于生产、`tape` 用于研究。

### 2.4 `std.ui`（桌面与移动）

```x
import std.ui

fn main() {
    runtime.reserveMainThreadForUI()        // 调度器让出主线程给 GUI 事件循环

    let app = ui.App.new("库存管理")
    app.window("主窗口", size: (1024, 700), |w| {
        let rows = @State([])               // @State 变化自动触发重绘
        let loading = @State(false)

        w.vstack([
            w.hstack([
                w.button("刷新", onClick: async || {
                    loading = true
                    rows = await api.fetchRows()       // 自动在 worker 线程
                    loading = false                    // 自动切回 UI 线程
                }),
                if loading { w.spinner() } else { w.space() },
            ]),
            w.table(
                columns: [("编号", .id), ("名称", .name), ("数量", .qty)],
                rows: rows,
                onRowClick: |r| detailWindow(r),
            ),
        ])
    })
    app.run()                               // 驱动平台事件循环
}
```

设计要点：

| 要点 | 说明 |
|---|---|
| `@State` 编译期生成观察 | 读写自动订阅/触发，无手写订阅代码 |
| 线程亲和检查 | UI 对象只能在 UI 域访问，lint 检查跨线程误用 |
| 后台→UI 自动切回 | `await` 恢复时若目标是 UI 对象，调度器自动切回 UI 线程 |
| 原生控件绑定 | Win32 / Cocoa / GTK / Android View / UIKit，不自绘 |
| 事件循环整合 | 平台循环每轮顺便 poll 调度器队列 |

**诚实的边界**：`std.ui` 是「绑定原生控件」，不是自绘引擎。这带来原生观感与无障碍免费，代价是三套平台实现。自绘方案（Skia 类）需要文本整形 + 输入法 + 无障碍 + 高 DPI 全部自研，1 人年以上，`--profile=desktop` 完全不需要为此付费。

### 2.5 `std.linalg`

```x
import std.linalg as la

let A = mat[[2.0, 1.0], [1.0, 3.0]]
let b = mat[[1.0], [2.0]]

la.solve(A, b)              // 解 Ax=b，奇异时 throw SingularMatrixError
la.inv(A)
la.det(A)
la.lu(A)                    // → (L, U, P)
la.qr(A)
la.svd(A)                   // → (U, S, Vt)
la.eig(A)                   // 不可对角化时 throw NotDiagonalizableError
la.cholesky(A)              // 非正定时 throw NotPositiveDefiniteError
la.norm(A, ord: 2)
la.rank(A)
la.pinv(A)

// 稀疏矩阵
import std.linalg.sparse as sp
let S = sp.csr.fromTriplets(rows, cols, vals, (m, n))
la.solve(S, b)              // 自动分派到稀疏求解器
```

**后端策略**：[裁决] `std.linalg` 默认用纯 X 实现的参考算法（正确性优先，性能基准的 0.3~0.7×）。编译开关 `--blas=system` 时链接 OpenBLAS/MKL/Accelerate，`--blas=builtin` 时用自研分块内核。API 完全一致，用户无感切换。

### 2.6 超越函数精度

`std.math` 的 `sin`/`cos`/`exp`/`log`/`pow`/`gamma` 等：

- 默认实现：自研多项式逼近，目标 ULP 误差 ≤ 2（对标 glibc）。
- `--math=libm` 切到系统 libm。
- 提供 `sinFast()` 系列（ULP ≤ 32，快 3~5 倍），供图形/信号处理用。

## 3. 网络模块

### 3.0 P0 已实现的部分（v0.20）

本节描述的是 P1 目标（协程 + TLS + HTTP/2）。P0 已经落地的是一个
**同步、无协程、无 TLS 的 HTTP/1.1 实现**，足以支撑真实的服务端
与客户端程序：

```
stdlib/net/
├── index.xle              统一入口 + 能力矩阵
├── core/
│   ├── tcp_listener.xle   TcpListener：accept/acceptWithin，port/boundPort
│   └── tcp_stream.xle     TcpStream：sendAll/recvWithin/drain/alive
└── http/
    ├── uri.xle            URI 解析、百分号编码、相对解析、点段归一化
    ├── header.xle         Headers：大小写无关、重复头、obs-fold
    ├── cookie.xle         Cookie 解析 + SetCookie 生成 + 配置校验
    ├── status.xle         状态码 + 每个码的使用建议
    ├── request.xle        请求解析 + 走私检测 + 缺 Host 检测
    ├── response.xle       响应序列化 + HEAD/204 处理 + 自动 Content-Length
    ├── reader.xle         读头/读 body（CL / chunked / 读到关闭）
    ├── router.xle         Route/Router/Match：参数、通配、405、HEAD 复用 GET
    ├── server.xle         Context + HttpServer（单线程 accept 循环）
    └── client.xle         HttpClient（单次请求，无连接池/重试/重定向）
```

三个关键约束必须写清楚，因为它们决定了上层怎么用：

| 约束 | 原因 | 应对 |
|---|---|---|
| **所有 socket 非阻塞** | 平台层统一 `set_nonblock` | 所有读操作都要带等待预算并轮询；`recvOnce` 返回空不等于关闭 |
| **`netRecv` 返回空串有二义** | 无数据（EAGAIN）与对端关闭（recv==0）都返回 `""` | 必须用 `netPending`（平台层 MSG_PEEK）区分，否则死连接会泄漏 |
| **`send` 可能只发一部分** | TCP 发送缓冲区有界 | `sendAll` 循环到发完；不循环会静默截断大响应 |

**`netListen` 失败会 `exit(70)`，不会返回 -1**（`interp.c` 的
`XBI_NET_LISTEN` 分支）。这是内建的硬行为，所以 `TcpListener`
用「`netPort` 能否读回端口」来判定成败，而不是判 `fd < 0`。

能力矩阵（`netSupportMatrix()` 可运行时打印）：

| 能力 | 状态 | 说明 |
|---|---|---|
| TCP 监听/连接/收发 | 完整 | IPv4；非阻塞 + 轮询 |
| HTTP/1.1 客户端 | 完整 | CL / chunked / 读到关闭三种 body |
| HTTP/1.1 服务端 | 完整 | 单线程 accept；`Connection: close` |
| URI 解析 | 完整 | 含 IPv6 字面量、userinfo、点段归一化 |
| Cookie | 完整 | 请求解析 + SetCookie + 错误配置检测 |
| 路由 | 完整 | 参数、通配、405、HEAD 复用 GET |
| UDP / IPv6 连接 | 无 | 语言无 UDP 内建；平台层只用 `AF_INET` |
| HTTPS / TLS | 无 | 语言无 TLS 内建；需前置反向代理 |
| HTTP/2 / WebSocket / gzip | 无 | 只用文本帧；无 zlib 内建 |

### 3.1 分层

本节起为 P1 目标设计。

```
std.http        HTTP/1.1 + 2、WebSocket、Server/Client
   │
std.net.tls     TLS 1.2/1.3（自研，或用系统 SChannel/SecureTransport/OpenSSL）
   │
std.net         TCP / UDP / Unix domain socket / DNS 解析
   │
std.sys         IOCP（Win） / io_uring（Linux 5.1+） / epoll（Linux 回退） / kqueue（macOS）
```

**[裁决]** 底层事件机制**分平台实现，共享接口**，不做统一抽象层。理由：IOCP 是完成端口模型，io_uring/epoll 是就绪模型，强行统一必然牺牲一方性能。接口层只暴露「注册读/写意图 + 回调」的语义，各平台映射到自己的模型。

TLS 策略：[裁决] 优先绑定系统 TLS（Windows SChannel、macOS SecureTransport、Linux OpenSSL），自研 TLS 排在 P4。理由：TLS 实现出错等于安全事故，自研性价比极低。`--tls=builtin` 走自研（无 OpenSSL 环境时）。

### 3.3 数据库访问

**[裁决]** 标准库只提供 **driver 接口抽象**（`std.db`），具体驱动（MySQL/PostgreSQL/SQLite/SQL Server/Oracle/MongoDB/Redis）全部走包生态。

理由：数据库协议持续演进（MySQL 8 的 caching_sha2、PG 的 SCRAM-SHA-256），把它绑进标准库等于承诺永久维护。SQLite 例外——它是嵌入式唯一合理选择且协议稳定，可在 `std.db.sqlite` 内置（vendored 源码静态链接）。

```x
// std.db 抽象（约 200 行接口定义）
pub trait Driver {
    fn connect(connStr: String) -> Connection throws DbError
}
pub trait Connection {
    fn query(sql: String, args: [Value]) -> Rows throws DbError
    fn execute(sql: String, args: [Value]) -> ExecResult throws DbError
    fn prepare(sql: String) -> Statement throws DbError
    fn begin(self) -> Transaction throws DbError
    fn close(self)
}
pub enum Value { Null, Int(Int64), Float(Float64), Text(String), Blob(Array[UInt8]), Bool(Bool) }
```

驱动包（第三方，官方维护前 4 个）。注册中心包名即引入名（§6.4.1）：

| 包名 | 源码写法 | 协议 | 说明 |
|---|---|---|---|

## 3A. 应用框架（P0 已实现，v0.20）

网络层解决「怎么收发报文」，应用框架解决「怎么组织一个服务」。
这一章对应 Spring Boot 在 Java 生态里的位置。

### 3A.1 三层与职责

```
stdlib/web/core/application.xle   Application + AppOptions：启动/关停编排
stdlib/web/core/container.xle     Container + Bean：显式注册 + 单例管理
stdlib/service/lifecycle.xle      Lifecycle + Component：phase 决定的启停顺序
stdlib/service/health.xle         HealthChecker：liveness / readiness 分级
stdlib/service/config.xle         Config：键值 + 来源追踪 + 类型校验

apps/blog/                        可运行的示例（Spring Boot 风格目录）
├── conf/application.properties
└── src/{main,config,controller,service,repository,model,middleware}
```

### 3A.2 与 Spring Boot 的对应关系（以及为什么有的做不到）

| Spring | 本项目 | 差异原因 |
|---|---|---|
| `@SpringBootApplication` | `Application.builder()` | — |
| `@Component` 扫描 | `Container.register(name, factory)` | **无反射**，不能扫注解 |
| `@Autowired` 按类型注入 | `container.attach(name, idx)` 按名 | **无反射**，不能按类型匹配 |
| `@ConfigurationProperties` | `AppConfig.fromConfig(cfg)` | — |
| `@RestController` + `@GetMapping` | `Router.get(path, handlerName)` + `dispatch` 里的显式分派 | **无一等函数**，路由不能持有函数值 |
| `Filter` / `Interceptor` | `middleware/pipeline.xle`（声明 + 阶段排序） | 动作仍由 `dispatch` 执行 |
| `application.properties` | `Config.loadFile` | 格式更简单（无转义、无续行） |
| `/actuator/health` | `/health`、`/health/live`、`/health/ready` | — |
| 内嵌 Tomcat | `net/http/server.xle` | 无 keep-alive、单线程 |
| 优雅关机钩子 | `Lifecycle.stopOrder()`（phase 降序） | 无信号处理，靠「处理满 N 个请求后返回」 |

三条做不到的能力（反射、一等函数、信号）都不是「还没做」，而是
语言 P0 的设计边界。框架的选择是**显式化**这些接线，而不是用宏
或代码生成去模拟 —— 模拟出来的东西在排查线上问题时无法自省。

### 3A.3 启停顺序为什么用一个整数 phase 就够

```x
lc.add("storage", 10)   // 数据库
lc.add("cache",   20)   // 缓存
lc.add("services", 30)  // 业务
lc.add("http",    40)   // 监听
```

启动按 phase **升序**：依赖先起（HTTP 开始接流量前，数据库必须就绪）。
关停按 phase **降序**：`stopOrder()` 是 `startOrder()` 的严格逆序，
保证「没有任何组件在其依赖还活着时被关掉」。

一个数字同时解决两个方向，不需要维护两份顺序表 —— 而两份列表
一定会有一天只改了一份。

### 3A.4 启动失败必须回滚

`Application.prepare()` 的五个失败点（配置文件缺失、必需项缺失、
监听失败、配置校验失败、组件初始化失败）都走 `fail()`，它做两件事：

1. 把 lifecycle 置为 `FAILED`
2. **关掉已经起来的监听**

第 2 点容易被忽略，但它是「反复重启后端口被占满」的根因。每个失败
的实例都留着一个没关的监听 socket，第 N 次重启时上一个还没来得及
释放，于是连启动都失败 —— 而日志上只有「端口被占用」，看不出是
自己泄漏的。

### 3A.5 健康检查必须分三层

| 探针 | 查什么 | 失败后果 |
|---|---|---|
| `liveness` | 只探进程内能否分配内存并做运算 | **重启容器** |
| `readiness` | 所有 required 组件的状态 | 从负载均衡**摘流量**，不重启 |
| `startup` | 启动期是否结束（P0 未实现） | 在此之前 liveness 不生效 |

混淆前两个会造成雪崩：如果 liveness 里查数据库，那么数据库抖
一下 → 所有实例被重启 → 重启后数据库压力更大 → 全挂。

`HealthChecker.live()` 刻意**不查任何外部依赖**，只做一次 16 元素
的数组分配与求和断言。这是唯一正确的 liveness 实现方式。

### 3A.6 配置层必须能回答的四个问题

`Config` 的设计对应这四个问题：

1. **有没有配这个键**（不是「值是否为空串」）：`has()` 与 `get()` 分离。
   `log.level =`（空值）与「没有 log.level」是两回事。
2. **值来自哪里**：`sourceOf()` 返回 `default` / `file` / `env` / `code`。
   排查「生产与本地不一致」时第一个要看的就是它。
3. **类型不对怎么办**：`getInt` / `getBool` 解析失败时**记进 errors
   并返回默认值**，而不是静默回退。`port = "80O0"`（字母 O）会
   在启动时暴露，而不是让服务起在错误的端口上。
4. **环境变量怎么覆盖**：优先级 `code > env > file > default`，用
   数字表达。这比「按调用顺序覆盖」可靠 —— 后者在某次重构调整
   调用顺序后，环境变量会悄悄失效。

### 5.4 语言服务 `x lsp`（v0.15 已实现）

stdio 上的 LSP 服务端，与编译器同一个 exe。编辑器扩展只做薄客户端。

**能力矩阵（当前实现）**

| 方法 | 状态 | 说明 |
|---|---|---|
| `initialize` / `initialized` | 已实现 | 声明 `positionEncoding: utf-16` |
| `textDocument/didOpen` / `didChange` / `didClose` | 已实现 | **全量同步**（`textDocumentSync: 1`） |
| `textDocument/completion` | 已实现 | 本文档符号 + 关键字 + 内建 + 类型，约 198 项 |
| `textDocument/hover` | 已实现 | 内建给参数个数与返回类型；本文档符号给定义行 |
| `textDocument/signatureHelp` | 已实现 | 内建用 `#1 #2` 占位；本文档函数取真实参数名 |
| `textDocument/documentSymbol` | 已实现 | 函数 range 覆盖整个函数体（括号配平），变量覆盖所在行 |
| `shutdown` / `exit` | 已实现 | |
| 诊断（`publishDiagnostics`） | **未实现** | 见下 |
| 定义跳转 / 引用 / 重命名 / 补全解析 | **未实现** | 需要跨文件索引 |

**为什么用全量同步**

增量同步要自己维护版本链与区间换算，算错时的表现是「补全结果对不上代码」—— 而这类错误几乎无法从界面反推。全量同步浪费一点带宽，换来的是「服务端永远有一份完整正确的文本」。LSP 消息本身有 8 MB 上限，单文件绝对够用。

**为什么符号扫描用词法器而不是 parser**

用户正在敲的时候文件必然残缺（少括号、函数写一半），而 parser 对残缺输入的处理是报错并放弃 —— 那样每次输入到一半补全就全空。词法级扫描不关心括号是否配对，代价是不区分作用域（函数 A 的局部变量与 B 的混在一起）。对补全而言多给候选优于给不出。

**补全词表的来源是 C 源码，不是手写**

`src/lsp_data.h` 由 `vscode-x/tools/gen-completions.js --write` 生成，分别从：

- `src/lexer.c` 的 `kKeywords` / `kZhAliases` / `kZhTypeAliases` → 45 个英文关键字、45 个中文别名、8 个中文类型别名
- `src/bytecode.c` 的 `g_builtins[]` → 内建函数名、参数个数、返回类型
- `src/compile.c` 的 `ty_from_name` 与特殊形式（`print` / `println` / `toInt` / `len` / `array` / `abs` …）→ 类型名与不走内建表的那批函数

改编译器后重新生成即可，提示不会与实现漂移。

> `print` / `println` / `toInt` 这类是编译器里的**特殊形式**，不在 `g_builtins[]`。
> 任何「从内建表提取补全」的工具都会漏掉它们 —— 早先就漏了，表现是补全里没有
> `println`。反过来提取时要小心：`ty_from_name` 附近也在用同样的 `strcmp(n, "...")`
> 判断类型名，必须把类型名从「函数」里剔掉，否则会推荐 `Int(` 这种不能调用的东西。

**诊断为什么不实现**

`publishDiagnostics` 要求「解析整份文件并给出所有错误」。当前编译器是 `main()` 驱动的整流程编译，没有「只解析不生成」的入口，直接复用会把编译器状态搞乱。硬做的话代价是给编译器加一个模式开关，收益只是省一次手动编译 —— 用户按 `Ctrl+B` 或跑 `x build` 得到的报错更完整。

裁决：**先不做**。等 `x build --json-diagnostics` 落地后再接入，那时只是把已有结果翻译成 LSP 格式，不需要第二套解析路径。

**位置编码**

协议位置是 UTF-16 码元偏移，服务端内部是 UTF-8 字节偏移。两个方向的换算都必须走同一组函数（`pos_to_offset` / `offset_to_pos`），且**只在边界处换算一次**。中文一个字：UTF-8 3 字节 / 1 字符 / UTF-16 1 码元 —— 三者都不同，混淆任何一个都会让含中文的行全错。

> 这里踩过的坑：`offset_to_pos` 的早期版本「从 0 走到目标位置，遇换行即 break」，
> 于是它永远返回第一行的列号。文档符号因此全部堆在文件开头，表现是「大纲里点了
> 不跳转」—— 看起来像 UI 问题，实际是位置算错。

### 6.3 锁文件 `x.lock`

```toml
version = 1

[[package]]
name = "math_extra"
version = "1.2.4"
source = "registry+x-pkg://registry.x-lang.org"
checksum = "sha256:9f8e..."

```

锁文件必须提交到版本库。CI 用 `x pkg fetch --locked` 强制使用锁定版本。

### 6.3.1 当前实现的锁文件（v0.14，本地注册表）

上面的格式是**远程注册中心**形态（有 `source` 与 `checksum`）。这两个字段
的意义完全依赖于「从网络上取到的字节需要校验」，而当前实现用的是本地
目录注册表 —— 没有下载、没有传输、没有中间人，`checksum` 无从谈起。
写一个假的校验和比不写更糟：它看起来像被验证过。

所以当前 `x.lock` 只记三样：包名、选定版本、相对目录。

```
# 由 `x pkg install` 生成 —— 不要手工编辑。
lockfile = 1

package name = jsonx
package version = 1.2.3
package dir = jsonx/1.2.3
```

几处有意的选择：

- **不用 TOML**。lock 是生成物，人不该读得很舒服、更不该手改。用和
  `x.toml` 一样的语法反而危险 —— 用户会以为可以照那种格式手写，然后
  和生成器打架。一眼不像手写文件的格式，能少掉一整类「我改了 lock
  怎么没生效」的问题。
- **`dir` 存相对路径**。lock 要进版本库，绝对路径一进 git 就变成
  「在我机器上能编」。
- **原子写**（先写 `.tmp` 再 rename）。写到一半断电会留下被截断的
  lock，而它是「可复现」的唯一依据 —— 坏了比没有更糟。
- 接远程注册中心时，`source` 与 `checksum` 加回来，格式版本升到 2。

### 6.4 依赖解析：MVS

**[裁决]** 采用 **Minimal Version Selection**（Go 的做法），不用 PubGrub 回溯求解。

| 方案 | 优点 | 问题 |
|---|---|---|
| PubGrub（Cargo） | 能给出最优解与人类可读的冲突解释 | 求解慢，复杂冲突时诊断困难 |
| **MVS** | **确定性、O(n) 求解、无需回溯** | 需要生态遵守语义化版本 |
| 饱和求解（npm） | 允许重复版本共存 | 依赖树膨胀、类型不兼容 |

MVS 规则：每个依赖取所有约束中**最高下界**，不做回溯。若某版本不满足上界，直接报错并要求上游升级——把问题暴露在依赖作者侧，而不是让解析器猜。

#### 6.4.0 当前实现与 MVS 的偏差（v0.14）

这一节记录**实现与上表裁决不一致的地方**，不修改裁决本身。

当前实现（`src/registry.c` + `src/semver.c`）的规则是：

1. 有 `x.lock` 且其中版本**仍然满足全部约束** → 沿用它
2. 否则从注册表里挑**满足全部约束的最高版本**
3. 没有任何版本同时满足 → 报错，逐条列出每个约束的来源

与 MVS 的差别在「取哪个」：

| | MVS（规范裁决） | 当前实现 |
|---|---|---|
| 选版本 | 最高**下界**（别人要求的最低版本） | 最高**可用**版本 |
| 意图 | 不主动升级，生态里最保守的可解 | 主动取新，靠 lock 冻结 |
| 升级方式 | 上游提升下界 | 显式 `x pkg update` |

之所以先这样落地：MVS 的「取最高下界」必须配合**内容可寻址缓存与
全局版本图**才成立（要让所有项目共享一份「某包某版本」的字节）。
本地注册表没有这层，取最高下界会和「用户以为自己装的是最新版」
产生持续摩擦。

两者共同保住的性质是一样的：**同一个 lock + 同一份注册表 → 同一个
构建结果**。差别只在「没有 lock 时第一次挑哪个」。所以这不是一个
不可回退的选择 —— 接远程注册中心时，`pick_version` 换成 MVS 下界
策略即可，约束求交、冲突诊断、lock 结构都不用动。

已实现的部分（与 MVS 无关，是解析本身的正确性）：

- 约束求交：同一包的多个约束**全部**必须成立，不是只满足第一个
- 冲突报错：给出每一条约束的来源（`alpha 要求 ^1.0` / `beta 要求 ^2.0`），
  而不是只说「无解」
- 传递依赖：沿 `absorb_deps` 展开，用工作列表而非递归
- path 依赖不参与选版本（版本由文件系统决定）

### 6.4.1 包名规则与引入名的绑定（v0.6）

**核心规则：清单键名 = 源码里的引入名。** 没有隐式映射，没有「包名自动转下划线」这类猜测。

| 层 | 名称 | 约束 |
|---|---|---|
| 注册中心包名 | `x.toml` 的 `[package] name` | `[a-z][a-z0-9_]*`，1~64 字符。**不允许连字符**（见下） |
| 清单依赖键 | `[dependencies]` 的键 | 同上，且**默认等于包名** |
| 源码引入名 | `import @<键名>` | 与依赖键**逐字符相同**，且必须是合法标识符 |

```toml
[dependencies]
http_client = "0.9"                    # 键 = 包名
fast_json = { version = "2.1", package = "json_fast" }   # 键 ≠ 包名，显式 package
```

```x
import @http_client
import @fast_json
```

**为什么禁连字符**：`@http-client` 在源码里无法作为标识符使用——`http-client.get()` 会被解析成减法。若允许连字符，就必须要么引入「自动转下划线」的隐式规则（`grep '@http-client'` 找不到代码），要么强制每次引入都起别名。两条都比「一开始就叫 `http_client`」贵。详论证见 [01](01-语言设计.md) §11.3。

这是与 Cargo/npm 惯例的**故意偏离**，代价明确：生态里看到 `http_client` 而非 `http-client`。收益是引入名、清单键、包名三者永远一致，搜一个名字能同时命中代码与清单。

这条规则的意义：**读代码的人不需要打开 `x.toml` 就知道一个 `@xxx` 在清单里对应哪一行**——因为键名就是引入名，搜索 `@http_client` 与搜索 `http_client =` 得到同一个结果。

反例（明确否决）：

| 否决的做法 | 为什么不行 |
|---|---|
| 包名 `http-client`，代码里写 `import @http_client` | 引入名需隐含转换规则（`-`→`_`），且 grep 断链 |
| 包名 `http-client`，代码里写 `import @httpClient` | 同上，且多一套大小写规则 |
| 引入名由包作者自由指定（如 npm 的 `browser` 字段） | 一个包可以有多个入口名，依赖审计无法闭合 |

**版本共存的处理**：同一包的两个不兼容大版本需要共存时，用键名区分：

```toml
[dependencies]
serde_v1 = { version = "1.8", package = "serde" }
serde_v2 = { version = "2.0", package = "serde" }
```

```x
import @serde_v1 as serde1
import @serde_v2 as serde2
```

代价是**必须显式起别名**（`serde_v1` 这种名字在代码里很别扭）。这是刻意的：版本共存是异常状态，应该看得见。

**保留名**：`std`、`crate`、`self`、`super` 开头的包名不允许注册（防止与路径首段关键字混淆）；与语言关键字同名的包名允许注册但引入时必须起别名。

**包名合法性在 `x pkg add` 时就校验**，不等到写 `import` 才暴露：

```
$ x pkg add json-schema
错误[E0320]: 包名含有非法字符 "-"
 原因   源码里必须能写成 import @json-schema，而 "-" 在 X 中是减号，
        会使 json-schema.parse() 被解析成 json - schema.parse()
 建议   改用下划线：x pkg add json_schema
        若包在注册中心的名字确实是 json-schema，用：
        x pkg add json-schema --as json_schema
```

最后一条是关键：**注册中心的包名可以是别人定的，但引入名由你控制**。`--as` 写入 `package =` 字段，源码里就有合法的引入名。这条路径让「生态里已经有带连字符的包」这个现实不至于变成死锁。

### 6.4.2 别名在依赖层的三种用法

别名是小项目用不上、大项目离不开的东西。它在包管理这一层有三个具体作用：

| 场景 | 写法 | 解决什么 |
|---|---|---|
| **长包名缩短** | `import @very_long_package_name as vlp` | 每次调用少敲 20 个字符，且不改变依赖关系 |
| **版本共存** | `import @serde_v1 as serde1` / `import @serde_v2 as serde2` | 两个不兼容大版本在一个二进制里共存 |
| **非法名修正** | `x pkg add json-schema --as json_schema` | 注册中心已有带连字符的包，本地仍能写出合法标识符 |

三种用法的共同点：**别名只改变「在你这个文件里它叫什么」，不改变「它是谁」**。`x pkg tree` 显示的是引入名（`@vlp`），`x pkg why` 两个名字都能查，`x.lock` 里记的是真实包名——三层信息各司其职，不会因为别名而丢失溯源能力。

**别名与语义搜索的配合**（解决别名唯一的真实代价）：

```bash
x refs Pool              # 语义级查找所有引用，走 LSP 索引而非文本匹配
x refs @mysql            # 查这个包的全部引用，别名不影响
x fmt --expand-alias     # 临时展开别名，用于 grep 式审计
```

文本 `grep` 在别名面前必然有盲区（搜 `mysql.Pool` 找不到写了 `db.Pool` 的文件），这是不许别名就要付更大代价时的必要让步。用语义工具补，而不是禁止别名。

### 6.5 注册中心 API

`registry.x-lang.org` 提供 REST 接口（实现为单个 X 服务）：

```
GET  /api/v1/packages/{name}
GET  /api/v1/packages/{name}/{version}
GET  /api/v1/packages/{name}/{version}/download
POST /api/v1/packages                     (需要 token)
GET  /api/v1/search?q=
```

**内容寻址存储**：包以 `sha256` 命名存储，元数据单独建索引。下载先校验哈希再解包。

### 6.6 缓存布局

```
~/.xle/
├── cache/
│   ├── registry/            # 下载的 .xpkg 归档（内容寻址）
│   ├── src/                 # 解包后的源码（只读，硬链接进项目）
│   ├── build/               # 编译产物缓存（按 (源码哈希, 编译选项, target) 键）
│   └── index/               # 本地索引副本
├── bin/                     # x 自身的二进制
└── config.toml
```

目标：跨项目复用编译产物。同一依赖在 3 个项目中用到，只编译一次。

### 6.7 包格式 `.xpkg`

```
foo-1.2.0.xpkg  (tar + zstd)
├── x.toml
├── x.lock
├── src/
│   └── *.xle / *.xlc        # 英文与中文源文件可混放，编译器按后缀判词表
├── docs/
├── MANIFEST         # 文件列表 + 逐文件哈希
└── SIGNATURE        # 发布者签名的 MANIFEST 哈希
```

签名：Ed25519。`x pkg publish` 用本地私钥签名，`x pkg install` 用注册中心公钥 + 发布者公钥双重验证。可配置 `--trust=first-use`（TOFU 首次信任）降低摩擦。

### 6.8 命令集

```bash
x pkg init                    # 初始化项目
x pkg add name[@ver]          # 添加依赖并写锁；name 即清单键，即 import @name
x pkg add name --as other     # 键名与包名不同时显式指定（写 package = "name"）
x pkg remove name
x pkg update [name]           # 更新锁（默认全部）
x pkg fetch                   # 只下载不编译
x pkg fetch --locked          # CI 用，锁不匹配则失败
x pkg build                   # 编译
x pkg clean                   # 清理产物（不动缓存）
x pkg cache clean             # 清理全局缓存
x pkg tree                    # 依赖树（显示 @名，与源码可对照）
x pkg why name                # 谁引入了这个依赖
x pkg vendor                  # 依赖源码导出到 vendor/
x pkg bundle                  # 冻结为单文件分发
x pkg publish                 # 发布
x pkg search q
x pkg info name
x pkg audit                   # 已知漏洞检查（对比公告库）
x pkg outdated
```

**`x pkg add` 顺带做的事**：检查包名是否为合法标识符（`[a-z][a-z0-9_]*`），非法直接拒绝并提示。这样「包名不可用作引入名」的问题在安装时就被拦下，不会等到写 `import` 才暴露。

**`x pkg tree` 的输出与源码对齐**：依赖树里显示的是 `@名`（引入名），不是包名。两者不同时（`package =` 重命名）额外标注原名：

```
demo 0.3.1
├── @http_client 0.9.2
├── @fast_json 2.1.0  (package: json_fast)
└── @local_util 0.1.0  (path)
```

### 6.9 build script 沙箱

包可以在 `x.toml` 声明 `[build] script = "build.xle"`，在编译前执行（用于代码生成、绑定生成）。这是供应链攻击的主要入口，因此沙箱强制：

- 无网络（除白名单域名，需用户在首次安装时批准）
- 只能写 `target/` 与 `OUT_DIR`
- 60 秒超时
- 不允许 `unsafe` 与 `syscall`（编译时禁用该模块导入）

## 7. 版本与兼容策略

| 变更 | 要求 |
|---|---|
| `0.x.y` → `0.x.z` | 修 bug，允许 |
| `0.x.y` → `0.(x+1).0` | 可破坏，需在 CHANGELOG 标注 |
| `1.x.y` → `1.x.z` / `1.(x+1).0` | 严格向后兼容 |
| `1.x` → `2.0` | 破坏，需要迁移指南 + `x pkg migrate` 支持 |

**语言版本**：`edition = "2026"` 机制（同 Rust）。一个项目固定 edition，编译器同时支持所有历史 edition，语法演进不会砍掉旧代码。每年一个 edition，只在 edition 边界引入破坏性语法变更。

**标准库稳定化流程**：新 API 先进入 `std.experimental.*`，至少两个 edition 后再晋升为 `std.*`。晋升后不破坏。弃用用 `@deprecated(since: "2027", remove: "2029")`，编译器给出警告 + 自动修复建议。
