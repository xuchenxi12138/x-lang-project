# 打包与异地使用

这份文档讲三件事：

1. 这个 VS Code 扩展由哪些文件组成，哪一部分**必须**跟着走
2. 怎么打包成 `.vsix`，怎么在别的机器上装起来
3. 装完之后代码提示不出现时，按什么顺序排查

> 读这份之前先知道一件事：扩展本身只提供**语法高亮**。补全、悬停、
> 参数提示、文档大纲这四类「代码提示」全部来自 `x.exe lsp`。
> 也就是说扩展必须能找到一个能跑的 `x.exe`，否则那四类能力一个都没有。
> 高亮不会因此消失 —— 这正是问题最难被发现的地方。

---

## 一、组成：哪些文件必须跟着走

扩展目录 `vscode-x/` 里真正会被打进 `.vsix` 的只有这些：

| 路径 | 作用 | 缺了会怎样 |
|---|---|---|
| `package.json` | 清单。声明 `main`、激活事件、语言、语法、配置项、命令 | 扩展根本不加载 |
| `src/lspClient.js` | 语言服务客户端。启动 `x.exe lsp`、转发四类请求 | 只剩高亮，没有代码提示 |
| `syntaxes/x.tmLanguage.json` | 高亮语法 | 代码全白 |
| `language-configuration/language-configuration.json` | 括号配对、注释、自动缩进 | 编辑体验退化，功能不坏 |
| `README.md` | 扩展页说明 | 无影响 |

`tools/` **不进包**。它只在开发时用：`gen-completions.js` 从 C 源码提取补全词表，`check-lsp.js` 与 `check-client.js` 做协议验证。这些依赖 node，而装扩展的人不需要 node。

`node_modules/` 也不进包 —— 事实上这个扩展**零依赖**，没有它。

### 和 `x.exe` 的关系

必须分清两个东西：

```
vscode-x/          扩展（编辑器里的那部分）
build/x.exe        编译器 + 语言服务（真正干活的那部分）
```

扩展会按以下顺序找 `x.exe`，用第一个存在的：

1. 设置项 `xlang.executablePath`（用户显式指定，最高优先）
2. 工作区根目录下 `build/x.exe`、`build/x`、`x.exe`、`x`
3. **工作区根目录下一层子目录**里的 `build/x.exe`、`x.exe`
4. 系统 `PATH` 里的 `x`

第 3 条是必需的，不是锦上添花。本项目的常见布局是：

```
F:/项目/x-project/            ← 工作区根（用 VSCode 打开这里）
├── x-lang/
│   ├── build/x.exe           ← 编译器在这里，下一层
│   └── stdlib/
└── 其它项目/
```

只查工作区根的话，这个布局就找不到 —— 而它会静默退回「系统 PATH」，
表现和「你根本没装 x.exe」完全一样。**0.2.0 就是栽在这里。**

限深一层是刻意的：往整棵树递归搜索会在打开大仓库时扫几十万文件，
而扩展激活在打开文件的关键路径上，卡住的代价大于「多一层就找不到」的不便。

扩展会把找到的路径和来源写进日志（`X: 查看语言服务日志`）：

```
x.exe：F:\项目\x-project\x-lang\build\x.exe（来源：子目录 F:\项目\x-project\x-lang\build\x.exe）
服务端就绪：{"name":"x-lang-lsp","version":"0.1.0"}
```

第一行是排查入口 —— 「找到了」和「找到了个错的东西」在功能上都表现为
「没提示」，只有这一行能区分。

## 二、打包成 .vsix

`.vsix` 是一个 zip 包，装着扩展目录的内容加一份清单。装的人不需要联网、不需要 node、不需要 `x.exe`（`x.exe` 单独给）。

### 2.1 一次性准备 `vsce`

```bash
npm install -g @vscode/vsce
vsce --version
```

`vsce` 是 VS Code 官方的打包工具。全球装一次就够。

如果公司内网装不上 npm 包，用 `npx` 也行（它会临时下载）：

```bash
npx @vscode/vsce package
```

### 2.2 打包

```bash
cd x-lang/vscode-x
vsce package
```

产物是 `x-lang-<版本>.vsix`，版本号取自 `package.json` 的 `version`。

正常输出类似：

```
 DONE  Packaged: ...\vscode-x\x-lang-0.2.0.vsix (8 files, 42.1KB)
```

**8 个文件、几十 KB** 是正常的。如果打出来是几 MB，说明 `tools/node_modules` 被包进去了 —— 检查 `.vscodeignore` 里有没有 `tools/**`。

### 2.3 打包时常见的两个报错

**报「Missing publisher」**

`package.json` 的 `publisher` 字段不能为空。本项目用的是 `"publisher": "x-lang"`。本地安装时这个字段只是标识符，不需要去 marketplace 注册。

**报「A 'repository' field is missing」**

同样只是警告，不影响打包。本项目已经填了 `repository`。

**报「Cannot find module 'vscode'」**

说明 `vsce` 在检查依赖。本扩展的 `require('vscode')` 由编辑器在运行时注入，不该出现在 `dependencies` 里 —— 确认 `package.json` 没有 `dependencies` 段即可。

### 2.4 用打包脚本一次做完

仓库里有一份脚本，做了三件事：先跑两套协议验证、再查清单自洽、最后打包。任何一步失败就停下，不产出损坏的 `.vsix`。

```bash
cd x-lang/vscode-x
sh tools/package.sh
```

产物在 `vscode-x/x-lang-<版本>.vsix`。

> 为什么先验证再打包：`.vsix` 一旦发出去，装的人遇到「提示不出现」
> 只会以为是自己的配置问题。而这类问题的根因通常在客户端映射表或
> 服务端 JSON 拼装 —— 两处都是手写的、编译器管不到的。打包前跑一遍
> 是唯一能在源头拦住的机会。

## 三、在别的机器上安装

### 3.1 装扩展

把 `.vsix` 拷过去，然后：

```bash
code --install-extension x-lang-0.2.0.vsix
```

或者在 VS Code 界面里：左侧扩展面板 → 右上角 `...` → `Install from VSIX...` → 选文件。

确认装上：

```bash
code --list-extensions | grep x-lang
# 应输出 x-lang.x-lang
```

装完**必须**重载窗口：`Ctrl+Shift+P` → `Developer: Reload Window`。扩展的 `activate` 只在窗口加载时执行一次。

### 3.2 装 x.exe

把 `build/x.exe` 拷过去。如果是 Windows，只需要这一个文件；语言服务已经编进同一个 exe（`x lsp` 子命令）。

放到哪儿？三个选择，按推荐顺序：

**选择一：项目根目录下的 `build/`**（最省事）

```
我的项目/
├── build/
│   └── x.exe
└── src/
    └── main.xle
```

扩展会自动找到，不需要任何配置。

**选择二：任意位置 + 设置项**

`Ctrl+,` 打开设置，搜 `xlang.executablePath`，填入完整路径：

```
F:/工具/x-lang/x.exe
```

改完重载窗口。

**选择三：放进 PATH**

把 `x.exe` 所在目录加进系统 `PATH`。这样扩展、命令行、别的工具都能直接调 `x`。

### 3.3 验证四类能力都在

打开任何一个 `.xle` 文件，依次试：

| 能力 | 怎么试 | 期望 |
|---|---|---|
| 语法高亮 | 看代码颜色 | 关键字、字符串、注释各有颜色 |
| 补全 | 敲 `pri` 然后 `Ctrl+Space` | 出现 `println`，图标是函数 |
| 悬停 | 鼠标停在 `println` 上 | 浮出「内建函数」说明 |
| 参数提示 | 敲 `arrPush(` | 浮出 `arrPush(#1, #2)` |
| 文档大纲 | `Ctrl+Shift+O` | 列出文件里的函数 |

五个都通过，说明扩展与 `x.exe` 都到位了。

### 3.4 打开扩展日志

`Ctrl+Shift+P` → `X: 查看语言服务日志`。

这个输出面板里会有：

```
启动：F:/.../x.exe lsp
服务端就绪：{"name":"x-lang-lsp","version":"0.1.0"}
```

如果只看到第一行、没有第二行，说明服务端启动了但没完成握手 —— 这时要看服务端自己的 stderr（同样在这个面板里）。

## 四、代码提示不出现时的排查顺序

按这个顺序查，每一步都能缩小范围。**不要跳步** —— 这五层里任何一层断掉，界面上看起来完全一样。

### 第 0 层：装的是哪个版本（最常见）

先看**实际装着的**清单，而不是你手上那个 `.vsix` 的清单：

```bash
ls -d "$HOME/.vscode/extensions"/x-lang*
# 用 Windows 资源管理器看：C:\Users\<你>\.vscode\extensions\x-lang*
```

然后看那个目录里 `package.json` 的 `version` 和 `main`：

```bash
node -e "const p=require('C:/Users/<你>/.vscode/extensions/x-lang.x-lang-0.2.2/package.json');
console.log('version:',p.version,'| main:',p.main||'(无)')"
```

**`main` 是「(无)」就等于代码提示永远不会出现** —— 那是 0.1.0，纯语法高亮扩展，
里面一行 JS 都没有。装了它再装 0.2.x，如果两个目录都在，行为会很混乱。

两个必须知道的事实：

- **目录名不等于版本号。** 从 `.vsix` 装的叫 `x-lang.x-lang-0.2.2`；早年手工
  `cp` 进去的叫 `x-lang-0.1.0`。后者不会被前者覆盖，两个会**同时存在**。
- **不改 `version` 就重新打包，装不上去。** `code --install-extension` 认为
  「同版本已装」会跳过，表现是「装了但代码没变」。改代码后务必先改
  `package.json` 的 `version`。

确认只剩一个、且是 0.2.x：

```bash
# 只应输出一行
ls -d "$HOME/.vscode/extensions"/x-lang*
```

### 第 1 层：扩展有没有激活

`Ctrl+Shift+P` → `Developer: Show Running Extensions`，找 `x-lang`。

- 不在列表里 → 扩展没装上，或者 `package.json` 的 `main` 指向的文件不存在
- 在列表里但标着「inactive」→ 打开的文件语言不是 `x`。看右下角状态栏是不是显示 `X`

语言 id 必须是 `x`。扩展只在 `onLanguage:x` 时激活。

### 第 2 层：x.exe 找没找到

日志面板里如果出现：

```
找不到 x 可执行文件：x
```

说明六个候选路径全落空了。设 `xlang.executablePath` 指向真实路径。

同时会弹一条警告消息 —— 这是刻意加的：扩展起不来必须说话，不能静默。

### 第 3 层：服务端有没有响应

日志里应该有 `服务端就绪`。如果没有，看同一面板里的 stderr 输出。

Windows 上曾经有一类问题：C 运行库把 stdout 当文本流，`\n` 被翻译成 `\r\n`，于是协议头的 `\r\n\r\n` 变成了 `\r\r\n\r\r\n`，客户端永远匹配不到消息分隔符。表现就是「启动了但一直不响应」。现在服务端启动时会把 stdin/stdout 切到二进制模式，这个坑已经堵上。

如果 stderr 里出现 `JSON 解析失败`，把日志贴出来 —— 那是服务端拼装或解析的问题，不是配置问题。

### 第 4 层：能力映射对不对

服务端回了数据但编辑器显示不对（比如补全项图标全是方块、大纲点了不跳转），问题在 `src/lspClient.js` 的映射表：

- `CompletionItemKind`：LSP 的数字编号与 VS Code 的枚举**完全是两套**
- `SymbolKind`：同样两套。LSP 里 Function 是 11，本服务端用的是 12；而 VS Code 的 `SymbolKind.Function` 是 11、`Struct` 是 22
- Position：VS Code 的 `character` 是 UTF-16 码元偏移，与服务端声明的 `positionEncoding` 一致，**不做换算**。这里如果「顺手改成按字节算」，含中文的行会全错

改完这两张表，用 `node tools/check-client.js` 验证，不用开编辑器：

```bash
cd x-lang/vscode-x
node tools/check-lsp.js      # 服务端：38 项断言
node tools/check-client.js   # 客户端：32 项断言
```

这两个脚本真的启动 `x.exe lsp`、真的按 LSP 协议发字节。它们能抓到的东西，比在编辑器里点点看要多得多。

## 五、把 `x.exe` 和标准库一起带走

如果只是想把语言跑起来（不装编辑器扩展），需要的东西很少。但**怎么摆**
有两种合法形态，选错会得到「找不到标准库」。

### 5.1 两种形态

**形态 A：平铺（最省事，适合临时试用）**

```
mydir/
├── x.exe
└── stdlib/
```

`x.exe` 按「exe 所在目录」找 `stdlib/`，与当前工作目录无关。

**形态 B：发行版布局（推荐，适合分发）**

```
xlang-0.8.0-p0/
├── bin/
│   └── x.exe
├── lib/
│   ├── stdlib/          ← 9 个 .xle
│   └── packages/        ← 包缓存（可为空）
├── conf/
│   └── xlang.env
├── src/                 编译器源码（可选）
├── docs/                规格与本文（可选）
├── tests/p0/            测试集（可选）
├── games/               示例（可选）
├── vscode-x/            编辑器扩展（可选）
├── tools/               构建脚本（可选）
├── VERSION
├── README.md
└── 发行说明.md
```

形态 B 就是 `sh tools/release.sh` 的产出，放在 `release/xlang-<版本>/`。

### 5.2 查找顺序（决定了什么能拷、什么不能）

`src/main.c` 的 `find_stdlib_root()` 按这个顺序试，用第一个命中的：

| # | 候选路径 | 服务于 |
|---|---|---|
| 1 | `<exe 目录>/stdlib` | 形态 A、源码树（`build/x.exe` + `stdlib/` 并列） |
| 2 | `<exe 目录>/../lib/stdlib` | **形态 B**（本节的发行包） |
| 3 | `<exe 目录>/lib/stdlib` | 省掉 `bin/` 的扁平式摆法 |
| 4 | `<exe 目录>/../stdlib` | 源码树的另一种摆法 |
| 5 | `<当前目录>/stdlib` | 临时把 exe 拷进项目的用法 |

`X_STDLIB_PATH` 优先于全部五项，语义是**指向 stdlib 目录本身**
（里面直接是 `math.xle` / `json.xle`），不是它的父目录。写错会明确报
「该目录不存在」，不会静默回退 —— 见下面 5.4。

`X_REGISTRY` 可覆盖包注册表位置（默认在 `x.exe` 旁边的 `packages/`）。
两个环境变量都是为了「同一份 exe 在测试里指向不同目录」而加的，
正常使用不需要设。

### 5.3 为什么 `lib/` 这一层不能省

`bin/x.exe` 单独拷走会找不到标准库 —— 它只按**自己所在目录**去推，
不会去猜「我旁边那个目录叫 lib 还是 stdlib」。

所以：**要拷就整个目录一起拷**。这不是保守，是唯一能保证正确的做法。
`tools/release.sh` 的自检就是干这个的：打完包在包内跑一次
`import std.math`，布局不对当场失败，不会发出去才发现。

### 5.4 手工验证（不依赖脚本）

```bash
cd <发行包根>
./bin/x.exe run tests/p0/01-hello.xle          # 编译器 + 解释器
printf 'import std.math\nprintln(normalize(5.0, 0.0, 10.0))\n' > t.xle
./bin/x.exe run t.xle                          # 标准库（应输出 0.5）
rm -f t.xle
```

两条都过，说明 exe / 解释器 / 标准库三条链路正常。只过第一条是不够的 ——
`01-hello` 不用标准库，它绿了只能证明 exe 能启动。

`x.exe` 静态链接 mingw 运行时，只依赖 Windows 自带的
`KERNEL32` / `USER32` / `GDI32` / `WS2_32` / `msimg32` / `msvcrt`，
所以 `bin/` 里不需要附任何 DLL。哪天它开始依赖 `libgcc_s_seh-1.dll`
之类，就必须把那个 DLL 也放进 `bin/`，否则在没装 mingw 的机器上闪退 ——
判断方法：`objdump -p bin/x.exe | grep "DLL Name"`。

## 六、版本升级

改完代码重新打包时，**先改 `package.json` 的 `version`**。

不改版本号直接 `vsce package`，产出的 `.vsix` 与已装版本号相同，`code --install-extension` 会认为「已经装了」而不覆盖。表现是「装了但代码没变」，非常容易误判成没生效。

```bash
# 1. 改版本
#    package.json → "version": "0.2.1"

# 2. 重新打包
cd x-lang/vscode-x && vsce package

# 3. 装
code --install-extension x-lang-0.2.1.vsix
```

## 七、清单：从零到能用的最短路径

```bash
# ── 在开发机上 ──────────────────────────────
cd x-lang
sh tools/build.sh                     # 编出 build/x.exe
cd vscode-x && vsce package           # 产出 .vsix

# ── 拷到目标机器 ────────────────────────────
#   需要带走：x-lang-0.2.0.vsix、x.exe（以及 stdlib/ 如果你要跑代码）

# ── 在目标机器上 ────────────────────────────
code --install-extension x-lang-0.2.0.vsix
mkdir -p 我的项目/build && cp x.exe 我的项目/build/
# 重载窗口，打开 .xle 文件，敲 pri 试补全
```
