# 04 · 中文编程方案

> 需求：中文编程作为**包外挂**，语言本体保持英文。
> 本文证明这个需求可以在**零语法改动、零运行时成本**的前提下实现，并说明三条必须同时成立的技术路径。

---

## 1. 结论先行

中文编程不是一个包能解决的，它是**三层叠加**，缺一层体验就断裂：

| 层 | 名称 | 作用 | 形态 |
|---|---|---|---|
| L1 | 词法映射层 | 让 `如果` 等价于 `if`，`函数` 等价于 `fn` | 编译器内置的**可选**模块，非默认加载 |
| L2 | 标准库别名层 | 让 `打印` 等价于 `println`，`矩阵` 等价于 `Matrix` | 一个纯 X 包 `zh`（`import @zh`） |
| L3 | 诊断本地化层 | 编译错误、警告、panic 消息用中文 | 编译器的 i18n 资源包 |

**关键判断**：L1 如果做成外挂包（即需要第三方插件改词法器），就永远无法进入编辑器的语法高亮、无法被 LSP 理解、无法保证不同实现一致。所以 L1 必须**内建在编译器里但默认关闭**，通过 `x.toml` 或源文件首行开启。这叫「官方外挂」，是唯一可行的形态。

---

## 2. L1：词法映射层

### 2.1 原理

词法器维护一张**关键字别名表**。原始 token 流为英文关键字；开启中文模式后，词法器在识别标识符时先查别名表，命中则产出对应的英文关键字 token。**后续所有阶段（语法、类型、代码生成）完全不知道中文存在。**

```x
// 开启方式（按优先级从高到低，但没有第一条时后两条才有意义）
// 1. 文件后缀（v0.8 起为**唯一常规入口**，见 01 §2.1）
//    foo.xlc  → 自动中文模式，不需要任何声明或命令行参数
//    foo.xle  → 英文模式，中文关键字降级为普通标识符
// 2. 命令行冗余开关（仅对 .xle 有效，用于快速试写）
x run --lang=zh file.xle

// 3. 项目级 x.toml（对未显式后缀化的场合兜底，v0.8 后不推荐）
[package]
lang = "zh"
```

**为什么把后缀提到第一位**：中文模式的开关如果只存在于「声明」或「命令行」里，那么一个 `src/utils.xle` 到底是中文还是英文，取决于编译器读到它时恰好带着什么参数——这是不可复现的。文件后缀写进文件名，`foo.xlc` 走到哪台机器、哪个构建系统、哪个 CI 里，都是中文模式。这也顺带解决了 `.xlc` 文件在编辑器里被错误高亮的问题：后缀即声明，编辑器插件读后缀就够了。

**首行 `#lang zh` 仍被接受**，但语义降级为「断言」：写在 `.xlc` 里是冗余确认，写在 `.xle` 里等价于 `--lang=zh`（并触发一条 lint 提示，建议改后缀）。**声明不能把 `.xle` 变成中文之外的什么东西**——后缀是权威，声明只能确认它，不能推翻它。

### 2.2 别名表设计原则

| 原则 | 说明 |
|---|---|
| 一对一 | 每个英文关键字最多一个中文别名，减少记忆负担 |
| 可混用 | 同一文件内 `if` 与 `如果` 可共存（词法层归一化后无区别） |
| 不占标识符 | 中文别名**不保留**——不开启中文模式时，`如果` 是合法变量名 |
| 无歧义 | 别名不得与另一个别名的英文等价物冲突 |
| 稳定 | 一旦发布不改名（改名等于破坏代码） |

### 2.3 完整别名表（45 个关键字）

| 英文 | 中文 | 英文 | 中文 |
|---|---|---|---|
| `fn` | `函` | `if` | `如果` |
| `let` | `令` | `else` | `否则` |
| `var` | `变` | `while` | `当` |
| `const` | `常` | `for` | `遍历` |
| `struct` | `结构` | `in` | `于` |
| `enum` | `枚举` | `loop` | `循环` |
| `trait` | `特征` | `break` | `跳出` |
| `impl` | `实现` | `continue` | `继续` |
| `mod` | `模组` | `match` | `匹配` |
| `import` | `引入` | `case` | `情形` |
| `pub` | `公开` | `return` | `返回` |
| `self` | `自身` | `yield` | `产出` |
| `true` | `真` | `spawn` | `派生` |
| `false` | `假` | `par` | `并行` |
| `null` | `空` | `defer` | `延后` |
| `mut` | `可变` | `void` | `无` |
| `ref` | `引用` | `dyn` | `动态` |
| `type` | `类型` | `where` | `约束` |
| `as` | `作为` | `or` | `或` |
| `not` | `非` | `comptime` | `编译期` |
| `extern` | `外部` | `unsafe` | `不安全` |
| `from` | `从` | `catch` | `捕获` |
| `do` | `做` | | |

表外预留三项（不是关键字，中文模式仍需要中文写法）：

| 英文 | 中文 | 说明 |
|---|---|---|
| `and` | `且` | 逻辑运算符而非关键字，与 `or`/`not` 三件套对齐 |
| `async` | `异步` | 当前是语法糖，若转关键字别名已就绪 |
| `await` | `等待` | 同上 |

**`use` 不在表中**：v0.5 已把引入与重导出统一归到 `import`，`use` 从关键字表移除，中文也不再有 `使用` 这个别名（避免与 `引入` 混淆）。

**`from` 的中文是 `从`**（v0.6 加入）。中文的引入语句语序与英文一致，来源在行首：

```x
引入 标准.math                       // import std.math
从 标准.math 引入 开方, 幂             // from std.math import sqrt, pow
从 标准.math 引入 sqrt 作为 开方       // from std.math import sqrt as 开方
```

### 2.4 类型名与字面量

类型名属于 `std` 的符号，不进词法层，而在 L2 里解决。但以下**内建类型**（编译器内置，非库符号）必须进词法层：

| 英文 | 中文 | 英文 | 中文 |
|---|---|---|---|
| `Int` | `整数` | `Bool` | `布尔` |
| `Float` | `浮点` | `Char` | `字符` |
| `Complex` | `复数` | `String` | `字符串` |
| `Array` | `数组` | `void` | `无` |

中文模式下，`整数` 与 `Int` 完全等价，可混用。

### 2.5 词法层的实现约束

- **零成本**：别名表是编译期的静态 map，查表在词法器内联，每 token 一次哈希。实测影响 < 1% 编译时间。运行时零成本（token 已归一化为英文）。
- **零歧义**：别名归一化发生在 Unicode 标识符识别**之后**。因此 `如果将` 这样的变量名不会被误切成 `如果` + `将`（最长匹配 + 整 token 比较）。
- **可关闭**：不开中文模式的代码，`如果` 就是普通标识符。这保证英文项目不会被中文别名污染命名空间。

### 2.5.1 模块路径的语言中立性（v0.6）

模块路径的**首段**有四个上下文关键字（[01](01-语言设计.md) §2.4、§11.5），中文模式下映射如下：

| 英文 | 中文 | 作用 |
|---|---|---|
| `std` | `标准` | 语言内置标准库 |
| `crate` | `包` | 当前包根 |
| `self` | `自身` | 当前模块 |
| `super` | `上级` | 父模块 |

但**路径的后续段不翻译**，原因很简单：那些段是真实的模块名（`std.math` 的 `math` 是包内目录名），翻译它们就等于要求标准库为每个模块维护两套目录。想用中文模块名，走 L2 别名包（§3）。

**`@` 包前缀不翻译**，符号本身语言中立：

```x
引入 @mysql                     // 中文模式下的包引入，@ 保持原样
引入 标准.math                   // 首段译，后续段不译 → import std.math
从 @mysql 引入 连接, 行            // 具名符号来自包导出；包若在 L2 里定义了中文名，这里才能用中文
从 @mysql 引入 Connection 作为 连接   // 更常见：显式起中文别名，不依赖包作者
```

**这一节解决的是「包名、模块名、字符串三者同形」的问题**：无论中文还是英文模式，引入语句里都不出现引号，包一定带 `@`，模块一定是裸路径。中文模式下 `引入 "路径"` 同样被 lint 拒绝。

### 2.6 完整示例

下面是 `mean.xlc` 的全部内容（**注意：没有 `#lang zh`，也不需要它**——后缀已经说明了）：

```x
引入 标准.math
引入 标准.collections 作为 阵

公开 函 均值(数据: 阵.数组[浮点]) -> 浮点 {
    变 和 = 0.0
    遍历 值 于 数据 {
        和 += 值
    }
    返回 和 / 数据.长度.转浮点()
}

公开 函 主() {
    令 数据 = 阵.数组.自([1.0, 2.0, 3.0, 4.0])
    打印("均值 {均值(数据)}")
}
```

同一段代码的英文版：

```x
import std.math
import std.collections as arr

pub fn mean(data: arr.Array[Float]) -> Float {
    var sum = 0.0
    for v in data {
        sum += v
    }
    return sum / data.len.toFloat()
}

pub fn main() {
    let data = arr.Array.from([1.0, 2.0, 3.0, 4.0])
    println("均值 {mean(data)}")
}
```

**两者编译产物完全一致**（逐字节相同，这是可验证的验收标准）。

## 3. L2：标准库别名包 `zh`

### 3.1 形态

纯 X 包，内容只有 `pub import` / `pub from ... import ... as ...` 重导出与薄包装函数。无任何逻辑。

**包名用 `zh`**（合法标识符，符合 [03](03-标准库与包管理.md) §6.4.1 的命名规则），用户写 `引入 @zh`：

```x
// pkg/zh/src/lib.xle
pub mod 数组 {
    pub 从 std.collections 引入 Array 作为 数组
    pub 函 自[T](xs: [T]) -> 数组[T] { 数组.from(xs) }
    pub 函 空[T](n: Int) -> 数组[T] { 数组.withCapacity(n) }
}

pub mod 数学 {
    pub 从 std.math 引入 sqrt 作为 开方, abs 作为 绝对值, pow 作为 幂
    pub 常 圆周率 = std.math.PI
    pub 函 阶乘(n: Int) -> Int { std.math.factorial(n) }
}

pub mod 文件 {
    pub 函 读文本(p: String) -> String throws IoError { std.fs.readText(p) }
    pub 函 写文本(p: String, s: String) -> void throws IoError { std.fs.writeText(p, s) }
}
```

**这里暴露一个必须解决的冲突**：`zh` 包内部的模块名是中文（`数组`、`数学`），而 [01](01-语言设计.md) §11.3 规定「子模块路径段必须是合法标识符」。中文标识符在 X 里合法（§1 铁律 6：标识符永远 Unicode），所以 `引入 @zh.数学` 语法合法。

但**包名 `zh` 本身不能是中文**——包名要进 URL、文件名、注册中心索引键，用中文会引入编码与大小写折叠问题（不同 Unicode 规范化形式的目录名在某些文件系统上不合并）。所以规则是：

| 层 | 语言 | 例 |
|---|---|---|
| 包名 | 必须 ASCII 下划线式 | `zh` |
| 包内模块名 | 可中文 | `@zh.数学` |
| 包导出的符号名 | 可中文 | `@zh.数学.开方` |

**引入名的绑定规则不受影响**：`import @zh` 绑定名字 `zh`（最后一段），中文模块名只在路径后半段出现。

### 3.2 覆盖范围与优先级

不可能给整个标准库起中文名——那会形成两个平行 API，维护成本翻倍且必然不同步。策略是：

| 层级 | 覆盖策略 | 中文名数量 |
|---|---|---|
| 内建类型（Int/Float/…） | 词法层全量映射 | 8 |
| 高频函数（数学、字符串、数组、文件、打印） | 全量中文别名 | ~200 |
| 中期函数（网络、数据库、并发） | 全量中文别名 | ~300 |
| 低频/专业 API（linalg 分解、crypto） | **不做中文别名**，直接用英文 | 0 |

**裁决**：总中文别名控制在 500 个以内。理由：超过这个规模，用户无法记住哪个函数有中文名、哪个没有，反复查文档的成本超过收益。低频 API 直接用英文是更诚实的做法。

### 3.3 中英混用的合法性

包内 `pub import` 产生的符号与英文符号**并列存在**，无命名冲突（不同标识符）。因此：

```x
令 a = 数组.自([1,2,3])
令 b = Array.from([1,2,3])    // 完全等价，可混用
```

这不是妥协，而是刻意的设计：中文名是**语法糖层**，不是替代层。用户按需替换，不必全盘切换。

### 3.4 使用方式（完整示例）

```x
#lang zh
引入 @zh                    // 别名包：数组/数学/文件 三个中文模块
从 @zh.数学 引入 开方, 幂      // 也可只取具体函数，来源始终是裸路径

公开 函 主() {
    令 xs = 数组.自([1.0, 4.0, 9.0])
    令 ys = xs.映射(|x| 开方(x))         // 用 L2 的中文函数名
    打印("结果 {ys}")
}
```

对应的英文写法（不需要 `@zh`，直接用标准库）：

```x
import std.collections
from std.math import sqrt, pow

pub fn main() {
    let xs = collections.Array.from([1.0, 4.0, 9.0])
    let ys = xs.map(|x| sqrt(x))
    println("结果 {ys}")
}
```

**关键点：`@zh` 是普通的包，享受 §6.4.1 的全部规则**——包名 `zh` 合法（ASCII 标识符）、清单里写 `zh = "0.1"`、源码里 `引入 @zh`。它没有任何「语言内置」特权。这意味着别名包可以被任何人 fork、改造、替换成自己的版本，不存在「官方中文层」这种不可替换的东西。

## 4. L3：诊断本地化

### 4.1 三种语言档

| 档位 | 行为 |
|---|---|
| `--msg=en`（默认） | 全部英文 |
| `--msg=zh` | 全部中文 |
| `--msg=both` | 英文 + 中文对照（学习期推荐） |

也可用环境变量 `X_LANG=zh` 或 `x.toml` 的 `[package] msg-lang = "zh"`。

**`.xlc` 后缀不影响诊断语言。** 这是一条刻意的分离：后缀管的是**源码里的关键字用哪套词**，`--msg` 管的是**编译器对你说话用哪套词**，两者正交。理由很实在——一个中英混放的项目（`utils.xle` + `报告.xlc`）里如果有 `--msg` 跟着后缀走，编译一次就会输出一半英文一半中文的诊断，而人要在同一屏里对着两套术语找错。所以诊断语言只由 `--msg` / `X_LANG` / `x.toml` 三个显式位置决定，缺省 `en`；想让整个项目中文，在 `x.toml` 写一行 `msg-lang = "zh"` 就行，不必去改每个文件。

### 4.2 诊断消息规范

所有编译器诊断消息以消息 ID 索引，资源文件独立：

```toml
# locale/zh.toml
[messages]
E0001 = "类型不匹配：期望 {expected}，实际得到 {found}"
E0001.note = "如需转换，请使用 {hint}"
E0002 = "变量 {name} 未定义"
E0002.note = "是否想用 {suggestion}？"
E0100 = "整数溢出：{ty} 最大值为 {max}"
W0200 = "浮点数不应使用 == 比较"
W0200.note = "建议使用 assertApprox 或比较差值"
```

### 4.3 中文诊断的排版要求

这是中文编程最容易做砸的地方。硬性要求：

1. **错误位置用字节偏移，不按字符宽度**。中文宽度占 2 列，`^^^` 标记必须按显示宽度计算。
2. **代码片段对齐**：行号右对齐、源码原样输出、标记行用 `^` 覆盖等宽字符数（中文字符算 2 个 `^`）。
3. **拼接消息时不硬编码英文介词**。用占位符 `{}` 而非字符串拼接，中文语序由译者控制整句。

正确示例：

```
错误[E0001]: 类型不匹配：期望 浮点，实际得到 整数
  --> src/main.xle:12:18
   |
12 |     令 结果 = 数据 / 2
   |                    ^ 这是 整数
   |
   = 提示：如需转换，请使用 2.转浮点()
```

### 4.4 术语表（强制统一）

中文编程的可信度取决于术语一致性。以下是定稿术语，禁止同义词混用：

| 英文 | 统一中文 | 禁止使用 |
|---|---|---|
| function | 函数 | 方法（method 专用）、过程 |
| method | 方法 | 函数 |
| parameter | 参数 | 形参（口语可用，文档不用） |
| argument | 实参 | 参数 |
| variable | 变量 | 值 |
| constant | 常量 | 常值 |
| type | 类型 | 型号 |
| trait | 特征 | 特质、接口（interface 专用） |
| interface | 接口 | 特征 |
| struct | 结构体 | 结构（作关键字时为 `结构`，作概念时为结构体） |
| array | 数组 | 阵列 |
| slice | 切片 | 片段 |
| index | 索引 | 下标（口语可用） |
| reference | 引用 | 指针（pointer 专用） |
| pointer | 指针 | 引用 |
| borrow | 借用 | 借 |
| move | 移动 | 迁 |
| clone | 克隆 | 复制（copy 专用） |
| copy | 拷贝 | 克隆 |
| generic | 泛型 | 模板 |
| module | 模块 | 模组（作关键字时为 `模组`，作概念时为模块） |
| package | 包 | 包裹 |
| crate | 编译单元 | 包 |
| compile-time | 编译期 | 编译时 |

| null | 空 | 空值、nil |

## 5. 中文编程的边界（明确不做的事）

避免走弯路，以下明确排除：

| 不做 | 理由 |
|---|---|
| 中文标点 `（）` `；` `，` | 中英文标点混用会让词法层歧义（全角逗号在字符串外无意义），且需处理输入法切换成本。**用英文标点** |
| 中文数字 `一二三` | 与标识符无法区分，且数值计算中无价值 |
| 全角空格 | 肉眼不可见，是最难查的 bug |
| 中文运算符（`加`/`减`） | 运算符已有数学符号，`+ - * /` 比任何文字都短 |
| 中英混排自动转换 | 编译器不做「智能猜测」，必须显式写 |
| 代码自动翻译（英→中） | 生成的代码不可读（标识符仍是英文），且翻译歧义无解 |
| 中文编程成为独立语言分支 | 会分叉生态。必须是同一语言的视图 |

## 6. 生态与工具链的中文支持

| 工具 | 中文支持 |
|---|---|

### 6.1 中文标识符的列宽计算

格式化器与错误标注必须用**东亚宽度**（East Asian Width）计算列宽：`W`/`F` 类字符占 2 列，其余占 1 列。这需要内嵌 Unicode 表（约 40 KB，编译期生成）。

```x
// 实现要点
comptime fn buildWidthTable() -> [u8; 0x110000] { ... }  // 编译期生成，产物内 40KB
fn displayWidth(s: String) -> Int { ... }                // 走表查询，O(n)
```

#### 6.1.1 显示宽度 ≠ 位置列号（两者必须分开）

这是中文支持里最容易做错的一处，踩过一次之后写进规范：

| 概念 | 中文一个字算几？ | 用在哪 | 错了会怎样 |
|---|---|---|---|
| **显示宽度** | 2 列 | `x fmt` 对齐、诊断标签补空、终端里的表格 | 视觉上参差不齐 |
| **位置列号** | 1 列（1 个码点） | `file:line:col`、编辑器跳转、`x://open` 的 `col` 参数 | **跳错位置**——用户按报的列过去，光标停在别处 |

具体到实现：

- 词法器的列计数器**只对码点的首字节加 1**，对 UTF-8 续字节（`10xxxxxx`）不加。于是「令 年龄 = 姓名 + 不存在的」里 `不存在的` 报第 13 列，与 VS Code 光标显示的列一致。
- 诊断输出里的标签补空、`x fmt` 的对齐、未来的表格渲染，全部走 `utf8_width()`（`W`/`F` 类算 2）。
- **不能把两者合成一个函数**。若列号也按显示宽度算，那么在汉字前插一个 ASCII 字符会让该汉字之后的所有列号 +2，而编辑器光标按码点走，于是又对不上了。

这条分工的直接体现：`位置` 标签占 **4 显示列**（2 汉字×2），但它后面的路径列号是按**码点**数的。同一个输出行里同时用到两种口径，这正是必须把两个概念在代码里也分开的原因。

#### 6.1.2 P0 的实际覆盖

P0 的 `utf8_width()` 覆盖以下区间，够用且不引入 40 KB 表：

| 区间 | 宽度 | 说明 |
|---|---|---|
| `U+0300–036F`、`U+1AB0–1AFF`、`U+20D0–20FF`、`U+FE20–FE2F` | 0 | 组合符号（叠加在基字上，不占位） |
| `U+200B`、`U+FEFF` | 0 | 零宽空格、BOM |
| `< U+0020`、`U+007F` | 0 | 控制字符 |
| `U+1100–115F`、`U+2E80–303E`、`U+3041–33FF`、`U+3400–4DBF`、`U+4E00–9FFF`、`U+A000–A4CF`、`U+AC00–D7A3`、`U+F900–FAFF`、`U+FE30–FE4F`、`U+FF00–FF60`、`U+FFE0–FFE6`、`U+20000–3FFFD` | 2 | CJK 主区与扩展区、假名、谚文、全角形式 |
| 其余 | 1 | 拉丁、希腊、西里尔、大多数符号 |

P1 换成从 Unicode 数据库生成的完整表（`EastAsianWidth.txt`），届时 `utf8_width()` 与 `comptime` 生成的表合并，P0 这份手写区间表作为测试基准保留——它是少数几个「手写比生成更可信」的地方，因为手写版覆盖的正是我们真正关心的字符。

## 7. 验收标准

中文编程方案是否成功，用以下可验证指标判定：

| 指标 | 目标 |
|---|---|
| 同一程序中英两版编译产物逐字节一致 | 必须（CI 门禁） |
| 词法层性能影响 | < 1% |
| 运行时性能影响 | 0（别名在编译期消失） |
| 中文别名总数 | ≤ 500 |
| 诊断消息中文覆盖率 | 100%（含 note 与 hint） |
| 术语表一致性 | 100%（CI 扫描 locale 文件） |
| 中文标识符下 fmt 对齐正确 | 100%（含混排测试集） |
| 无需任何第三方插件即可中文编程 | 是 |
| **中英两版引入语句指向同一依赖集** | 必须：`引入 标准.math` 与 `import std.math` 解析到同一模块；`引入 @zh` 与 `import @zh` 解析到同一包 |
| **`.xlc` 与 `.xle` 编出的字节码逐字节一致** | 必须（后缀只改词表，不改标记流） |
| **中文模式无需命令行开关** | 必须：只凭 `.xlc` 后缀即可编译，`--zh` 缺失不影响结果 |
| **中文前缀下的列号与编辑器一致** | 必须：`令 年龄 = 姓名 + 不存在的` 报 `2:13`（不是按字节的 `2:23`） |
| **诊断标签按显示宽度对齐** | 必须：`位置`（4 显示列）与 `error:`（6 显示列）之后的内容起点同列 |
| **UTF-8 端到端** | 必须：BOM 剥离、非法编码明确报错、中文路径可读写、Windows 控制台不乱码（`tools/check_utf8.sh` 11 项） |

第 1 条是关键：它证明中文编程真的是「视图」而不是「分支」。如果产物不一致，说明别名表在某处泄露到了语义层，必须修。

## 8. 一个现实提醒

中文编程的真实价值在**教学、行业软件（医疗/政务/工业）、以及非英语母语团队的早期上手**。它的价值不在替代英文编程。

因此本方案的设计取向是：**中文是一等公民的视图，英文是唯一的源语言**。这样做的后果是——中文编程的用户最终会自然学会英文标识符（因为包生态是英文的），而这恰恰是好事：他们能用全世界的库，只是在起步阶段用母语思考。

反过来，如果做成「中文独立生态」（所有包都中文命名），就必然分裂成两个互不兼容的世界，最终两边都做不大。这是我不建议的路线，也是本方案在 L2 层刻意「只做 500 个别名」的原因。
