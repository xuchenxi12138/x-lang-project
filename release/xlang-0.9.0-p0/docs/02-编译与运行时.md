# 02 · 编译与运行时

> 本文定义双档执行模型、三层 IR、目标代码生成、汇编的适用边界、运行时架构、差分测试。
> 解释器的高性能实现细节见 [07](07-高性能解释器.md)。
> 这是全项目风险最高的部分，因此先写清楚「性能从哪来」，再写「怎么实现」。

---

## 1. 先回答一个问题：性能真的来自汇编吗？

**[裁决]** 不是。**绝大多数的性能来自编译器的中后端（寄存器分配、循环优化、内联、向量化），而不是手写汇编。** 这个判断决定了整个实现策略，所以放在最前面。

手写汇编的真实收益与代价：

| 场景 | 汇编相对编译器生成代码的收益 | 代价 |
|---|---|---|
| 热路径数值内核（如 `dot`、`gemm` 微内核） | +10% ~ +40%（编译器难以完美做寄存器分块） | 可维护性极差，每换平台重写 |
| 协程上下文切换 | 必须用汇编（无法用高级语言表达） | 约 100 行，一次写对长期不动 |
| GC/ARC 屏障、原子操作 | 必须用汇编或内联汇编 | 每平台几十行 |
| 系统调用入口 | 必须用汇编 | 每平台 30 行 |
| 普通业务代码 | **0% ~ -20%**（手写通常更慢） | 开发效率 1/10 |
| 整个编译器用汇编写 | **负收益** | 项目必然失败 |

所以正确的策略是：**编译器用高级语言写（自举），只在编译器无法表达或能带来确定收益的地方用汇编。** 这才是「最大性能释放」的现实路径。

如果你的目标是「性能接近 C 且可接受」，这个策略足够。如果你坚持整条链路手写 NASM，我的结论是：**这个项目在 P2 之前就会因为无法维护而停滞**。我把两种路径都写出来，你选。

## 2. 执行模型：两档共享一份字节码

> 解释器的高性能实现细节见 [07 · 高性能解释器](07-高性能解释器.md)。本节只定位它在整体架构中的位置。

### 2.1 决策：解释 + AOT 双档，共用一套字节码

**[裁决]** 提供两个执行档位，**二者的输入是同一份寄存器式字节码**：

| 档位 | 命令 | 实现 | 启动 | 相对 native |
|---|---|---|---|---|
| 解释 | `x run` / `x script` / `x watch` | 直接线程化分派 + 超指令 + 类型化指令 | < 3 ms | 1/5 ~ 1/4 |
| AOT | `x build` | 同一字节码 → 优化 pass → 机器码 | 进程启动 | 0.9 ~ 1.1 |

关键设计：**字节码即 Mid IR 的序列化形式**（详见 [07](07-高性能解释器.md) §4）。AOT 不是「另一条前端路径」，而是「对同一份字节码跑优化 pass」。这使两档的语义一致性由构造保证，不需要两套实现同步。

```
源文件 .xle / .xlc
   │ 共享前端：词法 → 语法 → 类型推断 → 单态化 → comptime → 异常集合推断
   ▼
寄存器式字节码（.xbc，定长 6 字节指令）
   │
   ├─→ 解释器：超指令合成 → 直接线程化执行
   └─→ AOT：优化 pass ×13 → x86-64 / AArch64 / C 后端 → 单文件二进制
```

### 2.2 命令行语义

| 命令 | 行为 |
|---|---|
| `x run file.xle` | **解释执行**（首次会生成字节码并缓存到 `.xcache`，二次起 < 3 ms 启动） |
| `x run file.xlc` | 同上，中文关键字模式（由后缀自动开启，无需 `--zh`） |
| `x run file.xbc` | 直接执行字节码，跳过前端（分发、嵌入、性能基准用） |
| `x script file.xle` | 同 `x run`，不写缓存（给一次性脚本） |
| `x watch file.xle` | 常驻：监听文件 → 重新生成字节码 → 重启解释执行（开发主循环） |
| `x build` | AOT 编译产单文件二进制（默认含 `.xmap`，可回溯） |
| `x build --release` | 优化编译 |
| `x build --emit=bc` | 只产 `.xbc` 字节码，不产二进制（供分发或嵌入） |

**后缀与命令的合法组合**（非法组合直接报错，不做猜测）：

| 后缀 | `run` | `script` / `watch` | `build` | `disasm` |
|---|---|---|---|---|
| `.xle` | ✓ | ✓ | ✓ | ✓ |
| `.xlc` | ✓ | ✓ | ✓ | ✓ |
| `.xbc` | ✓ | ✗（已是字节码，无可监听） | ✗（输出即输入） | ✓ |
| 其他 | ✗ | ✗ | ✗ | ✗ |

`.xbc` 对 `build` 与 `script` / `watch` 关闭的理由是**语义单一**：字节码是编译产物，把产物再编译一次只能得到它自己，而「监听一个不会被作者编辑的文件」没有意义。允许这些组合只会让脚本里出现看起来能跑其实空转的调用。

`x run` 与 `x build` 的输出必须**逐字节一致**（浮点运算按位相同，不因优化改变结果）。这条由 `--verify=diff` 在 CI 中强制。

### 2.3 为什么不提供 REPL

**这是唯一保留的「不做」项**，与执行档位无关。

理由：泛型单态化下，「上一个 cell 定义的泛型实例」无法被下一个 cell 复用而不重新单态化；加上有栈协程与异常展开表，增量定义函数在保持语义一致的前提下不可实现。做一个语义不一致的 REPL 比没有更糟。

补偿：`x watch` + `--param` 热替换（见 §7.2）；数据分析场景另提供 `x notebook`（见 [08](08-多领域支撑.md) §3 缺陷 8）。

### 2.4 解释器的第二个用途：comptime 求值

`comptime` 需要在编译期执行任意 X 代码，这没有编译方案。因此**编译器内嵌一个字节码解释器**用于 `comptime`：

- 与运行时解释器**同一份代码**（不是两套实现），只是：
  - 受限环境：无 IO、无网络、无随机数、无时钟；
  - 内存与栈深度有硬上限（默认 256 MB / 深度 1000）；
  - 不加载超指令（编译期代码执行次数少，合成不值得）。
- 因为共用实现，`comptime` 与运行时的**语义天然一致**，且 compiler bug 只需修一处。

这比「单独写一个 comptime 解释器」省下约 4000 行，并且消除了「comptime 里能算但运行时不能算」这类经典不一致 bug。

## 3. IR 设计

### 3.1 三层 IR 的关系

```
AST
 │  降级
 ▼
Core IR（结构化、SSA、带完整类型）      ← comptime 求值、类型驱动的降级
 │  线性化 + 虚拟寄存器分配
 ▼
寄存器式字节码（定长 6 字节，可序列化为 .xbc）
 │  超指令合成（仅解释路径）
 ├───────────────────────────────┐
 ▼                               ▼
解释器直接执行                   Mid IR（SSA + CFG，去类型）
                                  │ 13 个优化 pass
                                  ▼ 代码生成
```

**字节码不是独立的一层，它是 Core IR 的线性化产物。** 这一层设计是 [07](07-高性能解释器.md) §4 的核心论点：让解释器与 AOT 共享输入，把「双档」的维护成本压到接近零。

### 3.2 Core IR（结构化、SSA、带类型）

用于类型驱动的降级与 comptime 求值。结构化控制流保留到字节码生成阶段。

```
指令集（约 64 条）：
  const, load, store, alloc, call, callIndirect
  binop(Add/Sub/Mul/Div/Rem/And/Or/Xor/Shl/Shr/...)
  cmp(Eq/Ne/Lt/Le/Gt/Ge), unop(Neg/Not/BitNot)
  br, condbr, switch, ret, phi
  cast(IntToFloat/FloatToInt/Bitcast/Trunc/Ext)
  slice, index, indexCheck, boundsCheck
  arcRetain, arcRelease, arcMove, send
  tryBegin, tryEnd, landingPad, throw, rethrow
  panic, unreachable
```

`tryBegin`/`tryEnd`/`landingPad`/`throw` 四条是异常的下限表示。字节码阶段展开为显式的正常边/展开边与清理代码，机器码阶段产出 unwind 表。细节见 [06](06-异常与诊断.md) §7、§8。

### 3.3 寄存器式字节码

定长 6 字节（1 opcode + 3×16 位槽位），约 140 条基础指令。完整格式、指令表、虚拟寄存器分配算法见 [07](07-高性能解释器.md) §3.2。

设计要点只有三条：

1. **定长**：`ip += 6` 是常量，取指无需解码长度。
2. **三地址**：`ADD_I64 dst, a, b` 一步到位，指令数比栈式少 46%（Shi et al., TACO 2008 实测）。
3. **指令带类型**：`ADD_I64` / `ADD_F64` / `ADD_ANY` 分开。静态类型路径上零类型检查、零装箱——这是 X 相对 CPython 的结构性优势（[07](07-高性能解释器.md) §2）。

### 3.4 Mid IR（SSA + CFG，去类型）

- SSA + CFG，显式 phi。
- 类型降级为位宽 + 符号性 + 浮点格式。
- 显式插入：边界检查、零检查、溢出检查、ARC 屏障、栈图（协程挂起点）、`landingPad`。
- 优化 pass 序列（固定顺序，可配置）：

| # | Pass | 作用 |
|---|---|---|
| 1 | Inline（小函数、`@inline`） | 消除调用开销，为后续优化创造条件 |
| 2 | SCCP 稀疏条件常量传播 | 常量折叠 + 死分支消除 |
| 3 | DCE | 死代码消除 |
| 4 | SROA | 聚合体标量替换，减少内存往返 |
| 5 | Mem2Reg | 局部变量提到寄存器 |
| 6 | LoopRotate / LICM | 循环旋转与不变量外提 |
| 7 | LoopUnroll（`@unroll`） | 展开小循环 |
| 8 | GVN | 全局值编号，公共子表达式消除 |
| 9 | TailCall | 尾调用消除（必做，递归降级为循环） |
| 10 | Vectorize（SLP + Loop） | 自动向量化到 SSE/AVX2/NEON |
| 11 | ExtractValue | 消除超指令残留的中间值（字节码里不存超指令，见 §3.5） |
| 12 | RegAlloc（线性扫描 + 活跃区间分裂） | 寄存器分配 |
| 13 | Peephole / BranchLayout | 强度削减、指令合并、hot/cold 分离 |

**[裁决]** 寄存器分配用**线性扫描 + 活跃区间分裂 + 二次机会着色**，不用图着色。理由：线性扫描编译速度是图着色的 10 倍以上，生成的代码质量差距在 5% 以内，而编译速度对开发体验影响更大。

### 3.5 超指令不落盘

超指令（[07](07-高性能解释器.md) §3.3）只对解释器有价值，对 AOT 是噪音（优化 pass 会自己合并）。因此：

```
.xbc 文件 = 140 条基础指令
   ├─→ 解释器加载后：合成超指令（按 profile 选组合）→ 执行
   └─→ AOT 加载后：直接进优化 pass
```

这保证两条路径各自最优，而源头的字节码只有一份。**这是「共享字节码」这个设计能成立的关键细节**——如果不这样切分，就得为两档维护两份字节码。

### 3.6 新增语法该花多少钱（v0.17 总结）

加一门语言的语法特性时，第一反应往往是「加一条指令」。这个反应是错的，
代价被严重低估。这一节把账算清楚，作为后续所有语法扩展的选型依据。

**Phase 0 的实际成本结构：**

```
parser.c  ──构造 AST──→  compile.c  ──发射──→  Bytecode  ──┬─→ interp.c      解释执行
                                                          ├─→ codegen_c.c  AOT 生成 C
                                                          └─→ xbc.c        .xbc 落盘
```

关键事实：**`codegen_c.c` 与 `interp.c` 只消费 `Bytecode*` 和 `FuncProto*`，
从不接触 AST；`xbc.c` 序列化的是字节码而不是 AST。**

由此推出两条结论：

| 改动类型 | 需要改的文件 | 三条通道是否自动继承 |
|---|---|---|
| 只改 parser + compile（降级到现有指令） | 2 个 | 是，全部自动 |
| 新增一条字节码指令 | 6 处（见下） | 否，且需升格式版本 |

新增指令的六处改动：`x.h` 枚举、`interp.c` 分派、`codegen_c.c` 生成、
`xbc.c` 序列化、`bc_op_stack_effect` 栈效应表、反汇编器。

其中 `xbc.c` 那条最贵：**`.xbc` 格式版本一升，所有已编译产物全部失效**。
文件头有版本号，加载时校验（§6.4），旧产物直接拒绝。这在开发期是每次都要
重编全部包，在发布后是用户侧的静默不兼容。

**[裁决] 新语法优先选「能降成现有字节码」的实现路径。**

v0.17 的四个特性全部走这条路，零新增指令：

| 特性 | 降级成什么 | 用了哪些现有指令 |
|---|---|---|
| 三元 `?:` | 与 `if` 表达式同一骨架 | `JUMP_IF_FALSE` / `JUMP` |
| 数组字面量 `[a,b]` | `NEW_ARRAY` + N×(DUP + `arrPush` + POP) | 已有的数组指令 |
| 空值合并 `a ?? b` | `DUP` + `PUSH_NULL` + `NE` + `JUMP_IF_FALSE` | 已有的比较与跳转 |
| 可选链 `a?.b` | `DUP` + 判非 null + 复用成员访问 | 已有的字段访问 |
| `match` | 比较链（`LOAD tmp` + `EQ` / `GE_NUM` / `LE_NUM`） | 已有的比较与跳转 |
| 字符串插值 `"a{x}b"` | `"a" + (x) + "b"` | 已有的字符串加法 |

代价是每条特性多两三条指令（`??` 比专门的 `JUMP_IF_NOT_NULL` 多两条）。
换的是**字节码格式不动、`.xbc` 不需重新生成、AOT 与解释器不需要任何改动**。
这笔交易在本阶段做得值：六条特性总共只改了 `parser.c`、`compile.c`、
`lexer.c`（插值需要保留转义原文）三个文件。

**一条反过来的教训**：`EX_STACK_REF` 这个伪节点不是「降级技巧」，而是
「复用」的技巧。可选链要先算对象、判 null，再交给正常的成员访问逻辑；
而那段逻辑的第一步就是「编译对象表达式」。让那个子节点退化成空操作，
就能复用字段偏移、类/结构体分支、可见性检查的全部分支，不必抄一遍。
抄一遍的后果不是代码长，而是**两处规则迟早走样**。

## 4. 目标代码生成

- x86-64 后端：优先做，Windows/Linux 共用（SysV 与 Win64 ABI 分别处理）。
- AArch64 后端：P3 再做，先靠 C 后端过渡。
- 汇编器与链接器：**不自研**。生成 `.s` 或直接产 ELF/Mach-O/PE 目标文件（P2 后期），交给 `gcc`/`clang` 的汇编器与系统链接器。理由：自研汇编器与链接器是 5 人年工作量，且不影响性能。

**单文件二进制**：链接时把运行时静态链接进来，`--static` 对 musl 目标默认开启。

## 5. 汇编在项目中的确切位置

这是对你「用汇编开发」要求的正式落地清单。列出每处的必要性。

### 5.1 必须用汇编（无法用高级语言表达）

| 位置 | 平台 | 规模 | 说明 |
|---|---|---|---|
| 协程上下文切换 | x86-64 | ~120 行 | 保存/恢复 callee-saved 寄存器 + 栈指针 + FPU 状态 |
| 协程初始入口 trampoline | x86-64 | ~30 行 | 首次调度进入用户函数，处理栈对齐与异常帧 |
| 系统调用桩 | x86-64 Linux (syscall)、Windows (SSN) | ~80 行 | 避免依赖 libc |
| 陷阱/信号处理入口 | x86-64 | ~150 行 | 段错误捕获、栈溢出检测、panic 栈展开的底层 |
| **展开恢复入口（personality routine）** | x86-64 | ~90 行 | 表驱动展开的落地实现，见 [06](06-异常与诊断.md) §7.1 |
| 原子原语（无 lock-free 指令时） | 全平台 | ~40 行 | CAS、fence；多数情况可用内联汇编 |
| 栈探测（大栈分配） | Windows | ~20 行 | `__chkstk` 等价物 |

合计约 **530 行汇编**。这是真实需要的全部。

personality routine 值得单独说明：它是异常展开的「每条栈帧被问一次『这一层有没有 catch / 需不需要跑清理』」的回调。Itanium ABI 要求它以特定寄存器约定被调用，且必须不破坏展开上下文，用高级语言写需要大量内联汇编与不透明约束——直接手写反而清晰。

### 5.2 值得用汇编（确定收益）

| 位置 | 说明 | 预期收益 |
|---|---|---|
| `dot` / `axpy` / `scal` 向量内核 | 手写 AVX2/FMA，编译器自动向量化在这些模式上常留 20% 余量 | +15% ~ +30% |
| `gemm` 微内核（4×16 分块） | 寄存器分块必须精确控制，编译器不做 | +30% ~ +100%（对比朴素实现） |
| 内存拷贝/填充（大块） | `rep movsb` / AVX 非临时存储 | +20% ~ 50% |
| 字符串 UTF-8 校验与解码 | 手写 SIMD 分类 | +3 ~ 5× |
| 哈希（xxHash/SipHash 内核） | 手写轮函数 | +10% |

注：`gemm` 若允许链接 OpenBLAS，则无需自研。**建议：P2 之前链接系统 BLAS，P4 再自研。**

### 5.3 不应该用汇编

| 位置 | 理由 |
|---|---|
| 编译器前端/中端 | 汇编写解析器是自虐，无任何性能收益（编译时间瓶颈不在这） |
| 标准库容器（Array/Map/String） | 高级语言写更可维护，热点已在 §4.2 单独处理 |
| 运行时 GC/ARC 逻辑 | 计数增减用内联汇编即可，整体逻辑用 X 写 |
| 包管理器 | 纯 IO 密集，汇编写毫无意义 |

### 5.4 自举路径

```
P0-P1：编译器用 C 写（bootstrap 编译器，只做 MVP 语法子集）
P2   ：X 能编译自己 → 用 X 重写编译器 → 自举（stage1 = C 版编译的 X 版，stage2 = X 版自己编译自己）
       验证：stage2 与 stage3 二进制完全一致（fixpoint 测试）
P3+  ：删除 C 版 bootstrap，只用 X 版
```

**[裁决]** 保留 C 版 bootstrap 编译器不删，作为「信任根」。这是 GCC/Rust/Go 的共同做法，属于工程必需而非妥协。

## 6. 运行时（runtime）架构

### 6.1 组成

```
libruntime（静态链接，两档共用，按 Profile 裁剪）
├── start       启动：栈探测、TLS 初始化、参数解析、main 调用、退出
├── interp      解释器核心：直接线程化分派、超指令、内联缓存（C 写，约 1.2 万行）
├── bc          字节码加载与校验：.xbc 解析、超指令合成、快速化
├── arc         ARC 头、retain/release、弱引用、周期检测（可选）
├── alloc       分配器：域本地缓存 + size class + 大对象直通 mmap/VirtualAlloc
├── domain      并发域：域结构、迁移原语、@shared 原子计数、task-local 槽位
├── sched       协程调度器：M:N，工作窃取，汇编上下文切换
├── unw         异常展开：table / sjlj 两档、personality routine、清理遍历
├── trace       栈回溯：.xmap 解析 / 解释器帧链、符号化、局部变量快照
├── report      诊断渲染：六段式输出、OSC 8 超链接、`x://` URI 生成
├── trap        陷阱处理：越界/溢出捕获、栈溢出检测、段错误转 PanicError
├── sync        Mutex/RwLock/Atomic（含内存序）/Channel/Condvar
├── num         数值内核：dot/axpy/gemm/transcendental（AVX2/NEON）
├── str         UTF-8 操作、格式化、SIMD 扫描
└── ffi         dlopen/dlsym 包装、C 字符串转换
```

各模块的**可裁剪性**（Profile 的落点）：

| 模块 | 体积（估） | 可被哪些 Profile 裁掉 |
|---|---|---|
| `start` + 分配器 + `arc` | 40 KB | `kernel`（无分配）、`core` |
| `interp` + `bc` | 80 KB | 所有 AOT 产物（`--strip-interp`） |
| `domain` + `sched` | 40 KB | `kernel`、`embedded`、`core` |
| `unw` + `trace` + `report` | 60 KB | `embedded`（`--unwind=abort`）、`core` |
| `str` + `num` | 30 KB | `core` 之外都保留 |

目标体积（三档分别度量，详见 §10.4）：

| 目标 | 内容 | 上限 |
|---|---|---|
| 最小可执行 | `start` + `alloc` + `arc` | **< 120 KB** |
| 标准运行时 | 上述 + `domain`/`sched`/`unw`/`trace`/`report`/`str` | **< 400 KB** |
| 完整发行 | 全部 + 全套 std | 不设上限，靠 `--gc-sections` + LTO |

### 6.2 分配器

**[裁决]** 自研分配器，不用系统 malloc。理由：ARC 需要精确的对象头控制，且协程调度需要线程本地缓存。

设计要点：

- **Size class**：8/16/24/32/48/64/96/128/192/256/384/512/1024/2048/4096/8192/16384 B，超过直接 `mmap`。
- **域本地缓存**：每个**并发域**（不是线程，见 [01](01-语言设计.md) §6.6）持有 64 个 size class 的空闲链表。域迁移时缓存随域走，因此无需加锁。这是 Domain 模型让分配器同时拿到「无锁」与「正确」的原因。
- **中央堆**：每 size class 一个，跨域用自旋锁（争用低，因为大部分分配走域本地缓存）。
- **对象头**：8 字节（前 32 位为 ARC 计数，后 12 位为 size class 索引，剩余为标志位）。计数值上限 2^20，超出后对象被标记为「饱和」永不清零（防溢出）。
- **回收**：release 到 0 时归还域本地缓存，缓存超阈值时批量归还中央堆。
- 可选：`--alloc=system` 切到系统 malloc（调试用）、`--alloc=trace` 记录分配点（泄漏排查）、`--no-alloc`（`kernel`/`core` Profile 下强制，所有分配改为 `arena` 或静态缓冲）。

### 6.3 协程调度器

- M 个 OS 线程（M = 物理核数，可 `--threads=N` 覆盖），N 个协程，**按 Domain 分组调度**。
- 每个 Domain 任一时刻最多在一个线程上运行；挂起后可被任意线程恢复（整域迁移）。
- 每线程一个本地运行队列（环形，容量 256），全局队列用于溢出与迁移。
- 工作窃取：空闲线程从其他线程队列尾部窃取一半。**窃取单位是协程，不是 Domain**——Domain 内的协程若分到不同线程，Domain 不变式就被破坏了。因此窃取时若目标协程属于一个「仍有协程在跑」的 Domain，则跳过它，只窃取属于已完全挂起的 Domain 的协程。
- 协程栈：初始 1 KB，栈溢出时通过信号/异常捕获扩栈（最大 1 MB）。
- 阻塞系统调用：调度器检测到阻塞操作（`fs`/`net` API 内部标记），自动把当前线程降级为「阻塞专用」并唤醒一个新线程（同 Go 的 `handoff`）。
- **网络 IO**：Windows 用 IOCP，Linux 用 io_uring（回退 epoll），macOS/iOS 用 kqueue。这是性能关键，不抽象成统一层则无法发挥各自优势，因此网络模块分平台实现、共享接口。

### 6.4 启动流程

**解释档**（`x run`，冷启动目标 < 3 ms）：

```
_entry（汇编 20 行）
  → 栈探测 → 设置 TLS
  → runtime.init（分配器、调度器、诊断渲染器）
  → mmap .xbc → 校验魔数与版本 → 超指令合成
  → 解析 argv（零拷贝视图）→ 构造 main 帧
  → 进入解释循环
  → 正常返回：exit(code)
  → 未捕获异常：report 渲染六段式诊断 → exit(1)
```

**AOT 档**（`x build` 产物）：

```
_entry（汇编 20 行）
  → 栈探测 → 设置 TLS
  → runtime.init（不含 interp/bc，除非 --keep-interp）
  → 解析 argv → 调用 main
  → 正常返回：exit(code)
  → 未捕获异常：report 渲染六段式诊断（含 OSC 8 链接）→ exit(1)
  → 未捕获 Error：同上，但标注「不应被捕获」，exit(101)
  → runtime.fini（flush、join 残留协程、报告泄漏 if --check-leaks）
```

两档的**启动期差异只有「是否加载字节码」**。其余（TLS、分配器、诊断渲染）完全共享。

`report` 在退出路径上必须**不分配内存**（用预分配的 64 KB 静态缓冲），否则 OOM 场景下无法打印诊断——这是 Java 也踩过的坑（`OutOfMemoryError` 时连错误消息都拼不出来）。

## 7. 编译速度与增量

**AOT 路径**的编译速度目标：**10 万行项目全量编译 < 8 秒，增量 < 300 ms。**

但注意：**日常开发的回路不依赖编译速度，而依赖解释器启动速度**。写代码时用 `x run`（< 3 ms 启动），只在需要交付性能时用 `x build`。这让「编译慢」不再是日常痛点——这是双档架构最实际的收益。

| 场景 | 命令 | 时间预算 |
|---|---|---|
| 改一行，跑一遍 | `x run`（已缓存字节码） | **< 50 ms** 总回合 |
| 改一行，自动重跑 | `x watch` | 保存到输出 **< 150 ms** |
| 首次跑新文件 | `x run`（需生成字节码） | 单文件 < 200 ms |
| 交付构建 | `x build --release` | 10 万行 < 8 s（非交互，可接受） |
| CI 全量构建 | `x build --release --target=all` | 不设上限，靠并行 |

AOT 编译速度的手段（仍要做，但优先级从 P0 降到 P1）：

| 手段 | 说明 |
|---|---|
| 模块并行编译 | 依赖图 DAG 上的拓扑并行，默认线程数 = 核数。依赖图由 `import` 语句静态构建（[01](01-语言设计.md) §11），不依赖配置：`@` 边来自 `x.toml` 声明，裸路径边来自文件系统，二者在解析期就固化 |
| 查询式编译（salsa 式） | 每个编译单元是缓存 key 的纯函数，输入不变则复用 |
| 字节码缓存 | `.xbc` 按内容哈希缓存，解释与 AOT 共用 |
| 增量代码生成 | 只有变化的函数重新生成机器码，其余复用 `.o` 片段 |
| 单态化去重 | 相同形状的实例只生成一次 |
| 惰性单态化 | 只单态化实际调用的泛型实例（不做预实例化） |
| comptime 结果缓存 | 相同输入 comptime 调用结果持久化 |

### 7.1 `x watch` 的工作方式

```
x watch experiment.xle
  ├─ 首次：生成字节码 → 缓存 → 解释执行子进程
  ├─ 监听 src/ 全部 `.xle` / `.xlc` 文件（含本项目模块，不含第三方包）
  ├─ 文件变化 → 防抖 80 ms → 重新生成字节码（增量，< 100 ms）
  │    ├─ 成功 → 终止旧进程 → 启动新进程（保留命令行参数与环境）
  │    └─ 失败 → 保留旧进程继续跑，红色输出编译错误（不重启）
  └─ 按 r 手动重启，按 q 退出
```

保留旧进程这个小设计很关键：改到一半语法错误时，服务不中断，你可以继续看它的日志。

### 7.2 参数热替换

弥补没有 REPL：

```x
// experiment.xle
comptime LR = 0.01              // 编译期常量，可被 --param 覆盖
let EPOCHS = 1000               // 顶层 let，同样可覆盖
```

```bash
x watch experiment.xle --param LR=0.05 --param EPOCHS=200
```

值在生成字节码前注入（等价于源码里改字面量），走增量路径，通常 **< 100 ms** 出结果。比 AOT 路径快一个量级，因为只需重新生成字节码，不需生成机器码。

| 能力 | 实现 |
|---|---|
| 栈回溯 | 两档统一：解释档用帧链直接读行号表；AOT 档用 `.xmap`。**输出格式完全相同**，见 [06](06-异常与诊断.md) §4 |
| 异常定位链接 | OSC 8 超链接 + `file:line:col` + `x://` 协议，见 [06](06-异常与诊断.md) §5 |

| 断点调试 | 解释档：原生支持（解释器带 `BREAKPOINT` 指令，无需 gdb）；AOT 档：`x debug` 包装 gdb/lldb |
| 泄漏检测 | `--check-leaks`：退出时报告未释放对象及分配点 |
| 数据竞争检测 | `--check-races`：影子内存（P3，只覆盖 `unsafe` 与 `send` 边界） |
| 内存剖析 | `--profile=heap`：分配点直方图 |

| 字节码剖析 | `--profile=ops` / `=pairs` / `=dispatch`：指令计数、超指令命中率、分派失败率（见 [07](07-高性能解释器.md) §6.2） |
| 运行时追踪 | `--trace=sched,arc,alloc,unwind`：环形缓冲，崩溃时 dump |

**解释档的调试体验优于 AOT 档**，这是它的第二个价值：`x run --breakpoint=src/app.xle:42` 直接停在源码行，不需要 gdb，不需要符号文件，不需要重新编译。日常调试应先用解释档定位，只在需要性能数据时切 AOT。

### 8.1 差分测试

两档共享同一份字节码，因此差分测试在构造上可行：

```bash
x test --verify=diff
```

每个测试的做法：

1. 解释档执行 → 记录 stdout、stderr、退出码、**以及所有对外副作用**（写文件、网络请求、随机数消耗序列）。
2. AOT 档执行 → 记录同样内容。
3. **逐字节比对**。

这是编译器正确性的核心保障。覆盖范围：

| 测试类型 | 说明 |
|---|---|
| 语言特性测试（目标 2000 个） | 每个语法/语义特性至少一个用例 |
| 浮点专项 | 断言两档浮点结果**按位相同**（`-ffast-math` 类优化默认关闭） |
| 异常专项 | 断言两档栈回溯内容一致（除地址值） |
| comptime 专项 | 同一表达式在 comptime 与运行时求值必须一致（第三个参照点） |
| 随机程序生成 | 生成器产随机算术/分支/循环程序，两档比对（每日 CI 跑 10 万个） |

不通过即阻塞合并。这条规则的严格执行，是「双档不会语义漂移」的唯一保证。

> 原设计「放弃解释器」时，这个自动验证手段随之失去。恢复解释器后它回来了，且比原来更强——因为参照点从两个变成三个（解释 / AOT / comptime）。

目标三元组（v0.4 扩充）：

| 平台族 | 目标 |
|---|---|
| Windows | `x86_64-windows-msvc`、`aarch64-windows-msvc` |
| Linux | `x86_64-linux-gnu`、`x86_64-linux-musl`、`aarch64-linux-gnu`、`aarch64-linux-musl` |
| macOS | `x86_64-macos`、`aarch64-macos` |
| **Android** | `aarch64-linux-android21`、`x86_64-linux-android21` |
| **iOS** | `aarch64-apple-ios14`、`aarch64-apple-ios14-sim` |
| **WASM** | `wasm32-wasi`、`wasm32-unknown-unknown` |

**平台特殊约束**（必须知道，否则会踩坑）：

| 平台 | 约束 | 应对 |
|---|---|---|

| 裸机 | 无 libc、无分配器、无展开表 | `--profile=kernel` + `--unwind=sjlj` 或 `abort` |

### 9.1 实现状态（v0.11）：C 后端已通，三平台可产

P0 阶段没有直接生成机器码，而是走 **C 后端**：把字节码翻译成 C 代码，再调用本机 gcc/clang 编译。这是 §5.3「不自研汇编器与链接器」的直接延伸——与其发 `.s` 再找汇编器，不如发 C 让编译器一条龙做完。约 1300 行同时覆盖三个平台。

`x output` 的三档产物：

| 命令 | 产物 | 用途 |
|---|---|---|
| `x build a.xle -o a.xbc` | `.xbc` 字节码 | 单发字节码，目标机用 `x run` 执行 |
| `x build a.xle --emit=c -o a.c` | C 源代码 | 拿到任意有 C 工具链的机器上自己编译 |
| `x build a.xle --emit=exe -o a.exe` | 本机可执行文件 | 开箱运行 |

#### 9.1.1 一个必须先讲清的事实：可执行格式不是可选参数

用户最初的问法是「希望能指定编译格式，在 Windows 上编译成 exe，在 Linux 和 macOS 上编译成对应的文件」。

这里有一个容易误解的点值得写下来：**可执行文件格式由操作系统决定，不是程序员可以指定的选项**。

| 平台 | 唯一可行的格式 | 说明 |
|---|---|---|
| Windows | PE（`.exe`） | 内核加载器只认 PE |
| Linux | ELF | 只认 ELF |
| macOS | Mach-O | 只认 Mach-O |

不存在「在 Windows 上产出一个 ELF 并直接运行」这种事。所以正确的接口是 `--target <三元组>`（选平台），格式由平台推出；而不是 `--format elf`（选格式）。后者会允许用户构造出「格式对但跑不了的产物」——比如 `--format elf` 配 Windows 目标，产出的文件在两边都不能跑。

`x target list` 会打印当前支持的所有目标及其对应格式。表里只列**当前真能产出并验证过**的集合，不列「计划支持」的。原因：交叉编译最常见的失败是「工具链配错，gcc 成功退出但产出的是宿主格式」，如果一个格式在表里但实际产不出来，用户会花很长时间排查自己的代码。

#### 9.1.2 产物格式自检

因为「gcc 成功退出但产出宿主格式」这类事故太常见，`--emit=exe` 之后会**读一次产物文件头**，确认它是目标平台该有的格式：

```c
XObjFormat got = fmt_detect_file(out_path);
if (got != tgt->format) {
    diag_error(..., "产物格式不符：期望 %s，实际 %s", ...);
    diag_note("快捷验证：`%s -dumpmachine` 会打印它默认的目标三元组。", cc);
}
```

读 4 个字节就能挡住整类事故，比「拿到目标机上跑一下才发现」便宜得多。

#### 9.1.3 平台边界隔离

为了让「跨平台」这件事在代码层面成立而不只是承诺，所有平台相关代码收在 `platform.c/h` 两个文件里。**其他任何源文件不许 `#include <windows.h>`、不许出现 `#ifdef _WIN32`**。这条规则由 `tools/check_portable.sh` 机械验证，一条 grep 就能查出违规：

```sh
grep -rn "_WIN32\|_MSC_VER\|__APPLE__\|__linux__" src/*.c src/*.h \
    | grep -v "platform\.[ch]:"
```

这条守门的价值在于：跨平台承诺最容易被无声破坏的方式，不是「不支持某平台」，而是某天有人为了图快在业务代码里塞了一个 `#ifdef _WIN32`，于是那个文件从此只能在 Windows 上编译，而没人注意到。

#### 9.1.4 中文路径下的 AOT 编译（Windows 特有的坑）

这是实现过程中最花时间的一个坑，值得完整记录，因为它不是「代码写错了」，而是 MinGW 工具链的行为。

**现象**：项目在 `F:\项目\...`（含中文），`--emit=exe` 报
```
Fatal error: can't create C:\Users\<乱码>\AppData\Local\Temp\ccXXXXXX.o
```

**根因有三层，逐层才是完整答案**：

1. `cc1`/`as` 把 `.o` 中间文件写到 `%TEMP%`，而默认 TEMP 是 `C:\Users\<用户名>\AppData\Local\Temp`。用户名含中文时，工具链的 ANSI 路径处理会拼出一个不存在的路径。
2. **只改 cwd 不够**。切到纯 ASCII 目录后仍失败——因为 TEMP 还是原来那个。必须同时把子进程的 `TMP`/`TEMP` 改到 ASCII 目录。
3. **`-pipe` 在这个 MinGW 版本上不生效**（文档里常见的推荐做法），实测仍落 `.o` 到 TEMP。

**最终解法**（三条一起做才成立）：

| 措施 | 为什么必须 |
|---|---|
| 子进程 cwd 切到纯 ASCII 目录 | `as` 会把 `.o` 放到 cwd |
| 子进程 `TMP`/`TEMP` 指向同一目录 | `cc1` 把 `.o` 放到 TEMP |
| 生成的 C 源文件也复制到该目录 | `cc1` 读含中文路径的源文件同样失败 |
| 产物先在该目录生成，再用自己的文件 API 搬到目标路径 | `ld` 打不开含中文的输出路径（`cannot open output file <乱码>/out.exe`） |

配套有两个必须知道的实现细节：

- **`CreateProcess` 的环境块必须是一整块连续内存**（`"K=V\0K=V\0...\0\0"`）。把 `_environ`（指针数组）强转成 `LPVOID` 传进去会得到 `ERROR_INVALID_PARAMETER (87)`，因为那些字符串在堆上是分散的，系统顺着第一段往后读，读到第二个指针就崩。必须自己摊平。
- **`_spawnvp` 不能指定 cwd**，所以这一层必须走 `CreateProcess`。

这些细节全部封在 `platform.c` 的 `plat_spawn_with_tmp()` 里。调用方只说「用这个目录当临时目录」，三平台代码完全一致——类 Unix 上该参数被忽略（文件系统本来就是字节串，无此问题）。

## 10. Profile 系统

六领域的需求互相冲突（详见 [08](08-多领域支撑.md) §2 矩阵）。解法不是做六个语言，而是**一份核心 + 七个 Profile**。

Profile 决定三件事，且只有这三件：

| 层 | 作用 | 举例 |
|---|---|---|
| 链接层 | 哪些运行时模块进二进制 | `kernel` 不链 `sched`/`alloc` |
| 语言层 | 哪些语法/特性可用 | `kernel` 下 `spawn` 报错；`embedded` 下 `try` 报错 |
| 默认值 | 优化档、展开机制、分配策略 | `mobile` 默认 `-Os` + `--strip` |

### 10.1 七档定义

| Profile | 目标场景 | 不链接 | 禁用特性 | 默认 |
|---|---|---|---|---|
| `server` | 长驻服务 | — | — | `-O2` `--unwind=table` |
| `desktop` | 桌面 GUI | — | — | `-O2` |
| `mobile` | 移动核心库 | 部分 std | 运行时代码生成、`dlopen` | `-Os` `--strip=all` |
| `kernel` | 内核/驱动 | `alloc`（可配）、`sched` | 协程、`dlopen` | `-O2` `--unwind=sjlj` |
| `embedded` | MCU/RTOS | `alloc`、`sched`、`unw` | 协程、动态分配 | `-Os` `--unwind=abort`（需要异常时改 `--unwind=sjlj`，`try` 随之解禁） |
| `wasm` | 浏览器 | 系统调用、原生线程 | 原生线程、`dlopen` | `-O3` |
| `core` | 无 OS 环境 | 除 `mem`/`ptr`/`num` 外全部 | 除纯计算外全部 | `-O2` `--unwind=abort` |

### 10.2 用法

```toml
# x.toml
[package]
profile = "server"
```

```bash
x build --profile=kernel --unwind=sjlj
x build --profile=mobile --target=aarch64-linux-android21
x build --profile=web --target=wasm32-wasi
```

### 10.3 诊断带 Profile 上下文

Profile 不仅控制编译，还控制错误信息的内容。这是它区别于「一堆编译开关」的地方：

```
错误[E0321]: 当前 Profile 不支持协程
  --> src/fs.xle:88:5
   |
88 |     spawn { flushAsync() }
   |     ^^^^^ `kernel` Profile 下不可用
   |
   = 说明：内核态没有调度器，`spawn` 无法实现。
   = 建议：改为同步调用，或用 `defer` 延迟到安全点执行。
   = 相关：`x build --profile=server` 可用协程。
```

同样的代码在 `server` Profile 下编译通过。**错误信息能指出「是因为 Profile 才不可用」，而不是让人怀疑语法错了。**

### 10.4 体积可度量

Profile 的核心价值之一是体积。三个目标必须分开度量：

| 目标 | 内容 | 上限 |
|---|---|---|
| 最小可执行 | core + 分配器 + 启动 | **< 120 KB** |
| 标准运行时 | 上述 + 调度器 + 展开 + 诊断 + 字符串 | **< 400 KB** |
| 完整发行 | 上述 + 全套 std | 不设上限（靠 gc-sections + LTO） |

`x build --report=size` 输出符号级体积归因（自研，类似 Bloaty），让「为什么二进制这么大」可回答。

## 11. 汇编开发可行性对照

如果你仍然希望最大化汇编比例，这里是按「汇编占比」排列的三条路线：

| 路线 | 汇编占比 | 交付时间（1 人全职，估） | 性能 | 结论 |
|---|---|---|---|---|
| A 主流路线 | ~450 行（0.1%） | 语言可用 14~18 个月，生态可用 3 年 | 基准的 0.9~1.1×（C 级） | **推荐** |
| B 内核汇编路线 | 数值内核 + 运行时约 8 千行（3%） | 同上 +50% 时间 | 基准的 1.0~1.2× | 可接受，P3 后做 |
| C 全汇编路线 | ~15 万行（100%） | **无法估，实际上不可完成** | 理论上 1.1~1.3× | **不推荐**，且编译器质量（优化 pass）才是性能主语 |

路线 C 的致命问题不在工作量，而在**无法迭代**：你改一个语法规则要重写几千行汇编；你无法快速试错优化 pass；你无法用工具链调试。而语言的性能 90% 取决于优化 pass 的质量，这部分无论用什么都得写，用汇编写只会让它写不出来。

**我的建议：走路线 A，把路线 B 的清单作为 P3 的性能专项。** 这样既能拿到 C 级性能，又能在两年内真正用上这门语言。
