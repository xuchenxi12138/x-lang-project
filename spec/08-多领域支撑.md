# 08 · 多领域支撑审查

> 目标场景从「数值计算」扩展到六个方向：网站服务端、桌面软件、移动 app、操作系统、AI 开发、数据分析。
> 本文先做缺陷审查（找出已有设计在新目标下**错在哪**），再列新增特性。
> 审查原则：能靠库解决的绝不进语言；进语言的必须是因为「库做不到」或「库做会失去关键性质」。

---

## 1. 三个必须先做的裁决

扩展目标后，原设计有三处从「合理取舍」变成「错误」，必须先改，否则后面加多少特性都是歪的。

| # | 原设计 | 问题 | 新裁决 |
|---|---|---|---|
| 1 | ARC 线程本地，跨线程须 `send` | **协程会在 OS 线程间迁移，线程本地的对象必然被并发访问 → 数据竞争** | 所有权单位从「线程」改为「并发域」，域整体迁移 |
| 2 | 运行时 < 300 KB | 六领域需要 GUI/编解码/字体/TLS/压缩/时区/Unicode 数据，全部塞进运行时必然爆 | 改为「运行时 < 400 KB，标准库按 Profile 裁剪，最小二进制 ~200 KB」 |
| 3 | 单一异常通道，内核态 `--unwind=abort` 下 `try` 不可用 | 内核里驱动/文件系统代码需要错误处理，不能全靠 panic | 新增 `--unwind=sjlj` + 小对象异常栈分配，内核也能用异常 |

第 3 条展开一下，因为它推翻了 [06](06-异常与诊断.md) 的一个隐含前提：

```
原方案：表驱动展开（.eh_frame / .pdata）
  → 优点：不抛时零成本
  → 问题：需要生成 unwind 表，内核/嵌入式不想付这个体积，且需要运行时支持

新增第三档：--unwind=sjlj（setjmp/longjmp）
  → 每个 try 入口一次 setjmp（约 15 周期）
  → 不需要 unwind 表（体积省 1~3%）
  → 内核驱动、嵌入式可用

配套：异常对象 ≤ 64 字节时栈分配，不碰堆
  → 绝大多数异常（错误码 + 2~3 个字段）都在 64 字节内
  → 内核态 throw 不再需要分配器
```

三档并列：`--unwind=table`（默认，AOT）/ `--unwind=sjlj`（内核、嵌入式）/ `--unwind=abort`（中断处理、早期启动，禁止 `try`）。

## 2. 六领域硬约束矩阵

先量化各领域对语言提出的**硬要求**。凡是「硬要求」列的，说明不能靠库绕过。

| 约束 | 服务端 | 桌面 | 移动 | 操作系统 | AI | 数据分析 |
|---|---|---|---|---|---|---|
| 二进制体积敏感 | 低 | 中 | **高**（< 15 MB 理想） | **极高**（< 1 MB） | 中 | 低 |
| 内存占用敏感 | 高 | 中 | **高** | **极高** | **高**（GPU 显存） | 高 |
| 启动延迟敏感 | 中（冷启动 < 50 ms） | **高**（< 200 ms 可见） | 高 | 不适用 | 低 | 低 |
| 需要分配器 | 是 | 是 | 是 | **否**（早期启动） | 是 | 是 |
| 需要协程调度器 | **是**（万级连接） | 是 | 中 | **否** | 中 | 低 |
| 需要异常展开 | 是 | 是 | 是 | **否**（用 sjlj 或 abort） | 是 | 是 |
| 需要内联汇编 | 否 | 否 | 否 | **是**（端口 IO、MSR、cpuid） | 否 | 否 |
| 需要精确内存布局 | 低 | 中 | 中 | **极高**（MMIO、页表） | 中 | 中 |
| 需要 GPU | 否 | 可选 | 可选 | 否 | **是** | 可选 |
| 需要 GUI 事件循环 | 否 | **是** | **是** | 否 | 否 | 否 |
| 需要交互式探索 | 中 | 否 | 否 | 否 | 中 | **是** |
| 需要数值数组 | 低 | 低 | 低 | 否 | **是** | **是** |
| 需要编译期反射 | 高（序列化/路由） | 高（UI 状态） | 高 | 低 | 中 | 高（列名检查） |
| 需要第三方语言互操作 | 低 | 中（WebView） | **极高**（JNI/ObjC） | 低 | **高**（CUDA/ONNX） | 中（Arrow） |

**从矩阵能直接读出的结论：**

1. 操作系统的需求与其他五个**几乎完全相反**（不要分配器、不要调度器、不要展开表，但要内联汇编、要精确布局）。这意味着 OS 必须是**同一语言的受限子集**，不是同一套运行时。
2. 移动和桌面共享「GUI + 体积」需求，但移动的互操作要求高一个量级（不能绕过 JNI/ObjC）。
3. AI 和数据分析共享「数值 + 编译期反射」，但 AI 多一个 GPU。
4. 服务端对数值几乎无需求——这是最容易做的领域。

## 3. 发现的 10 个设计缺陷

按严重程度排序。每条给出「为什么错」与「怎么改」。

### 缺陷 1（致命）· ARC 线程本地与协程迁移冲突

**原设计**（[01](01-语言设计.md) §6.2 v0.3）：`@ref` 对象默认线程本地，跨线程须 `send()`，以此让引用计数非原子化。

**问题**：有栈协程的调度器带工作窃取，协程会在 OS 线程之间迁移。一个 Web 请求的处理协程在 `await db.query()` 处挂起，恢复时可能跑在另一个线程上。它捕获的所有对象此时被两个线程先后访问——**引用计数非原子就意味着数据竞争，计数可能丢失，对象提前释放**。

这是设计冲突，不是实现 bug：**非原子 ARC 的正确性前提是「同一时刻只有一个线程能访问该对象」，而协程迁移打破了这个前提。**

**修复**：把所有权单位从「OS 线程」改为「并发域（Domain）」。

```
Domain = 一组协程 + 一组对象，语义上单线程
  ├─ 任一时刻，一个 Domain 只在一个 OS 线程上运行
  ├─ Domain 可以在挂起点整体迁移到另一个线程（迁移是原子的：整域搬家）
  ├─ Domain 内的对象用非原子 ARC（安全，因为单线程访问）
  └─ 跨 Domain 共享 → 必须 @shared（原子计数）或显式转移（move）
```

```x
// 默认：同一并发域，非原子 ARC，零同步开销
let conn = Connection.new(socket)      // 属于当前 Domain
let req  = conn.readRequest()          // 同一 Domain

// 跨域共享：显式标注，编译器改用原子计数
@shared struct SessionStore { map: Map[String, Session] }

// 跨域转移：所有权搬家，原处不可再用
let work = move(payload)               // payload 的 Domain 归属转移
spawnOn(otherDomain) { process(work) }

// 数据并行：切片按 Domain 拆分，各自独占一块，无共享
par for chunk in data.chunks(8) {
    compute(chunk)                     // 每个 chunk 是独立 Domain 的独占数据
}
```

**为什么这样是对的**：整域迁移时，域内对象没有任何外部引用（否则就不叫独占），因此计数不需要原子；迁移本身是「一次指针切换 + 一次内存屏障」，成本与协程切换同量级。

**代价（必须承认）**：`par for` 的循环体不能捕获外部可变状态，只能通过返回值或独占输入工作。这是数据并行本来就应该有的限制（Rayon 也是这样），但对习惯 Go 共享内存的人需要适应。

**对 Web 服务端的影响**：典型架构是「一个连接一个 Domain」，连接的整个生命周期内状态都在域内，非原子 ARC 全程有效。这恰好是 Web 服务端最需要的形状。

### 缺陷 2（严重）· 运行时体积目标与六领域需求矛盾

**原设计**：运行时核心 < 300 KB。

**问题**：六个领域合起来需要的东西远超此数：

| 组件 | 体积（估） | 谁能裁掉 |
|---|---|---|
| 分配器 + ARC | 40 KB | 内核 |
| 协程调度器 | 30 KB | 内核、嵌入式 |
| 异常展开 + 回溯 + 诊断渲染 | 60 KB | 内核（用 sjlj）、嵌入式 |
| Unicode 表（大小写、宽度、分段、规范化） | 90 KB | 服务端可裁（若不用文本处理） |
| 时区数据库 | 200 KB+ | 大多数可裁 |
| 正则引擎 | 60 KB | 可裁 |
| 图像编解码（PNG/JPEG/WebP） | 300 KB+ | 可裁 |
| 字体渲染 + 文本整形 | 800 KB+ | 桌面/移动要，服务端裁 |
| TLS | 绑定系统（0）或自研（500 KB+） | 用系统 |
| 压缩（zlib/zstd） | 150 KB | 可裁 |
| GUI 工具箱（绑定原生） | 200 KB 胶水 | 桌面/移动要 |

**修复**：分三个可独立度量的体积目标。

| 目标 | 内容 | 目标值 |
|---|---|---|
| **最小可执行** | core + 分配器 + 启动（无 std，无调度器，无展开） | **< 120 KB** |
| **标准运行时** | 上述 + 调度器 + 展开 + 诊断 + 字符串/格式化 | **< 400 KB** |
| **完整发行** | 上述 + 全套 std 静态链接 | 不设上限，靠 `--gc-sections` + LTO 收敛 |

配套机制：

- 所有 std 模块**按符号粒度链接**（`-ffunction-sections -fdata-sections` + `--gc-sections` 等价），没用到的代码不进二进制。
- 大体积数据（Unicode、时区）拆成独立可选模块 `std.unicode.data` / `std.time.tzdata`，用 `@embedFile` 按需打包。
- `x build --report=size` 输出每个符号的体积归因（自研，类似 Bloaty）。

### 缺陷 3（严重）· 移动平台不在目标列表，且缺互操作基础设施

**原设计**目标三元组只有 x86-64 与 aarch64 的桌面/服务端。

**问题**：移动端不是「加个 target」就能做。真正的障碍是**必须与 Kotlin/Swift 共存**：

- Android：X 只能作为 `.so` 被 JNI 调用，Activity/Service 生命周期在 Java 侧。纯 X 无法写完整 App。
- iOS：X 只能作为静态库被 Swift/ObjC 调用，`dlopen` 被禁，JIT 被禁（意味着**必须 AOT，且不能有运行时代码生成**）。

**修复**：明确「移动端 = X 作为核心库嵌入原生壳」，并补上互操作基础设施。

```
Android 结构：
  app (Kotlin) ── JNI ──→ libxcore.so (X 编写)
    ├─ UI：Jetpack Compose（Kotlin）
    ├─ 生命周期：Activity/Service（Kotlin）
    └─ 业务/算法/数据层：X

iOS 结构：
  App (Swift) ── ObjC runtime ──→ libxcore.a (X 编写)
    ├─ UI：SwiftUI
    └─ 业务/算法/数据层：X
```

需要的语言设施：

| 设施 | 用途 |
|---|---|
| `@jni` 注解 + 绑定生成 | `x bind android` 从 Java 类生成 X 侧声明与 JNI 胶水 |
| `@objc` 注解 + 方法名映射 | 让 X 的函数可被 ObjC runtime 调用（`objc_msgSend` 选择器） |
| `@export` 导出符号控制 | iOS 静态库只导出必要符号，避免符号冲突 |
| `--target=aarch64-linux-android21` / `aarch64-apple-ios14` | 交叉编译 |
| 版本脚本 / 导出列表 | 控制 `.so` / `.a` 的可见符号 |
| `--opt=size` 与 `--unwind=sjlj` | 体积与展开机制（见 §1 裁决 3） |

**不说假话**：移动端完整支持（含 UI）需要 X 自己实现声明式 UI 并绑定原生控件，这是一年以上的独立项目。**合理的落地顺序是：先做「X 作为计算核心嵌入」，不做 UI。**

### 缺陷 4（严重）· 禁止内联汇编与操作系统目标直接冲突

**原设计**（[01](01-语言设计.md) §10）：只有 extern 声明与 syscall 直通，没有内联汇编。

**问题**：写 OS 必须有内联汇编。无法回避的具体场景：

| 场景 | 需要的指令 |
|---|---|
| 端口 IO（串口、PS/2、PCI 配置空间） | `in` / `out` |
| MSR 读写（syscall 入口、EFER、APIC） | `rdmsr` / `wrmsr` |
| CPU 特性探测 | `cpuid` |
| 页表基址 | `mov cr3` |
| 中断开关 | `sti` / `cli` |
| TLB 刷新 | `invlpg` |
| 内存屏障（部分场景） | `mfence` / `lfence` |
| 原子操作（细粒度控制） | `lock cmpxchg` 带指定内存序 |
| 上下文切换 | 寄存器批量保存/恢复 |

**修复**：加入 `asm` 表达式，仅 `unsafe` 内可用，约束语法对齐 Rust/GCC 的成熟设计。

```x
unsafe {
    // 基础形式：读 TSC
    let tsc = asm!("rdtsc", out("eax") lo, out("edx") hi);

    // 带输入输出与副作用标记
    asm!(
        "out dx, al",
        in("dx") port,
        in("al") value,
        options(nostack, preserves_flags),
    );

    // 读写 MSR
    unsafe fn rdmsr(msr: UInt32) -> UInt64 {
        asm!("rdmsr", in("ecx") msr, out("eax") lo, out("edx") hi);
        (hi as UInt64) << 32 | lo as UInt64
    }
}
```

约束集（必须支持的最小集合）：

| 约束 | 含义 |
|---|---|
| `in(reg)` / `out(reg)` | 通用寄存器输入/输出 |
| `in("eax")` 等 | 指定寄存器 |
| `inout(reg)` | 读写同一寄存器 |
| `in("dx")` | 指定寄存器（端口 IO） |
| `const` | 编译期立即数 |
| `mem` | 内存副作用（阻止重排） |
| `options(nostack)` | 声明不改栈（允许优化） |
| `options(pure)` | 纯函数（无副作用，可消除） |
| `options(nomem)` | 不访内存 |
| `clobber_abi("C")` | 声明破坏整套 C ABI 寄存器 |

**风险控制**：`asm!` 是唯一能绕过所有安全检查的设施，因此：

- 只能在 `unsafe` 内使用（无例外）。
- 语义由用户保证，编译器不做正确性检查——**在文档中明确「`asm!` 的错误由写它的人承担」**。
- 提供 `asm!` 的单元测试范式：用已知输入输出对验证（如 `cpuid` 的已知值）。

### 缺陷 5（严重）· 缺精确布局控制，无法描述硬件结构

**原设计**：只有 `@repr(C)` 与 `@packed`。

**问题**：写 OS/驱动需要描述硬件寄存器块，这些结构有特定的内存布局要求，仅靠 `@repr(C)` 无法表达：

- **联合体（union）**：同一个偏移有多个解释方式（如 PCI 配置空间、页表项）。
- **位域（bitfield）**：一个字节里的多个标志位（如描述符表项）。
- **固定偏移**：MMIO 寄存器块中间有大量保留区。
- **段归属**：代码/数据需要放进特定段（`.text.boot`、`.bss.stack`）。

**修复**：加入以下布局设施。

```x
// 联合体：同一块内存的多种解释
@repr(C)
union PageTableEntry {
    raw: UInt64,
    fields: struct {
        present:   bool,   // bit 0
        writable:  bool,   // bit 1
        user:      bool,   // bit 2
        addr:      UInt40, // bit 12..51
    },
}

// 位域：精确控制每个字段的位宽与位置
@repr(C)
struct Descriptor {
    limit_low:  UInt16,       // bit 0..15
    base_low:   UInt16,       // bit 16..31
    base_mid:   UInt8,        // bit 32..39
    @bits(4) access:  UInt8,  // bit 40..43
    @bits(4) flags:   UInt8,  // bit 44..47
}

// 固定偏移（MMIO 寄存器块，中间有保留区）
@repr(C)
struct UartRegs {
    data: UInt8,
    @offset(1) ier: UInt8,
    @offset(2) iir: UInt8,
    @offset(5) lcr: UInt8,
}

// 段归属（链接脚本配合）
@section(".text.boot") fn earlyEntry() { ... }
@section(".bss.stack", zeroed) static bootStack: [UInt8; 16384];

// 对齐控制
@align(4096) struct Page { ... }        // 页对齐（页表要求）
```

同时补齐原子操作的内存序：

```x
let counter: Atomic[Int] = 0
counter.store(1, .release)              // 显式内存序
let v = counter.load(.acquire)
counter.compareExchange(0, 1, .acqRel)
counter.fetchAdd(1, .relaxed)
// 枚举：Relaxed / Acquire / Release / AcqRel / SeqCst
// 默认：SeqCst（最保守），性能敏感处显式放松
```

**为什么内存序必须进语言**：它不是「库的实现细节」，而是影响正确性的程序员可见契约。Rust/C++/Java 都把它做成语言/标准库的一等概念，X 不能例外。

### 缺陷 6（中）· 缺 const 泛型，shape 与 buffer 尺寸无处表达

**原设计**：泛型只有类型参数 `[T]`。

**问题**：

- `NDArray[T, S: Shape]` 中的 `Shape` 如果是类型，`NDArray[Float, Shape2[3,4]]` 的 `3,4` 无处安放。
- `[T; N]` 的 `N` 是值不是类型。
- 固定大小缓冲区、SIMD 宽度、矩阵分块参数都需要值级泛型。

**修复**：加入 `const` 泛型参数，用 `comptime` 求值，单态化时实例化。

```x
// 值级泛型
struct Vec[T, const N: Int] { data: [T; N] }
fn dot[const N: Int](a: Vec[Float, N], b: Vec[Float, N]) -> Float {
    var s = 0.0
    for i in 0..N { s += a.data[i] * b.data[i] }    // N 是编译期常量，循环可完全展开
    s
}

// 形状作为 const 泛型
struct NDArray[T, const D0: Int, const D1: Int = 1> { ... }
type Mat3 = NDArray[Float, 3, 3];

// 编译期断言（形状匹配检查）
comptime assert(D0 == D1, "矩阵必须为方阵才能求逆");

// SIMD 宽度
fn reduce[const W: Int](xs: [Float; W]) -> Float { ... }
```

**双重收益**：不只是表达力，还是性能。`for i in 0..N` 在 `N` 为编译期常量时可完全展开并向量化——这是数值代码能达到手写循环性能的前提。

### 缺陷 7（中）· 强类型无数值提升，数据分析摩擦过大

**原设计**（[01](01-语言设计.md) §1.2）：禁止隐式类型转换，`Int + Float` 报错。

**问题**：这条规则对系统编程是对的，但数据分析代码天然充满混合类型：CSV 读进来全是字符串，列可能全空（`Float?`），整数列与浮点列要一起算。如果每处都手写 `toFloat()`，代码会淹没在转换里。

**修复**：不放宽隐式转换（那会引入真正的 bug），改为**用类型系统把转换收敛到数据加载边界**。

```x
// 列式 schema：类型在读取时确定，之后全强类型
@derive(FromCsv)
struct SaleRow {
    @col("date")  date:  Date,
    @col("sku")   sku:   String,
    @col("qty")   qty:   Int,          // 读入时转换，失败则该行报错并给出行号
    @col("price") price: Float,
}

let df = DataFrame.load[SaleRow]("sales.csv")     // 一次性转换，之后是强类型列
let revenue = df.qty * df.price                    // Int * Float 在 DataFrame 层允许（列级广播）
                                                   // 但不是语言层的隐式转换，是 DataFrame 的列算子
```

关键区分：**语言层不允许隐式转换，但 `DataFrame` 的列算子可以定义自己的提升规则**（就像 NumPy 的 dtype 提升）。这不是开后门，因为它是显式的库语义，且只在 DataFrame 语境生效。

配合：编译期列名检查。

```x
// 列名在编译期校验，拼错立刻报错（而不是运行时 "column not found"）
let x = df["qty"]          // 编译期检查 SaleRow 有 qty 字段
let y = df["quatity"]      // 编译错误：SaleRow 没有字段 quatity，是否想用 qty？
```

这条是 X 相对 pandas 的实质优势：**数据分析里最常见的错误是列名拼错和类型意外**，两者都能在编译期消灭。

### 缺陷 8（中）· 无 REPL 与数据分析工作流冲突

**原设计**（[02](02-编译与运行时.md) §2.3）：不提供 REPL。

**问题**：数据分析本质上是**探索性**的——看一列分布、试一个假设、改一个参数。这需要「输入即见结果」。没有 REPL，数据分析的体验会断裂。

但 REPL 的技术障碍是真的（泛型单态化无法增量定义）。所以不恢复 REPL，而是**用编译模型模拟探索流程**：

```x
// analysis.xnb —— 带 cell 标记的普通 .xle 文件
//# cell 1
let df = DataFrame.load[SaleRow]("sales.csv")
println(df.describe())

//# cell 2
let byMonth = df.groupBy(df.date.month()).agg(revenue: sum(df.qty * df.price))
println(byMonth)

//# cell 3
plot(byMonth.revenue)     // 直接在浏览器打开
```

```bash
x notebook analysis.xnb
```

工作方式：

```
1. 解析 .xnb，按 cell 切成 N 个编译单元
2. 每个 cell 是一个模块，自动 import 之前所有 cell 的导出
   （cell 3 能看到 df 和 byMonth，因为它们被导出）
3. 用户点「运行 cell 3」→ 只编译 cell 1..3 的增量链（缓存命中则 < 50 ms）
4. 输出以 HTML 渲染到浏览器（表格、图表、错误诊断都可点击）
5. 每次运行形成一个「快照」，可以回退到任意快照重跑
```

为什么这在语义上是干净的：**cell 只是同一个模块里的顶层语句分段**，编译时全部合成为一个程序（与 Jupyter 的「每 cell 独立全局状态」不同）。因此不存在「上一格定义的类型下一格看不到」的问题——它们本来就是同一个编译单元。

代价：cell 之间有依赖时，改 cell 1 会导致 cell 2..N 重编译（增量，通常 < 200 ms）。Jupyter 允许乱序执行、状态偷偷保留，X 不允许——**这是刻意的**，因为乱序执行产生的状态不一致是 notebook 最大的可信度问题。

### 缺陷 9（中）· GUI 事件循环与我方协程调度器争夺主线程

**原设计**：协程调度器用 M 个 OS 线程（M = 核数），工作窃取。

**问题**：桌面/移动的 GUI 框架都要求「UI 只能从主线程访问」，且主线程必须跑它自己的事件循环（Win32 `GetMessage`、Cocoa `NSApplication.run`、Android `Looper`）。而 X 的调度器想独占所有线程。

**修复**：引入「主线程锚定」与事件循环整合协议。

```x
import std.ui

fn main() {
    // 调度器预留线程 0 给 UI，其余线程跑协程
    runtime.reserveMainThreadForUI()

    let app = ui.App.new("我的应用")
    app.window("主窗口", size: (800, 600), |w| {
        // 这里的代码运行在 UI 线程
        let count = @State(0)
        w.button("点我 {count}", onClick: || {
            count += 1              // @State 变化自动触发重绘
        })
    })
    app.run()                       // 驱动平台事件循环 + 协程调度器
}
```

整合规则：

| 规则 | 说明 |
|---|---|
| UI 线程只跑 UI 协程 | 其他协程在 worker 线程，`spawnOnUI` 才能投递到 UI 线程 |
| 后台任务回 UI 用 `await` | `let data = await fetchAsync(); updateUI(data)` 自动切回 UI 线程（类似 Kotlin 的 `Dispatchers.Main`） |
| 阻塞调用禁止在 UI 线程 | lint 检查：UI 上下文里调用 `fs.read` 等阻塞 API 报错 |
| 平台事件循环的每一轮 | 顺便 poll 一次调度器队列（避免额外线程唤醒） |

```x
// 后台计算，回主线程更新
async fn loadData(button: Button) {
    button.setEnabled(false)
    let rows = await db.query("SELECT ...")     // 自动在 worker 线程
    table.setRows(rows)                         // 自动切回 UI 线程（因为 table 是 UI 对象）
    button.setEnabled(true)
}
```

**为什么必须进语言而不仅是库**：`@State` 需要编译期生成观察代码（否则每处手写订阅），线程切换需要编译器知道哪些对象属于 UI 域。这两件事都必须编译器参与。

### 缺陷 10（中）· 缺 GPU 与自动微分，AI 只能做推理不能做训练

**原设计**：只有 `NDArray` + `std.linalg` + BLAS 绑定。

**问题**：AI 开发的核心循环是「前向 → 求梯度 → 反向更新」。缺自动微分就没有训练；缺 GPU 就只能做小模型。

**修复**：分两步，且明确边界。

**第一步（P3~P4）：自动微分进语言。**

```x
// 语言提供 @differentiable，comptime 生成反向传播代码
@differentiable
fn loss(w: Tensor, x: Tensor, y: Tensor) -> Float {
    let pred = x @ w
    ((pred - y) ** 2).mean()
}

// 用法：grad 自动生成，无运行时 tape 开销
let g = grad(loss)(w, x, y)         // 编译期生成的反向函数
w -= lr * g

// 需要动态图时用 tape 模式（调试友好，慢 2~3 倍）
tape {
    let pred = x @ w
    ...
}
```

相比 PyTorch 的 tape 方案，`@differentiable` 的优势：

| 维度 | PyTorch（tape） | X（`@differentiable`） |
|---|---|---|
| 每算子开销 | 记录 tape 节点（~100 ns） | 0（编译期生成） |
| 图优化 | 有限（TorchScript 才能优化） | 完全（编译器可见整体图） |
| 调试 | 好（可逐步） | 中（生成代码可读性差） |
| 动态控制流 | 天然支持 | 需要 `@differentiable` 支持控制流的规则 |

**[裁决]** 提供两种：`@differentiable` 用于生产（快），`tape` 用于研究（灵活）。默认推荐前者。

**第二步（P5+）：GPU。**

诚实的路线：

| 阶段 | 做法 | 说明 |
|---|---|---|
| P3 | 绑定 cuBLAS / cuDNN / ROCm / Metal Performance Shaders | 只做 host 侧调用，无 device 代码 |
| P4 | `@kernel` 函数子集编译到 PTX / SPIR-V | 需要限制子集（无递归、无动态分配、固定线程块大小） |
| P5+ | 自研张量编译器 | 只有在前面都稳定后才考虑 |

`@kernel` 的样子：

```x
@kernel(block: (256, 1, 1), grid: dynamic)
fn saxpy[const N: Int](a: Float, x: [Float; N], y: mut [Float; N]) {
    let i = threadIdx.x + blockIdx.x * blockDim.x
    if i < N { y[i] = a * x[i] + y[i] }
}
```

**但这条路线要算清楚代价**：一个可用的 GPU 后端（PTX 生成 + 内存管理 + 异步流 + kernel 调度）是 1.5~2 人年。**不建议在 1.0 之前做。**

## 4. 新架构概念：Profile

六领域需求冲突的根源是「一个运行时想服务所有场景」。解法不是做六个语言，而是**一份核心 + 七个 Profile**，Profile 决定链接哪些运行时模块、允许哪些语言特性、默认什么优化档位。

| Profile | 目标 | 不链接 | 禁用特性 | 默认优化 |
|---|---|---|---|---|
| `server` | 长驻服务 | — | — | `-O2` |
| `desktop` | 桌面 GUI | — | — | `-O2` |
| `mobile` | 移动嵌入式 | 部分 std | 运行时代码生成、`dlopen` | `-Os` |
| `kernel` | 内核/驱动 | 分配器（可配）、调度器 | 协程、`dlopen`；`try` 需 `--unwind=sjlj` | `-O2` |
| `embedded` | MCU | 分配器、调度器、异常表 | 协程、动态分配；默认 `--unwind=abort`，需要错误处理时改 `--unwind=sjlj` | `-Os` |
| `wasm` | 浏览器 | 系统调用、线程 | 原生线程、`dlopen` | `-O3` |
| `core` | 无 OS 环境 | 全部 | 除了纯计算能力全部禁用 | `-O2` |

用法：

```toml
# x.toml
[package]
profile = "server"
```

```bash
x build --profile=kernel --unwind=sjlj
x build --profile=mobile --target=aarch64-linux-android21
```

Profile 的三层作用：

| 层 | 作用 |
|---|---|
| 链接层 | 决定 `libruntime` 的哪些模块被链接（体积来源） |
| 语言层 | 决定哪些语法可用（`kernel` 下 `spawn` 报错「当前 Profile 不支持协程」） |
| 诊断层 | 错误信息带 Profile 上下文（「`kernel` Profile 下不允许堆分配，请用 `arena` 或静态缓冲」） |

**这套机制的价值**：它把「六个目标互相冲突」变成「六个配置各自独立」。核心语言与字节码不变，编译器与运行时按 Profile 装配。**这也是 Rust 的 `no_std` + target feature 的经验：一个语言能同时做内核与 Web，靠的不是妥协，是分层裁剪。**

## 6. 各领域的诚实评估

这一节回答「能做多少」。**不夸大。**

### 6.1 网站服务端

**可行性：高。这是最容易做好的领域。**

| 需求 | X 的支撑 | 状态 |
|---|---|---|
| 万级并发连接 | M:N 协程 + IOCP/io_uring | 设计已有 |
| 请求上下文 | task-local 存储（新增 #9） | 待实现 |
| 可观测性 | span 追踪（新增 #10） | 待实现 |
| 数据库 | driver 抽象 + 纯 X 驱动 | 设计已有 |
| 序列化 | comptime 生成（新增 #11） | 待实现 |
| 热重载 | 模块级热替换（#18） | P1 |
| 内存占用 | 非原子 ARC + Domain（#1） | 修缺陷后有效 |
| 冷启动 | < 50 ms（AOT 静态二进制） | 有优势 |

**X 的差异化**：单文件二进制 + 毫秒级冷启动 + 无 GC 停顿。这三条正好是 Serverless / 边缘计算场景的痛点。**这是最值得主打的方向。**

### 6.2 桌面软件

**可行性：中。依赖一个关键决策——绑定原生控件还是自绘。**

| 路线 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| 绑定原生控件（Win32/Cocoa/GTK） | 原生观感、无障碍免费、体积小 | 三套平台代码、控件行为不一致 | **推荐** |
| 自绘（Skia 类） | 完全一致的外观、单套代码 | 需要自研文本整形/输入法/无障碍，1 人年以上 | 不推荐 |
| 嵌入 WebView | 生态成熟、UI 快 | 内存大（100 MB+）、非原生 | 作为补充（复杂界面用） |

需要补的：`@State`（#14）、事件循环整合（#15）、热重载（#18，桌面开发体验的关键）、三平台绑定。

**主要的诚实结论**：桌面 GUI 是最容易被低估的方向。它的难点不在语言，而在**文本渲染（字体整形、双向文本、emoji）+ 输入法 + 无障碍 + 高 DPI** 这四件事，每一件都是数月工作量。绑定原生控件能绕开这些，但需要维护三套。

### 6.3 移动 app

**可行性：低（作为完整 App 方案），中（作为计算内核）。**

| 能力 | 可行性 |
|---|---|
| X 写业务/算法/数据层，Kotlin/Swift 写 UI | **高**（这是现实路径） |
| X 写完整 Android App（不用 Kotlin） | 低（需要 JNI 生命周期桥 + 自研 UI） |
| X 写完整 iOS App | 极低（需要 ObjC runtime 深度互操作 + 自研 UI，且禁止 JIT） |
| X 作为推理引擎嵌入 App | **高**（AOT 静态库，这是好场景） |

**结论**：移动端定位为「核心库」，不做「App 开发方案」。这不是能力不足，是 ROI 判断——移动 UI 生态的护城河是十年积累，不值得攻。

### 6.4 操作系统

**可行性：中高。这是 X 最"纯"的场景，因为只需语言子集。**

| 需求 | 支撑 | 状态 |
|---|---|---|
| 无 libc | `--freestanding` + L0 层 | 设计已有 |
| 无分配器启动阶段 | `--no-alloc` + 静态缓冲 | 待补 |
| 内联汇编 | `asm!`（#2） | 待实现 |
| 硬件结构描述 | `union`/`@bits`/`@offset`（#3） | 待实现 |
| 内存序 | 原子内存序（#4） | 待实现 |
| 链接脚本控制 | `@section` + `--emit=obj` | 待实现 |
| 无展开表 | `--unwind=sjlj`（#7） | 待实现 |
| 中断上下文 | `@interrupt` 标记 + 禁用 try/alloc | 待实现 |
| 无红区、无 TLS | 编译选项 | 待实现 |

需要新增一个概念：**中断上下文约束**。

```x
@interrupt
fn timerHandler(frame: *InterruptFrame) {
    // 此函数内禁止：分配、协程切换、可能展开的 try、可能睡眠的调用
    // 编译器强制检查，违反即编译错误
    ticks += 1
    scheduleNext()      // 只能是 explicit 的、非阻塞的调度原语
}
```

`@interrupt` 的语义等价于「一个禁止几乎所有便利设施的沙箱」。编译器检查比运行时崩溃好得多——中断里分配导致的死锁是最难查的内核 bug。

### 6.5 AI 开发

**可行性：推理高，训练中，训练框架低。**

必须先明确一件事：**AI 训练框架的护城河不在语言，在生态。** PyTorch 有 3 万个模型实现、无数教程、整个 HuggingFace。X 不可能在 5 年内追上。

所以定位应该是：

| 场景 | 可行性 | 理由 |
|---|---|---|
| **推理部署**（训练在 Python，部署在 X） | **很高** | 单文件二进制、无 Python 运行时、毫秒启动、低内存。这是 X 的杀手场景 |
| 训练（自己写模型） | 中 | 需要 autograd + GPU + 优化器库 + 数据管道，能做但不占优 |
| 训练框架（替代 PyTorch） | 低 | 生态壁垒，不做 |
| 科学计算（非深度学习） | 高 | 这是数值语言的老本行 |

**推理场景的具体形态**：

```x
// 加载 ONNX 模型，编译期确定输入输出形状
let model = Model.load("resnet50.onnx")    // 启动时加载并校验
let input = Tensor[Float, 1, 3, 224, 224].fromImage("cat.jpg")
let output = model.run(input)              // AOT 编译的推理循环

// 打包成单文件服务
// x build --release --profile=server → 一个 5 MB 的二进制，启动 3 ms
```

这个形态的价值：**Python 推理服务的冷启动是秒级、镜像 2 GB；X 是毫秒级、二进制 5 MB。** 在 Serverless / 边缘推理场景这是数量级差异。

### 6.6 数据分析

**可行性：高，但需要专门的数据结构。**

| 需求 | 支撑 | 状态 |
|---|---|---|
| 列式数据 | `DataFrame`（新库） | 待实现 |
| 编译期列检查 | comptime（#12） | 待实现 |
| 缺失值 | `Float?` 列 + 三值逻辑 | 待设计 |
| 探索工作流 | Notebook（#17） | P1 |
| Arrow/Parquet | 零拷贝互操作（#28） | P1 |
| 绘图 | SVG 生成 + 浏览器渲染 | 待实现 |
| SQL | 查询引擎（库） | P2 |

**最大风险**：数据分析的生态惯性极强（pandas → polars 花了五年才有起色）。X 的差异化只能是「编译期检查 + 单二进制分发 + 与生产环境同语言」，不能是「更快」——polars 已经很快了。

**一个实际的机会**：数据分析最常见的痛点是「分析代码在 notebook 里跑得通，上生产就崩」。X 的编译期类型检查 + 同一份代码可 AOT 编译，正好解决这个断层。**这是 pandas 做不到的。**

## 7. 定位裁决：两个主场，四个可用

六个领域全做到最好是不可能的，任何语言都没做到。必须明确主次，否则资源分散到全部做不到。

| 领域 | 定位 | 投入 | 判断依据 |
|---|---|---|---|
| **数据分析 / 科学计算** | **主场** | 最高 | 数学一等公民 + 编译期列检查 + 同语言上生产，三点都是真差异 |
| **网站服务端** | **主场** | 最高 | 单二进制 + 毫秒冷启动 + 无 GC 停顿，直击 Serverless 痛点 |
| 操作系统 | 可用 | 中 | 语言子集够用，且与 x-os 相互成就（自用场景，不需生态） |
| AI 推理 | 可用 | 中 | 部署场景有数量级优势，训练不争 |
| 桌面 | 可用 | 中 | 绑定原生即可，不做自绘 |
| 移动 | 边缘 | 低 | 只做核心库嵌入，不做 App 方案 |

**这个定位的直接后果**（决定特性优先级）：

1. const 泛型、自动微分、DataFrame、Notebook → 优先级最高（数据分析 + AI）
2. Domain、task-local、span 追踪、序列化、热替换 → 优先级最高（服务端）
3. `asm!`、union、内存序、Profile → 必做但可以晚（OS 不是首发场景）
4. GUI、JNI/ObjC → 可以最晚（桌面/移动是 1.x 的功能）
