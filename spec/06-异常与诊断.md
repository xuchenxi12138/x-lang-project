# 06 · 异常与诊断

> 本文定义异常模型、栈回溯格式、可点击链接机制、通俗语言诊断。
> 核心目标：**任何一次失败，用户都能在一秒内知道「哪一行错了、为什么错、怎么改」，且点一下就跳到那一行。**

---

## 1. 决策摘要

| 项 | 决策 | 否决的替代 |
|---|---|---|
| 错误通道 | **单一通道：异常**。移除 `Result` + `?` | 双轨（异常 + Result）——两套机制让用户每次都要选，必然选错 |
| 异常分类 | `Exception`（可捕获）与 `Error`（应终止）两层，同 Java | 单一 Throwable——把 OOM 和文件不存在混在一起 |
| 受检性 | **异常集合由编译器推断，`throws` 可选**。写了就强制检查 | Java 强制受检——签名噪音大；全不受检——调用方不知情 |
| 展开机制 | **三档**：默认表驱动（DWARF CFI / PE xdata / Mach-O compact unwind）；`--unwind=sjlj` 供内核与嵌入式；`--unwind=abort` 供中断上下文 | 只有单一表驱动——内核与嵌入式付不起 unwind 表体积 |
| 异常对象 | ≤ 64 字节**栈分配**，> 64 字节堆分配 | 全部堆分配——内核早期启动时堆还不存在 |
| 抛出成本 | 不抛时 **0**（`table` 档）；抛出时 5~15 µs（含栈回溯） | Java 的 `fillInStackTrace` 每次 10~50 µs |
| 可点击 | 终端 OSC 8 超链接 + `file:line:col` + `x://` 协议，三套并行 | 只输出文本——终端里点不了 |
| 错误解释 | 结构化四段（发生了什么/为什么/怎么改/去哪里看） | 单行字符串——「Invalid input」这类消息毫无价值 |
| 局部变量 | **debug 构建自动快照**（Java 没有的能力） | 只给栈——用户还得自己加日志复现 |

## 2. 类型模型

### 2.1 两个根

```x
// 可捕获。所有业务错误、IO 错误、解析错误都是它的子类型
trait Exception {
    fn message(self) -> String              // 必填：一句话说清发生了什么
    fn help(self) -> String?                // 必填（可为 null，但 lint 建议填）：通俗解释 + 怎么改
    fn cause(self) -> Exception?            // 选填：链式原因
    fn location(self) -> Location?          // 由运行时填充，用户不用实现
}

// 不应捕获。捕获了也无法继续正确执行
trait Error: Exception {
    fn isFatal(self) -> Bool                // 默认 true
}
```

`Error` 的子类型固定为语言内置，用户不能新增：

| 类型 | 触发 |
|---|---|
| `PanicError` | `panic(msg)`、`assert()` 失败、`unwrap` 于 `null` |
| `OutOfMemoryError` | 分配失败 |
| `StackOverflowError` | 协程栈超限 |
| `OverflowError` | 算术溢出（受 `--overflow=wrap` 影响） |
| `IndexError` | 越界（受 `--no-bounds-check` 影响） |
| `DivideByZeroError` | 整数除零 |
| `UnreachableError` | `match` 的 `_` 不穷尽时的兜底（正常不该发生） |

`Exception` 的子类型由用户与标准库定义。

### 2.2 标准异常层级

```
Exception
├── IoError
│   ├── NotFound           文件/路径不存在
│   ├── PermissionDenied   权限不足
│   ├── AlreadyExists      已存在
│   └── DeviceError        设备层错误
├── NetworkError
│   ├── ConnectError       连接失败
│   ├── TimeoutError       超时
│   ├── TlsError           证书/握手
│   └── ProtocolError      协议解析失败
├── ParseError
│   ├── JsonError
│   ├── TomlError
│   └── SyntaxError
├── ValueError
│   ├── NumberFormatError  字符串转数字失败
│   ├── RangeError         取值越界（非索引）
│   └── ShapeError         NDArray 形状不匹配
├── KeyError
├── TypeError
├── DbError
└── NotImplementedError
```

命名规则：全部 `XxxError` 结尾（与内置 `Error` 区分开，读起来不会混淆）。层级深度**不超过 3 层**，超过说明分类失败。

## 3. 语法

### 3.1 定义异常

```x
// 最简：只需要一个 message
struct ConfigError implements Exception {
    path: String,
    line: Int,

    fn message(self) -> String {
        "{self.path} 第 {self.line} 行无法解析"
    }

    fn help(self) -> String? {
        "配置文件里常见的问题是字符串漏了引号，或者键值之间少了等号。"
    }
}
```

`message` 与 `help` 都是必须实现的方法（`help` 可为 null 但显式写 null 是一种态度；lint 对 `help() -> null` 报 style 警告）。

### 3.2 抛出

```x
throw ConfigError { path: p, line: 12 }

// 带原因链
catch e: ParseError {
    throw ConfigError { path: p, line: e.line, cause: e }
}

// 重抛（保留原始栈）
catch e {
    log(e)
    rethrow
}

// 包装并改文案（新建栈，原异常进 cause）
throw Wrap(e, "加载配置失败")
```

**[裁决]** `throw` 只接受 `Exception` 子类型的实例，不接受字符串。理由：`throw "出错了"` 是 Java/Python 的常见劣习，它让调用方无法按类型捕获，也无法附加上下文。

### 3.3 捕获

```x
try {
    let cfg = load("app.toml")
    run(cfg)
}
catch e: ConfigError {
    // 精确类型
    eprintln("配置有问题：{e.message()}")
    eprintln("建议：{e.help() ?? "查看文档"}")   // 注：?? 用于 Option，见下
    exit(2)
}
catch e: IoError | NetworkError {
    // 联合类型
    retryLater(e)
}
catch e {
    // 兜底
    eprintln("未预期的错误：{e}")
    rethrow
}
finally {
    // 无论是否抛出都执行；即使 catch 里再次 throw
    cleanup()
}
```

`finally` 的保证：**即使 `catch` 块内 `rethrow`，`finally` 也执行**。这与 Java 一致。`finally` 内 `throw` 会覆盖原异常（原异常进 `cause`），并在 debug 构建里给出警告。

### 3.4 函数签名

```x
// 不写：编译器推断出异常集合，调用方仍受约束（类型系统知道它可能抛什么）
fn load(p: String) -> Config {
    ...
}

// 写：锁定集合，多抛一个就编译报错。适合公开 API 与跨模块边界
fn load(p: String) -> Config throws ConfigError, IoError {
    ...
}

// 声明不抛：编译器验证。违反了就报错（不是警告）
fn pureCompute(x: Float) -> Float throws nothing {
    ...
}
```

**[裁决]** 默认推断、可选锁定。理由：

| 方案 | 问题 |
|---|---|
| Java 强制受检 | 每个签名都要写 `throws`，改一个底层异常要改 30 个签名，实际项目中全部被 `throws Exception` 绕过 |
| 完全不受检 | 调用方不知道 `open()` 会抛什么，只能盲目 catch 全部 |
| **推断 + 可选锁定** | 编译器全知（能给出精确的异常集合），用户不用写（零注解），需要时能锁死 |

推断规则：函数体的异常集合 = 直接 `throw` 的类型 ∪ 所有被调函数声明的异常集合，再减去被 `try/catch` 完全覆盖的类型。集合在 `x doc` 与 IDE hover 中显示，因此**不写也有文档**。

### 3.5 `Option` 与 `??`

移除 `Result` 后，`Option[T]`（`T?`）保留，用于表达「可能没有值」而非「可能出错」：

```x
let port = env.get("PORT")?.toInt() ?? 8080
let user = findUser(id) ?? throw NotFoundError { what: "用户 {id}" }
```

`??` 的右侧可以是表达式或 `throw`，这让「没有值就当错误抛」不用写四行：

```x
let cfg = readConfig(path) ?? throw ConfigError { path, line: 0 }
```

### 3.6 移除 `?` 传播运算符

`?` 曾用于 `Result` 传播。移除 `Result` 后 `?` 只保留一个含义：**可选链**（`a?.b`）。同名符号两种含义是设计灾难，因此彻底区分：`?.` 是可选链，`??` 是空值合并，`?` 单独出现非法。

## 4. 栈回溯输出格式

这是本文的核心。目标是「用户看一眼就知道怎么办」，不是「给编译器作者看的」。

### 4.1 完整格式

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 未捕获的 ConfigError
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

 位置   src/config.xle:42:18
 原因   app.toml 第 12 行无法解析：期望 "=" 但读到换行
 解释   解析器在读到键 "server.port" 后，期待紧跟一个 "=" 和值，
        但这一行直接结束了。最常见的原因是把键和值写在了两行里，
        或者键名末尾多了一个空格导致解析器没能识别到等号。
 建议   把第 12 行改成：server.port = 8080
 文档   x://doc/E1004

 当时的值
   path = "app.toml"
   line = 12
   text = "server.port"

 调用栈
   → loadConfig        src/config.xle:42:18      ← 抛出点
     Application.init   src/app.xle:118:9
     main               src/main.xle:7:1

 打开   x://open?file=src/config.xle&line=42&col=18
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

六个字段的职责必须分清，不能混：

| 字段 | 职责 | 谁提供 |
|---|---|---|
| 位置 | 精确到行与列 | 运行时（栈回溯） |
| 原因 | 一句话，含具体值，不含建议 | `message()` |
| 解释 | 补全上下文与因果，说明「为什么」 | `help()` 第一段 |
| 建议 | 可执行的改法，最好带代码 | `help()` 第二段 或 `@suggest` |
| 文档 | 消息 ID 链接，含完整说明与示例 | 诊断库 |
| 当时的值 | 抛出点作用域的局部变量快照 | 编译器生成的调试元数据 |

### 4.2 消息文案的硬性规范

诊断消息质量是语言体验的分水岭。以下规则由 lint 强制执行：

| 规则 | 反例 | 正例 |
|---|---|---|
| 必须含具体值，不能只说类型 | `类型不匹配` | `期望 浮点，得到 整数 2` |
| 使用第二人称或无人称，不用第一人称 | `我无法打开文件` | `无法打开文件` |
| 不用「非法」「无效」这类空词 | `无效的输入` | `第 12 行缺少 "="` |
| 一句话不超过 40 个汉字 | 长句堆砌 | 拆成原因 + 解释 |
| 不暴露内部术语 | `arena 分配失败 at offset 0x3f` | `内存不足，需要 512 MB，当前可用 120 MB` |
| 必须说清「哪个东西」 | `解析失败` | `app.toml 第 12 行解析失败` |
| 建议必须可执行 | `请检查输入` | `把第 12 行改成 server.port = 8080` |

**为什么会有人写出烂消息**：因为写消息时脑子里只有自己的代码。规范的做法是：编译器内置的 lint 规则 `diagnostic-quality` 会扫描所有 `message()` 的返回值，检查是否含参数插值、是否含禁用词。这不是形式主义——一条 `Invalid input` 平均让用户多花 15 分钟。

### 4.2.1 诊断的编码与对齐（实现约束）

诊断是**唯一必须同时处理中英文排版**的输出，因此有两条硬约束。它们都不会报错，只会让输出看起来「差一点」——恰恰是最容易长期留存的那类缺陷。

**一、标签必须按显示宽度对齐到同一内容列。**

| 标签 | 组成 | 显示列数 | 需补空格（到第 8 列） |
|---|---|---|---|
| ` 位置` | 1 空格 + 2 汉字（2×2） | 5 | 3 |
| `  error:` | 2 空格 + 5 ASCII + 冒号 | 8 | 0 |
| `  note:` | 2 空格 + 4 ASCII + 冒号 | 7 | 1 |
| `  help:` | 2 空格 + 4 ASCII + 冒号 | 7 | 1 |

四个标签的补空数互不相同，**靠人肉数空格必然错**。实现上统一成「先算已打印字符串的显示宽度，再补到固定列」（`diag_label()`），以后加新标签（`原因` / `解释` / `文档`）也不用重新数。

**二、位置列号按码点计，不按字节也不按显示宽度。**

`file:line:col` 里的 `col` 必须与编辑器光标列一致，否则「精确到列」是空话。中文一个字符 3 字节、显示宽 2 列——两个数字都不是 1。正确口径是**一个码点算 1 列**（详见 [01](01-语言设计.md) §2.1.1、[04](04-中文编程方案.md) §6.1.1）。

这条在实测中的一个具体表现：修之前 `令 年龄 = 姓名 + 不存在的` 报 `2:23`，修之后报 `2:13`；而第 13 列正是 VS Code 里 `不存在的` 的起始列。**23 是字节偏移，13 是用户看到的列。**

**三、输出编码与终端代码页是两件事。**

诊断文案经 `fprintf` 出来的一直是合法 UTF-8 字节。在 Windows 上看到「浣嶇疆」不是输出错了，而是控制台按 GBK(936) 解码了 UTF-8——「位置」的 6 个字节被当成 3 个 GBK 汉字来解释。修法在交界处：启动时切 `CP_UTF8`，退出时还原（细节见 [01](01-语言设计.md) §2.1.2）。

由此得出一条排错原则：**遇到乱码先看字节，再看终端**。用 `xxd` 确认 `e4 bd 8d` 是否真是「位」——如果是，问题一定在终端侧，改程序输出是白改。

### 4.3 多语言输出

`help()` 与 `message()` 是代码里的字符串，无法运行时切换语言。因此：

- **库作者的异常**：走诊断库的 message ID 机制（§6），支持 `--msg=zh/en/both`。
- **直接用字面量的异常**：只输出原文，不翻译。

两者可混用。标准库全部走 message ID，因此标准库异常必然支持中英双语。

## 5. 可点击机制

「点一下就跳过去」需要三条路径并行，因为用户分布在不同的环境里。**这是本文最重要的工程细节**。

### 5.1 机制一：终端超链接（OSC 8）

现代终端（Windows Terminal、VSCode 集成终端、iTerm2、WezTerm、Kitty、Alacritty）支持 OSC 8 转义序列把任意文本变成超链接：

```
ESC ] 8 ; params ; URI ESC \ 文本 ESC ] 8 ; ; ESC \
```

X 的运行时在检测到 `stdout` 是支持超链接的终端时，自动把 `src/config.xle:42:18` 渲染为指向 `x://open?file=src/config.xle&line=42&col=18` 的链接。

检测方式：

```x
fn supportsHyperlink() -> Bool {
    if env.get("NO_HYPERLINK") != null { return false }
    if env.get("TERM_PROGRAM") in ["vscode", "WezTerm", "iTerm.app", "Apple_Terminal"] { return true }
    if env.get("WT_SESSION") != null { return true }        // Windows Terminal
    if env.get("TERM")?.startsWith("xterm") == true { return true }
    false
}
```

不支持时退化为纯文本，不输出转义序列（避免垃圾字符）。

### 5.2 机制二：`file:line:col` 纯文本

无论是否支持超链接，都要输出标准格式 `path/to/file.xle:42:18`。原因：

- VSCode / IntelliJ / Emacs 的输出面板会自动识别 `文件:行:列` 并变成可点击。
- CI 日志、错误报告、聊天粘贴都需要纯文本。
- 这是唯一不依赖任何协议的通用形式。

路径规则：优先输出**相对于项目根的路径**（`src/config.xle`），因为绝对路径在别人机器上无意义。若异常来自依赖包，输出 `pkg://mysql@1.2.0/src/conn.xle:88:5` 形式，`x` 能解析到缓存目录。

### 5.3 机制三：`x://` 协议处理器

`x install-uri` 注册系统协议处理器：

| 平台 | 机制 |
|---|---|
| Windows | `HKCU\Software\Classes\x` → `x.exe open-uri "%1"` |
| macOS | 生成 `.app` 壳并 `LSSetDefaultHandlerForURLScheme` |
| Linux | `xdg-mime` + `.desktop` 文件 |

URI 规范：

```
x://open?file=<相对或绝对路径>&line=<行>&col=<列>&project=<项目根>
x://doc/<消息ID>                          打开文档站的对应条目
x://file/<pkg>@<ver>/<path>:<line>        打开依赖包内文件
x://heap?addr=0x...                       打开堆分析视图（泄漏排查用）
```

`x open-uri` 的实现逻辑：

1. 读 `project` 参数确定项目根（缺省则从当前工作目录向上找 `x.toml`）。
2. 读 `~/.xle/config.toml` 的 `[editor] command`（默认 `code --goto`，可配 `idea`、`nvim`、`subl`、自定义）。
3. 执行 `<editor> <file>:<line>:<col>`。
4. 编辑器未配置时，打印提示「运行 `x config set editor vscode` 以启用点击跳转」。

如果没有注册协议处理器（用户没跑过 `x install-uri`），点击行为由终端决定：多数终端会对 `x://` 无反应，但 `file:line:col` 文本仍可被 IDE 识别。**降级路径必须无损**。

### 5.4 机制四：结构化输出（给 IDE 插件）

```bash
x run --json-errors
```

```json
{
  "kind": "uncaught_exception",
  "type": "ConfigError",
  "severity": "error",
  "location": { "file": "src/config.xle", "line": 42, "col": 18, "len": 3 },
  "message": "app.toml 第 12 行无法解析：期望 \"=\" 但读到换行",
  "explain": "解析器在读到键 \"server.port\" 后，期待紧跟一个 \"=\" 和值……",
  "suggest": [
    { "text": "把第 12 行改成：server.port = 8080",
      "edit": { "file": "src/config.xle", "line": 12, "col": 1, "remove": 1, "insert": "server.port = 8080\n" } }
  ],
  "values": [
    { "name": "path", "value": "\"app.toml\"", "type": "String" },
    { "name": "line", "value": "12", "type": "Int" }
  ],
  "frames": [
    { "func": "loadConfig", "module": "config", "file": "src/config.xle", "line": 42, "col": 18 },
    { "func": "Application.init", "file": "src/app.xle", "line": 118, "col": 9 },
    { "func": "main", "file": "src/main.xle", "line": 7, "col": 1 }
  ],
  "cause": null,
  "doc": "x://doc/E1004"
}
```

字段 `suggest[].edit` 是**机器可应用的修复**，`x fix` 与 IDE 的「快速修复」都消费这个字段。目标是：常见错误点一下自动改好。

`cause` 嵌套同结构，形成链。每一层的 `location` 都不同，因此一个异常可以同时指向「用户代码的调用行」与「库内部的抛出点」。

## 6. 诊断消息库

### 6.1 为什么需要 ID

编译器与标准库的错误消息必须能：

1. 多语言切换（中文编程要求）。
2. 被文档站索引（用户搜「E1004」能找到完整说明）。
3. 被统计（哪些错误出现最多，优先改进）。

因此内部一律使用 message ID，渲染时才变成自然语言。

```x
// 编译器的诊断定义（comptime 生成，产物内只有 ID + 参数）
@diagnostic("E1004")
struct TomlParseError implements Exception {
    path: String,
    line: Int,
    got: String,
    want: String,
}
```

资源文件：

```toml
# locale/zh.toml
[E1004]
message = "{path} 第 {line} 行无法解析：期望 {want} 但读到 {got}"
explain = """
解析器在读到键 "{got}" 后，期待紧跟一个 {want} 和值，但这一行直接结束了。
最常见的原因是把键和值写在了两行里，或者键名末尾多了一个空格导致
解析器没能识别到 {want}。
"""
suggest = "把第 {line} 行改成完整形式，例如：{example}"

# locale/en.toml
[E1004]
message = "Cannot parse {path} at line {line}: expected {want}, found {got}"
explain = """..."""
suggest = """..."""
```

### 6.2 用户自定义异常的诊断规范

用户异常没有 ID，但也有质量要求。`@diagnose` 注解让用户不必手写 `help()`：

```x
@diagnose(
    message: "端口 {port} 已被占用",
    explain: "同一个端口只能被一个进程监听。上次运行的进程可能还没有完全退出。",
    suggest: "换成其他端口，或运行 `netstat -ano | findstr {port}` 找到占用进程并结束它。",
)
struct PortInUseError implements Exception { port: Int }
```

注解在编译期展开为 `message()` / `help()` 的实现，零运行时开销（字符串常量进 rodata）。**没有 `@diagnose` 也没有 `help()` 实现的异常，lint 报 warn**。

### 6.3 文档站

`x doc --diagnostics` 生成所有消息 ID 的 HTML 页面，每条含：

- 完整消息模板与占位符说明
- 3 个真实触发示例（由测试用例自动提取）
- 常见原因清单
- 修复示例

这是「通俗易懂」的最终落点：终端里只放一句话，详细内容在文档站，链接直接可达。

## 7. 运行时实现

### 7.1 展开机制

**[v0.4 修订]** 展开机制分三档，由 `--unwind=` 选择。默认表驱动，内核/嵌入式用 sjlj，中断上下文用 abort。

| 档 | 机制 | 不抛成本 | 抛成本 | 表体积 | 适用 |
|---|---|---|---|---|---|
| `table`（默认） | 表驱动展开（zero-cost unwinding），与 C++/Rust 一致 | **0** | 5~15 µs | +1%~3% | `server` / `desktop` / `mobile` / `wasm` / 常规 AOT |
| `sjlj` | setjmp/longjmp + 显式 handler 链 | 每次进 `try` 约 15 周期 | 约 1~2 µs | 0 | `kernel` / `embedded` |
| `abort` | 无展开，`throw` 直接 `abort()` | 0 | 不适用 | 0 | 中断处理、早期启动；`try` 编译报错 |

`table` 档的平台表：

| 平台 | 表格式 | 说明 |
|---|---|---|
| Linux x86-64 | `.eh_frame` + `.gcc_except_table` | Itanium C++ ABI 的 LSDA |
| Windows x86-64 | `.pdata` + `.xdata`（UNWIND_INFO） | 表驱动 SEH，非 SJLJ |
| macOS arm64 | `__unwind_info`（compact unwind） | 压缩格式 |

编译器在 Mid IR → 机器码阶段生成这些表。生成依据是 Mid IR 里显式的 `landingPad` 标记（由 `try` 语句降级而来）。

成本：

| 指标 | 数值 |
|---|---|
| 二进制体积 | +1% ~ 3% |
| 不抛出时的运行时成本 | **0**（无 `setjmp`，无状态寄存器） |
| 单次抛出成本 | 5~15 µs（含栈回溯与符号化） |
| 单次 `catch` 命中后的恢复 | ~200 ns |

`table` 档不适合内核：unwind 表本身要占 1%~3% 体积，且表遍历需要运行时支持。所以内核与嵌入式走 `sjlj`。

**`sjlj` 档的两个代价必须说清**：① 进入每个 `try` 要执行 `setjmp`（约 15 周期），所以「`try` 在热循环里」会明显变慢——这也是 `table` 档存在的意义；② `longjmp` 跳过栈帧时**编译器无法自动插入析构调用**，因此 `sjlj` 档下 `defer` 与 ARC 释放由编译器在 `try` 边界处生成显式 handler 链来保证，不能依赖栈展开。这条正确性要求在 §9.1 的测试项里单独覆盖。

**`abort` 档**：`throw` 直接 `abort()`，`try` 语句编译报错。用于中断处理程序与早期启动代码——这些上下文里根本不允许有异常控制流。

**异常对象的小对象栈分配**（全档通用）：

```
异常对象 ≤ 64 字节 → 分配在抛出面栈帧的预留槽位，不碰堆
异常对象 > 64 字节 → 堆分配（走域本地分配器）
```

64 字节足以容纳「错误码 + 2~3 个字段」这类绝大多数异常。收益是内核态 `throw` 不再需要分配器（内核早期启动阶段堆还没起来），同时把常规场景的抛出成本削掉一次 malloc/free（约 30~50 ns）。

### 7.2 栈回溯与符号化

抛出时的动作序列：

```
throw expr
  → 分配异常对象（若在上一级 catch 中已存在则复用）
  → 填充 location（当前 PC）
  → 【debug】快照局部变量 → 挂到异常对象
  → 遍历 unwind 表，逐帧记录返回地址
  → 若未捕获，交由顶层 handler 符号化并打印
```

符号化来源（按优先级）：

| 来源 | 内容 | 何时有 |
|---|---|---|
| `.xmap` 伴随文件 | 地址区间 → 文件/行/列/函数名 | `--debug` 构建自动生成，与二进制同目录 |
| 内嵌 DWARF | 同上，但支持完整变量信息 | `--debug=full` |
| PDB（Windows） | 同上 | `--debug` 且 `--pdb` |
| 仅符号表 | 函数名，无行号 | release 构建（`--strip=lines`） |
| 无 | 显示 `0x00007ff6...` | 完全 strip |

`.xmap` 的设计动机：DWARF 解析器是 3000 行代码，而 99% 的场景只需要「地址 → 行号」。`.xmap` 是一个紧凑的二分查找表（每函数一个区间条目），解析器 200 行。**release 构建默认携带 `.xmap`，除非显式 `--strip=all`。**

体积：`.xmap` 约为 DWARF 的 1/8，10 万行项目约 400 KB。对「崩溃时能否定位」这点投入完全值得。

### 7.3 局部变量快照

debug 构建在 `throw` 点生成快照代码：

```
对每个在 throw 点活跃（live）且类型可打印的局部变量：
  生成一次序列化调用，写入异常对象的 values 列表
```

限制（必须明确告知用户）：

| 限制 | 说明 |
|---|---|
| 仅 debug 构建 | release 关闭（`--trace-values` 可单独开启） |
| 仅可打印类型 | 实现了 `Display` 的类型；未实现的显示 `<类型名 省略>` |
| 仅标量与短字符串 | 超长容器只记录 `len`（避免抛异常时再 OOM） |
| 深拷贝成本 | 单次抛出 +2~5 µs，仅在 debug 构建付费 |

这是相对 Java 的实质改进：Java 的异常只有栈和消息，用户复现问题时仍需加日志。X 直接给出「抛出那一刻所有相关变量的值」。

### 7.4 线程与协程

- 栈回溯只回溯**当前协程**的栈，不跨协程。
- `--trace=full` 时附加所有协程的**状态与创建位置**（不打印其他协程的栈，那没有意义）。
- 异常不跨线程传播。跨线程错误（`spawn` 的任务失败）通过：任务句柄的 `join()` 重新抛出原异常（保留原栈）。
- `scope` 块中任一子任务抛出：取消同组其余任务，`scope` 退出时抛出第一个异常，其余进 `suppressed` 列表（同 Java 的 `getSuppressed`）。

### 7.5 热路径优化

对于「抛出频率极高、且明确知道不想看栈」的场景：

```x
throw! NotFoundError { id }        // 感叹号：不采集栈回溯，成本降到 ~80 ns
```

用于内部循环里的信号式控制流（如解析器的「试探」）。`throw!` 的异常被捕获后 `location()` 返回 null，栈为空。lint 对 `throw!` 给出提示「该异常不含栈回溯」。**普通业务代码禁止用 `throw!`**（lint style 警告）。

## 8. 与编译流程的关系

无解释器后，异常语义必须在编译期完全确定：

| 阶段 | 职责 |
|---|---|
| 类型检查 | 校验 `throw` 的对象是 `Exception` 子类型 |
| 异常推断 | 计算每个函数的异常集合，写进元数据 |
| 签名校验 | `throws` 显式声明时，校验推断结果 ⊆ 声明 |
| Core IR | `try` 降级为 `tryBegin` / `tryEnd` / `catchBlock` 标记 |
| Mid IR | 生成 `landingPad`，插入清理代码（ARC release、`finally`） |
| 代码生成 | 产出 unwind 表 + `.xmap` |
| 链接 | 静态链接顶层 handler（打印栈 + 退出码） |

关键正确性要求：**所有 `catch`/`finally` 路径上的 ARC 释放必须完整**。这是表驱动展开最容易出错的地方（泄漏或双重释放）。防护手段见 §9.1。

## 9. 验证

### 9.1 异常安全性测试

每个含 `try` 的函数都要通过以下测试（由测试框架自动生成部分）：

| 测试 | 手段 |
|---|---|
| 展开路径无泄漏 | `--check-leaks` 下运行「抛出 → 捕获 → 退出」，泄漏数必须为 0 |
| **三档展开语义一致** | 同一程序在 `--unwind=table` 与 `--unwind=sjlj` 下跑，`defer` 执行次数与顺序、最终输出必须一致。**这是 `sjlj` 档最大的风险点**——`longjmp` 会跳过栈帧，编译器必须显式生成 `defer` 与 ARC 释放的 handler 链 |
| `finally` 必执行 | 注入计数，断言 `finally` 执行次数 = 进入次数 |
| 嵌套展开 | 4 层 `try` 嵌套，抛出点在第 4 层，断言 4 层 `defer` 全执行 |
| 协程展开 | 协程内抛异常 → 协程终止 → 调度器状态正确（不泄漏栈内存） |
| 重抛保留栈 | `catch` 内 `rethrow` 后，栈必须含原始抛出点 |
| 异常链完整 | A→B→C 三层包装，`cause` 链深度必须为 3 |

### 9.2 消息质量测试

```
对 locale/*.toml 中每条消息：
  1. 必须是合法模板（占位符都能被对应异常的字段填充）

CI 门禁：任何一条不通过则阻塞合并。
```

```x
// src/config.xle

@diagnose(
    message: "{path} 第 {line} 行无法解析：{detail}",
    explain: "Toml 解析器逐行读取键值对。当它读到键之后没有找到等号，就会在这一行停下。"
             "最常见的两种情况：键和值被换行拆开了；键名末尾有不可见空格。",
    suggest: "单独成一行写成 key = value 的形式；若键名从别处复制而来，删掉末尾空白再试。",
)
struct ConfigError implements Exception {
    path: String,
    line: Int,
    detail: String,
}

pub fn loadConfig(path: String) -> Config throws ConfigError, IoError {
    let text = fs.readText(path)              // IoError 直接上抛，编译器自动加入集合
    let doc = toml.parse(text) catch e: TomlError {
        throw ConfigError {
            path: path,
            line: e.line,
            detail: e.detail,
            cause: e,
        }
    }
    validate(doc)
}

// src/main.xle
pub fn main() {
    let cfg = loadConfig("app.toml")
    println("监听 {cfg.host}:{cfg.port}")
}
```

## 11. 明确不做的事

| 不做 | 理由 |
|---|---|
| 异常用于常规控制流 | 成本 5 µs 量级，循环里用等于自毁性能。用 `Option` 或状态变量 |
| `on error resume next` 式忽略 | 静默失败是最坏的失败 |
| 异常携带完整堆转储 | 体积失控，且 99% 无用。用 `--profile=heap` 单独排 |
| 自动重试 | 语言不该替用户决定重试策略 |
| 异常跨进程序列化 | 分布式错误应显式建模为消息，不是异常 |
| `finally` 内 `return` | 覆盖异常，明确禁止（编译错误） |
