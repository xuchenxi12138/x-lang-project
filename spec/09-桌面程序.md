# 09 · 桌面程序

> 本文回答一个问题：**X 语言怎么写出一个带窗口的桌面程序。**
> 没有 UI 框架、没有控件树、没有事件回调——只有 17 个绘图函数和
> 一个 `while` 循环。这份文档解释为什么是这个设计，以及怎么用它。

---

## 0. 结论

**结论一：P0 的窗口能力是「一块画布 + 鼠标位置」，不是 UI 框架。** 17 个内建全部是即时模式（immediate mode）：每帧从零重画，状态全在 X 语言自己的变量里，窗口系统那边什么都不存。

**结论二：这不是妥协，是刻意选择。** 保留状态的地方越少，「显示的和实际的不一致」这类 bug 的生存空间越小。扫雷的每一格状态只有一份，就在 `board.xle` 的数组里。

**结论三：AOT 产物必须自包含单文件。** 不能依赖编译期去找 `src/gui/gui_win32.c` —— 那个文件在用户机器上不存在。做法是构建期把窗口运行时的 C 源码转成字符串常量内嵌进生成的 C 代码里。

---

## 1. 为什么是即时模式

### 1.1 传统控件方式的代价

按「窗口里存一份控件树」的方式做，一个格子按钮至少有四个状态要同步：

| 状态存在哪 | 谁负责改 | 什么时候改 |
|---|---|---|
| 窗口系统的控件属性 | 窗口系统 | 收到点击时 |
| X 语言的棋盘数组 | 游戏逻辑 | 收到点击时 |
| 控件的视觉（按下/悬停/禁用） | 窗口系统 | 鼠标移动时 |
| 重绘消息的时机 | 窗口系统 | 不确定 |

四份状态，三处修改点。任何一次漏同步的表现都是「显示的和实际的不一样」——而这类 bug 的复现条件往往要求特定的鼠标移动顺序，极难定位。

### 1.2 即时模式的代价与收益

每帧重画意味着 480 格 × 2 个矩形 = 每帧不到 1000 次 GDI 调用。这个量级在 60fps 下完全不是问题——GDI 的 `FillRect` 单次调用在微秒级。

真正的代价在别处：**没有「只重绘变化的部分」这个优化，也没有它的复杂度。** 不需要脏矩形管理、不需要失效传播、不需要双重缓存的同步逻辑。

收益是状态只有一份。扫雷的绘制函数全部是纯的：给它一个棋盘数组和一个鼠标位置，它画出对应的画面。没有任何隐藏状态，所以任何一帧都可以用任意棋盘状态直接构造出来——这正是 `demo.xle` 能拿到确定截图的原因。

## 2. 函数清单

全部 29 个，按用途分五组。

### 2.1 生命周期

| 函数 | 签名 | 说明 |
|---|---|---|
| `winOpen` | `(title: String, w: Int, h: Int) -> Bool` | 开窗。失败返回 `false`（无图形环境、尺寸非法） |
| `winClose` | `() -> Null` | 关窗并释放 GDI 资源 |
| `winShouldClose` | `() -> Bool` | 用户点了关闭按钮吗 |

### 2.2 绘制

**所有绘制调用必须夹在 `winBeginFrame` 和 `winEndFrame` 之间。**

| 函数 | 签名 | 说明 |
|---|---|---|
| `winBeginFrame` | `() -> Null` | 开始一帧，清空后备缓冲 |
| `winEndFrame` | `() -> Null` | 结束一帧，把后备缓冲一次性贴到窗口 |
| `winFillRect` | `(x, y, w, h, color: Int) -> Null` | 填充矩形。颜色是 `0xRRGGBB` |
| `winBorderRect` | `(x, y, w, h, thickness, color) -> Null` | 画边框（描边，不填充） |
| `winText` | `(x, y, text: String, color) -> Null` | 在 `(x,y)` 画文字，`y` 是文字**顶部** |
| `winTextWidth` | `(text: String) -> Int` | 文字的像素宽度，用于居中 |
| `winTextHeight` | `() -> Int` | 当前字体的行高 |

### 2.3 形状与样式（v0.16 新增）

前 17 个内建只能画**轴对齐的实心矩形**，所以「圆角、旋转、渐变、淡入
淡出」在语言层无论怎么写都出不来 —— 这不是缺 API 包装，是底层没有
能力。下面 12 个补的就是这块。

| 函数 | 签名 | 说明 |
|---|---|---|
| `winFillRound` | `(x, y, w, h, radius, color) -> Null` | 圆角填充。半径按 `min(w,h)/2` 自动夹紧，给大了变胶囊而不是怪形状 |
| `winBorderRound` | `(x, y, w, h, radius, thickness, color) -> Null` | 圆角描边。空画刷 + 宽画笔一次成型，背景自然透出 |
| `winEllipse` | `(x, y, w, h, color) -> Null` | 椭圆填充（`w == h` 即圆） |
| `winPath` | `(points: Array, color) -> Null` | 多边形。`points` 是扁平点表 `[x0,y0,x1,y1,...]`，少于 3 点直接返回 |
| `winGradient` | `(x, y, w, h, c1, c2, vertical: Bool) -> Null` | 线性渐变。`vertical` 真 = 上 c1 下 c2，假 = 左 c1 右 c2 |
| `winPushTransform` | `(pivotX, pivotY, rotDeg: Float, scale: Float) -> Null` | 压入变换。绕 `(pivotX, pivotY)` 旋转 + 缩放，累计角度相加、缩放相乘 |
| `winPopTransform` | `() -> Null` | 弹出变换 |
| `winAlpha` | `(a: Float) -> Null` | 压入透明度。**乘性**叠加（0.5 × 0.5 = 0.25），不是覆盖 |
| `winPopAlpha` | `() -> Null` | 弹出透明度 |
| `winClip` | `(x, y, w, h) -> Null` | 压入裁剪区。列表、滚动区域必须用，否则内容会画到别的控件上 |
| `winUnclip` | `() -> Null` | 弹出裁剪区 |
| `winTextRot` | `(x, y, text, color, rotDeg: Float) -> Null` | 旋转文字。走 GDI escapement，与 `winText` 分开是因为建字体时机不同 |

#### 为什么透明度是「乘性」而不是「覆盖」

嵌套才是真实场景：一个 alpha=0.8 的面板里放一个 alpha=0.5 的按钮，
本意是「按钮比面板更透」。覆盖语义会得到 0.5 —— 面板的 0.8 凭空消失。
乘性语义得到 0.4，与直觉一致。

#### 透明度的实现边界（重要）

GDI 没有全局 alpha。精确做法要把整段绘制画进临时位图再 `AlphaBlend`，
实测在 800×600 上掉 40% 帧率。所以这里用「颜色与背景色预混合」的近似：

- 背景按纯色假设（`0x1E1E24`）
- 叠在**渐变或图片**上的半透明元素颜色会偏

这是实现上限，不是 bug。真需要精确透明度时走后台缓冲整段混合。

### 2.4 输入

| 函数 | 签名 | 说明 |
|---|---|---|
| `winMouseX` / `winMouseY` | `() -> Int` | 鼠标在窗口内的坐标 |
| `winMouseDown` | `(button: Int) -> Bool` | 某个键当前是否按住（0=左 1=右 2=中） |
| `winPollClick` | `() -> Array` 或 `Null` | 取一个点击事件 `[x, y, button]`；队列空时返回 `null` |

### 2.5 时间与截图

| 函数 | 签名 | 说明 |
|---|---|---|
| `winTime` | `() -> Float` | 自进程启动的秒数（浮点，可用于计时） |
| `winSleep` | `(ms: Int) -> Null` | 休眠。用于限制帧率 |
| `winScreenshot` | `(path: String) -> Bool` | 把当前后备缓冲存成 BMP |

### 2.6 关于 `winPollClick` 的返回值

它返回 `Array` 或 `null`，所以循环写法是：

```x
var click = winPollClick()
while click != null {
    let x = click[0]
    let y = click[1]
    let btn = click[2]
    // ... 处理
    click = winPollClick()
}
```

**必须用 `while` 而不是 `if`。** 快速连点会在一帧内积累多个事件；只取一个的话剩下的留到下一帧，在 60fps 下表现为「点击有延迟」。最终都会生效，但手感明显。

### 2.7 样式层：`Style` 与 `Anim`

12 个原语解决的是「底层画不出来」，但直接调它们仍然要写十来个参数。
`stdlib/ui.xle` 因此加了两层描述：

| 类型 | 字段 | 作用 |
|---|---|---|
| `Style` | 19 个（填充三态 / 描边 / 圆角 / 文字 / 渐变 / 透明度 / 旋转 / 缩放 / 裁剪 / 阴影） | 把「控件长什么样」收成一个值 |
| `Anim` | 5 个（起点 / 终点 / 起始时刻 / 时长 / 缓动） | 把「某个值随时间的插值」收成一个值 |

```x
// 链式派生：每个方法返回新 Style，原值不变
let card = Style.fromTheme(Theme.dark())
    .fill(0x2A2A33).states(0x34343F, 0x3E3E4C)
    .border(0x3F3F4D, 1).radius(10)
    .gradient(0x3B82F6, 0x9333EA, true)
    .opacity(85).rotate(12.0).scaleTo(120)
    .withShadow(0x000000, 2, 6)

Style.render(card, Rect { x: 40, y: 40, w: 160, h: 48 }, "确定", hover, down)
```

**为什么是栈而不是一个大结构体。** 样式会嵌套生效（面板 alpha=0.8，
里面的按钮不该每层重算），栈让「继承 + 局部覆盖」自然成立。

**为什么动画按 `winTime` 插值而不是关键帧。** 即时模式每帧重建一切，
状态机式动画需要一个长期存活且可变的对象。`Anim` 只是「一个值 + 一个
时间区间」，`value()` 用 `winTime()` 现算 —— 同一个 `Anim` 值在任何帧
调用都得到「按真实时间应得的值」，因此天然可在多控件间共享、可拷贝。

```x
let a = Anim.at(0.0, 1.0, 0.3).withEase(2)   // easeOut
let alpha = a.valueInt()                     // 每帧算一次
Style.opacity(style, alpha)
```

**`UI_NONE = -1` 而不是 `0`。** `0x000000` 是合法的黑色。用 0 表示
「不画」会让黑色填充永远画不出来，症状是「设了黑色却没效果」——
看起来像圆角或裁剪出了问题，排查方向完全不搭。

## 3. 一个最小程序

```x
fn main() -> Int {
    if !winOpen("Hello", 320, 200) {
        return 1
    }

    var running = true
    while running {
        winBeginFrame()
        winFillRect(0, 0, 320, 200, 0x1E1E24)
        winText(20, 20, "你好，桌面", 0xE8E8F0)
        winEndFrame()

        if winShouldClose() {
            running = false
        }
        winSleep(16)      // ~60fps
    }

    winClose()
    return 0
}
```

`winSleep(16)` 不是可选的。没有它，程序会以 CPU 满载的方式跑满几千帧每秒，风扇会响，笔记本电池会掉。

## 4. 中文显示：为什么必须走 W 系列 API

这是一个踩过的坑，写在这里因为它的症状极具误导性。

### 4.1 症状

用 `TextOutA` 画中文，Windows 上简体中文系统（CP936）得到的是「鎵弿」这类乱码。

### 4.2 原因

`TextOutA` 的 `A` 表示「参数是按**系统默认代码页**解释的字节流」。X 语言的字符串内部是 UTF-8。「中文」这三个字节的 UTF-8 是 `E4 B8 AD E6 96 87`，按 CP936 解读会得到完全不同的字符——而且**不会报错**，因为 CP936 恰好能解码大部分字节序列。

### 4.3 做法

全部转成宽字符再调 `W` 系列：

```c
static wchar_t* u8_to_w(const char* s) {
    if (!s) return NULL;
    int n = MultiByteToWideChar(CP_UTF8, 0, s, -1, NULL, 0);
    if (n <= 0) return NULL;
    wchar_t* out = (wchar_t*)malloc((size_t)n * sizeof(wchar_t));
    if (!out) return NULL;
    if (MultiByteToWideChar(CP_UTF8, 0, s, -1, out, n) <= 0) {
        free(out); return NULL;
    }
    return out;
}
```

同样的转换适用于 `CreateWindowW` 的标题、`_wfopen` 的截图路径——**任何接受字符串的 Win32 调用都要走 W 版本**。

### 4.4 字体也必须换

最初用的是 Consolas（等宽，方便算字宽）。但 Consolas **不含中文字形**，Windows 会走 font linking 借别的字体来画中文，结果是中英文混排时字宽不一致、基线错位，`winTextWidth` 算出来的宽度和实际绘制宽度对不上，所有居中全部偏移。

改用微软雅黑：

```c
s_font = CreateFontW(15, 0, 0, 0, FW_NORMAL, FALSE, FALSE, FALSE,
    DEFAULT_CHARSET, OUT_TT_PRECIS, CLIP_DEFAULT_PRECIS,
    CLEARTYPE_QUALITY, DEFAULT_PITCH | FF_DONTCARE,
    L"Microsoft YaHei UI");
// 回退链：Microsoft YaHei → DEFAULT_GUI_FONT
```

## 5. 双缓冲：为什么必须有

`winBeginFrame` 在内存 DC 上画，`winEndFrame` 用一次 `BitBlt` 把整块贴到窗口。

不做双缓冲的表现：每画一格就贴一次，屏幕上的中间状态肉眼可见——翻格子时会看到闪烁，窗口拖动时会有拖影。

实现上有个细节：`winFillRect` 如果每帧创建/销毁 `HBRUSH`，1000 次堆分配会在任务管理器里留下可见的 CPU 曲线。用 `DC_BRUSH` 这个股票对象 + `SetDCBrushColor` 改颜色，零分配：

```c
HGDIOBJ old = SelectObject(s_mem_dc, GetStockObject(DC_BRUSH));
SetDCBrushColor(s_mem_dc, RGB(...));
FillRect(s_mem_dc, &rc, (HBRUSH)GetStockObject(DC_BRUSH));
SelectObject(s_mem_dc, old);
```

## 6. AOT：产物必须自包含

### 6.1 问题

`codegen_c_build` 生成一份 C 代码再交给 gcc。如果生成的 C 代码里写 `#include "gui/gui_win32.c"`，那么：

- 在开发机上能编译（源文件在那儿）
- 用户拿到 `.exe` 之后一切正常
- 但**用户如果拿到的是那份生成的 `.c`**（`--emit=c` 的输出），它就编译不了

更麻烦的是「AOT 产物应该可以被单独分发」这条契约：产物不该依赖任何源文件。

### 6.2 做法

构建期把 `gui.h` + `gui_win32.c` 转成 C 字符串常量，写进 `src/gui/gui_embed.h`：

```
tools/gen_gui_embed.py  →  src/gui/gui_embed.h
   │                          │
   │                          ├── GUI_IMPL_HEAD  (gui.h 的内容)
   └── 读两个源文件            └── GUI_IMPL_BODY  (gui_win32.c 的内容)
```

生成的 C 代码里直接 `fprintf(out, "%s", GUI_IMPL_HEAD)` 把它们贴进去。这样产物是单文件、自包含。

### 6.3 按需内嵌

不是所有程序都需要窗口。`bc_uses_gui` 扫一遍字节码，只有出现 `BC_BUILTIN` 才内嵌并链接 `gdi32`/`user32`/`msimg32`：

> `msimg32` 只为 `GradientFill`（`winGradient`）而加，但这里是**无条件**
> 加进 GUI 档的链接参数，不按「用到渐变才加」来判。理由是判据要扫
> 字节码里的具体内建 id，而多一个 `if` 就多一条可能与 `bc_uses_gui`
> 不同步的分支 —— 漏加的报错是 `undefined reference to GradientFill`，
> 对用户毫无指向性；而 `-lmsimg32` 在无渐变时只是一个空的链接项。

```c
static bool bc_uses_gui(Bytecode* bc) {
    for (int i = 0; i < bc->code_count; i++) {
        if (bc->code[i].op != BC_BUILTIN) continue;
        XBuiltin id = (XBuiltin)bc->code[i].a;
        if (id > XBI_NONE && id < XBI_COUNT) return true;
    }
    return false;
}
```

判据是「出现过」而不是「会执行到」。哪怕写在 `if false` 里也照样内嵌——保守方向是「多编一点」，漏掉会导致链接期报 `undefined reference to xgui_open`，那个错误对用户毫无指向性。

不加这一步的代价：hello world 也会依赖 gdi32/user32，产物大 200 KB，而且交叉编译到 Linux 时 `-lgdi32` 直接链接失败。

### 6.4 生成器自己的正确性

`gen_gui_embed.py` 把源文件转成 C 字符串字面量，逐字符处理。第一版用 Python `str` 遍历，对中文执行 `ord('中') & 0xFF` 得到 `0x2D`——也就是减号。生成的 C 代码里所有中文注释变成一串 `-----`，**编译完全正常，运行完全正常**，只有人眼去看那份 .c 才会发现。

这类错误靠 review 抓不住。所以生成器自带编译期自检：把生成的 C 字面量交给编译器解回来，和原文件逐字节比对。自检本身又暴露了两个问题（都是中文路径导致的，见 `tools/build.sh` 的坑 3）。

## 7. 案例：扫雷

`games/minesweeper/` 是这套能力的完整用例，分三层：

| 文件 | 职责 | 能否脱离窗口测试 |
|---|---|---|
| `board.xle` | 棋盘逻辑：布雷、计数、连锁展开、胜负判定 | **能**，纯 `println` 驱动 |
| `ui.xle` | 绘制与交互 | 能被 `demo.xle` 用构造好的局面调用 |
| `minesweeper.xle` | 主循环 | 不能 |

### 7.1 为什么这样分层

`board.xle` 不画一个像素、不读一次鼠标。所以它的 25 项断言（`board_test.xle`）能在无头环境里跑，也能比对 AOT 产物的一致性。

如果棋盘逻辑和绘制混在一起，「连锁展开是否正确」这个纯逻辑问题就必须开窗、点鼠标、看截图才能验证——而截图看不出一格数字算错。

### 7.2 没有结构体怎么办

P0 没有 struct，所以：

- **棋盘**用一个 9 元组数组：`b[0]=w, b[1]=h, b[2]=雷数, b[3]=mine数组, ...`
- **格子状态**用三个平行数组（`mine`/`open`/`flag`）加一个 `num`

不打包成「一个数组，0..9 表示数字、10 表示旗」的理由：打包省内存但让每个读写点都要解包，而且「有旗且已翻开」这种非法组合无法表达。三个平行数组各自语义单一，出错时一眼能看出是哪个字段错了。

### 7.3 截图回归

`demo.xle` 用固定种子造四个局面（进行中/失败/胜利/中级），各画一帧、存 BMP。

不做像素比对——没有基线时「检查像素对不对」毫无意义，第一版永远「不对」。价值在于**留下基线**：改了绘制代码后重跑，`diff` 一下就知道哪里变了。

已验证两档一致性：解释器与 AOT 产物生成的 BMP **逐字节相同**。

## 8. P0 的能力边界

明确不做的：

| 不做 | 理由 | 替代 |
|---|---|---|
| 控件（按钮/输入框/列表） | 需要控件树与事件分发，与即时模式冲突 | 用矩形 + `winMouseDown` 自己画 |
| 图片加载（PNG/JPG） | 需要解码器。BMP 能直接写是因为格式够简单 | 用 `winScreenshot` 输出，外部工具转格式 |
| Alpha 混合 | GDI 的 `AlphaBlend` 需要额外的 DC 与位图管理 | 用相近的实色叠加 |
| 抗锯齿线条 | GDI 的 `LineTo` 有锯齿，而且没有粗线 | 用多个矩形拼（扫雷的旗就是五个矩形） |
| 多窗口 | 需要窗口句柄的完整生命周期管理 | 单窗口够用 |
| 键盘输入 | 需要 `WM_KEYDOWN` 的分发与字符映射 | P1 |
| 文字换行/对齐 | `TextOut` 不做换行 | 自己按 `winTextWidth` 断行 |

这些边界不是能力的上限，是**当前版本的选择**。每加一项都是几百行平台代码加一套新的失败模式，而 P0 要证明的是「X 能写出能用的桌面程序」——扫雷已经证明了。

---

## 9. 平台现状

| 平台 | 状态 |
|---|---|
| Windows | 完整实现（GDI + W 系列 API） |
| Linux / macOS | 空实现（所有函数返回恒定的假值，不崩溃） |

非 Windows 平台上 `gui.h` 的接口仍然可编译，所有函数是空体：`winOpen` 返回 `false`，`winScreenshot` 返回 `false`。这样跨平台的程序能编译、能跑逻辑测试，只是画不出东西。

移植到 X11/Cocoa 的工程量估计：X11 约 400 行（`XCreateWindow` + `XPutImage` + Xft），Cocoa 约 500 行（`NSWindow` + `CGContext`）。接口不变，因为 `gui.h` 不含任何平台类型。
