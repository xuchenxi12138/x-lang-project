# 05 · 路线图与风险

> 阶段划分、里程碑验收标准、技术风险 Top 13 与应对、以及「如果只能做一个功能」的取舍。

## 1. 阶段划分总览

以 1 人全职投入为基准估算；多人并行不是线性加速（核心部分强耦合）。

| 阶段 | 内容 | 里程碑 | 估时 |
|---|---|---|---|
| P0 | 可跑的最小语言 | 能算斐波那契，`x run` 可用 | 2 个月 |
| P1 | 完整语言核心 + 高性能解释器 | 解释器达 native 的 1/6，能实现 JSON 解析器 | 5 个月 |
| P2 | AOT 编译 + 自举 | `x build` 产单文件二进制，X 编译 X，差分测试全绿 | 6 个月 |
| P3 | 数值 · 数据 · AI 推理 | DataFrame + Notebook + 自动微分 + ONNX 推理可用 | 7 个月 |
| P4 | 服务端 · 桌面 · OS 子集 | HTTP 服务压测通过，`std.ui` 三平台可用，`--profile=kernel` 可编 | 6 个月 |
| P5 | 包管理 · 生态 · 移动绑定 | 注册中心上线，≥ 30 个包，JNI/ObjC 绑定可用 | 5 个月 |
| P6 | 中文编程 + 硬稳定性 | 中文版产物与英文逐字节一致，1.0 发布 | 3 个月 |

合计 **34 个月**到 1.0。

**两个主场的压缩路线**：若只做「数据分析 + 服务端」（见 [08](08-多领域支撑.md) §7 的定位裁决），砍掉 `std.ui`/`std.ml` 的 GPU 部分与移动绑定，可压到 **24 个月**。**建议走这条路线**——主场不成立，其他领域也不会有用户。

**现实的打折**：以上基于「已具备编译器工程经验且无重大返工」。语言设计的实际历史（Go/Rust/Zig 的早期）显示 P0-P2 经常出现 2 倍偏差，主要来自类型系统、解释器优化与后端调试。**建议以 42 个月做预算**（全领域）/ **30 个月**（两主场）。

注意 P1、P2 各涨 1 个月，P3 涨 3 个月，原因分别是：

| 阶段 | 涨幅来源 |
|---|---|
| P1 | 解释器性能优化（[07](07-高性能解释器.md) L1~L5）+ const 泛型 + Domain 模型 |
| P2 | `asm!`、union/位域、内存序、`--unwind=sjlj`、Profile 系统（[08](08-多领域支撑.md) §5.1 的 OS 类特性） |
| P3 | DataFrame、Notebook、自动微分、SIMD——数据分析与 AI 的全部主场特性 |

## 2. 各阶段详细验收

### P0 · 可跑的最小语言（2 个月）

| 项 | 内容 |
|---|---|
| 语法子集 | `fn`、`let`/`var`、`if`/`else`、`while`、算术、函数调用、返回值 |
| 类型 | 仅 `Int`/`Float`/`Bool`/`String`，无推断（全部必须注解，暂时违反铁律 3） |
| 执行 | **栈式字节码 + switch 分派**（不做 AST 树遍历，见下） |
| 工具 | `x run`、`x script` |
| 交付验收 | 能跑通 20 个手工测试程序，含递归、循环、字符串拼接 |
| 明确不做 | 泛型、trait、模块、AOT、内存管理（用引用计数 + 永不释放的粗糙实现） |

P0 的目的不是可用，而是**验证语法手感**。如果写 P0 时发现语法别扭，此时改成本最低。

**为什么直接做栈式字节码而不是 AST 树遍历**：树遍历实现快 2 周，但它无法复用为 AOT 输入，也无法作为差分测试的参照。直接做栈式字节码多花 2~3 周，但它是 P1 寄存器式字节码的对照基准（[07](07-高性能解释器.md) §7 步 1），这份基准会在 P2 之后持续发挥作用。**省下的 3 周换来的是后面两年的「没有正确性基线」。**

### P1 · 完整语言核心 + 高性能解释器（5 个月）

| 项 | 内容 |
|---|---|
| 语法 | 全部 45 关键字、match、闭包、泛型、**const 泛型**、trait、模块、comptime 基础 |
| 类型 | 双向推断、默认回退、单态化、空安全、**异常（不做 Result）** |
| 并发 | M:N 协程、**并发域（Domain）**、`@shared`/`move`、task-local、`par` |
| 执行（前半） | 栈式字节码解释器（P0 基础上补全语言特性） |
| 执行（后半） | **寄存器式字节码 + 直接线程化 + 超指令 + 类型化指令 + 调用优化**（[07](07-高性能解释器.md) L1~L5、L7） |
| 运行时 | ARC（域本地非原子）、分配器、异常展开（table）、栈回溯与可点击诊断 |
| 工具 | `x fmt`、`x test` |
| 交付验收 | ① 用 X 写 JSON 解析器 + 正则引擎（各 < 800 行），测试全绿 ② **`fib(30)` 达 native 的 1/6 以内** ③ 数值循环零分配 ④ **`--check-races` 下 1000 个并发协程跑 24 小时无竞争报告** |
| 明确不做 | AOT、网络、内联缓存（L6 推迟到 P2） |

**P1 是验证「语言能否表达真实程序」的关键节点。** 如果不能顺手写 parser，说明语法有问题，此时还能改（P2 后改语法要重写自举编译器，代价 10 倍）。

**P1 也是验证「解释器能否达到设计性能」的关键节点。** 如果寄存器式 + 线程化 + 超指令三层做完还达不到 1/6，说明设计有问题，必须在 P2 之前发现（P2 之后再回头改字节码格式，等于重写后端）。验收方式：跑 [07](07-高性能解释器.md) §6.1 的六个基准，实测值写回该表。

**Domain 模型必须在 P1 完成**，因为它改变对象的所有权语义，越晚改代价越大（P2 之后所有库代码都依赖它）。

### P2 · AOT 编译与自举（6 个月）

| 项 | 内容 |
|---|---|
| 后端 | 字节码 → Mid IR → 优化 pass ×13 → x86-64 代码生成、寄存器分配 |
| 链接 | 静态链接运行时，产单文件二进制（Windows PE + Linux ELF） |
| 系统级设施 | **`asm!`、`union`/位域/`@offset`、原子内存序、`Volatile`/MMIO** |
| Profile | 七档 Profile 定义与校验、`--report=size` |
| 展开 | `--unwind=sjlj` + 小对象异常栈分配 |
| 自举 | 用 X 重写编译器前端，fixpoint 测试通过 |
| 并发 | 协程调度器、汇编上下文切换、`async`/`await`/`scope`/`par` |
| 调试 | `.xmap` + DWARF 生成、两档栈回溯格式统一 |
| 差分测试 | `--verify=diff` 基础设施，2000 个测试用例全绿 |
| 内联缓存 | [07](07-高性能解释器.md) L6（仅 `dyn` 路径） |
| 交付验收 | ① `x build` 产物能跑 P1 的全部测试 ② X 编译器能编译自身且 stage2 == stage3 ③ 与 C 版程序对比 5 个基准，性能 ≥ 0.9× ④ **差分测试：解释档与 AOT 档输出逐字节一致** ⑤ **`--profile=kernel` 能编出一个能在裸机打印的 hello world** |
| 明确不做 | AArch64 完整支持、移动平台、网络、包管理 |

**这是全项目最危险的阶段。** 风险集中在：寄存器分配 bug（表现为随机崩溃）、DWARF 格式（文档差）、自举 fixpoint 不收敛（通常是浮点常量或哈希迭代顺序不确定）。

**差分测试是本阶段的主要安全网**。解释档在 P1 已经验证过（跑了几千个测试），它成了 AOT 后端的参照标准：AOT 输出与解释输出不一致，就是 AOT 的 bug。

## 3. 技术风险 Top 13

按「发生概率 × 影响程度」排序。每条给出可执行的应对。

| # | 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|---|
| 1 | **自举 fixpoint 不收敛** | 高 | 致命 | 编译产物必须确定性：禁用哈希表迭代顺序影响输出、浮点常量统一用 bit 模式、单态化按名字排序。CI 强制 stage2 == stage3 |
| 2 | **寄存器分配 bug 导致随机崩溃** | 高 | 致命 | **差分测试：同一字节码在解释档与 AOT 档跑，输出逐字节一致**。配合随机程序生成器（fuzz）每日跑 10 万个程序比对 |
| 3 | **ARC 循环引用导致内存泄漏** | 高 | 严重 | debug 构建默认开启周期检测；文档明确「图结构用 arena 或索引」；lint 检测可疑模式 |
| 4 | **单态化导致代码膨胀、编译爆炸** | 中 | 严重 | 实例数上限 + 自动降级到 `dyn`；提供 `@noMono` 强制擦除 |
| 5 | **DWARF/PDB 生成错误导致无法调试** | 中 | 严重 | 先只做 `.xmap`（200 行解析器），DWARF 排 P3；用 `gcc -g` 生成对照参考逐字段比对 |
| 6 | **协程栈溢出检测在 Windows 上不可靠** | 中 | 严重 | Windows 用 `VirtualAlloc` 保护区 + SEH；Linux 用 `mprotect` guard page + SIGSEGV。两平台各写集成测试 |
| 7 | **数值函数精度不达标** | 中 | 中 | MPFR 对照测试集（100 万点），CI 门禁；不达标就降级为 wrapper libm |
| 8 | **语法设计后期发现致命缺陷** | 中 | 严重 | P1 结束前用 X 写 3 个真实程序（JSON、正则、小解释器）验证；语法变更窗口只到 P2 开始 |
| 9 | **包生态冷启动失败** | 高 | 中 | 官方先做 15 个核心包；提供 C 绑定生成器（`x bindgen`）让 C 库立刻可用，这是初期生态的主要来源 |
| 10 | **优化 pass 互相干扰导致性能回退** | 中 | 中 | 每个 pass 独立开关 + pass 顺序的自动搜索（`x build --search-passes`），基准测试进 CI，回退超 3% 则阻塞合并 |
| 11 | **解释器性能达不到设计目标（1/6）** | 中 | 严重 | P1 中期设检查点：寄存器式 + 线程化 + 超指令做完必须达 1/8，否则停下来查原因（通常是字节码格式设计问题，此时改代价小；P2 后改等于重写后端） |
| 12 | **字节码格式设计不当，两档都受限** | 中 | 致命 | 格式冻结前先写三个真实程序（数值、字符串、对象密集）压测；预留操作码空间与扩展位；格式版本号从第一天就有 |
| 13 | **领域扩散导致核心不聚焦** | **高** | 致命 | 六个目标领域的需求互相排斥（[08](08-多领域支撑.md) §2 矩阵），若同时追六个，结果是一个都不好用。**对策是把「数据分析 + 服务端」钉死为唯一主场**（[08](08-多领域支撑.md) §7），其余领域只保证「可用」不保证「好用」；每个新特性提案必须回答「它服务哪个主场」。这条风险不是技术风险而是**决策风险**，所以要用文档约束：任何偏离两主场的投入都必须显式推翻 §7 的定位裁决 |

### 3.1 单项深入：为什么「两档差分」是最大的风险管理手段

如果只有 AOT 一档，编译器 bug 极难定位——你不知道是语义错了还是代码生成错了。

两档共享同一份字节码，提供免费的双重验证：

```
同一份 .xbc ──→ 解释器 ──→ 输出 A（含副作用序列）
             └→ AOT    ──→ 输出 B
                       assert A == B
```

解释器只有 1.2 万行 C（相对 AOT 后端的 5 万行更容易做对），且它在 P1 阶段已被几千个测试验证过。因此它天然成为 AOT 的**事实标准**。

这个设计的代价是必须维护两套执行机制，收益是编译器正确性可自动化验证。**这是必做项，不是可选项。** 上一版设计曾砍掉解释器，随即失去了这个验证手段——恢复解释器的第一个理由就是它。

## 4. 取舍：如果只能留三个特性

资源不足时按此顺序砍。这个顺序反映「什么真正决定语言能否被使用」。

**必须保留（不可砍）**：

1. **AOT 单文件编译** — 这是与 Python/MATLAB 的根本区分点，砍了就没有存在理由。
2. **数学计算能力（NDArray + 切片视图 + 广播）** — 这是目标场景，砍了就没有用户。
3. **自动内存管理** — 这是目标用户（工程师/科研人员，非系统程序员）的门槛。

**优先砍（成本高、价值低）**：

| 顺序 | 砍什么 | 理由 |
|---|---|---|
| 1 | 中文编程 | 完美好做，且是「视图」层，随时可加 |
| 2 | 反射运行时（只留 comptime） | 运行时反射用户极少 |
| 3 | 泛型擦除 `dyn`（只留单态化） | `dyn` 用于异构容器，可先用枚举替代 |
| 4 | 协程（只留 OS 线程） | 并发模型可后期换，API 兼容。但注意：砍协程等于让**并发域退化为线程**，非原子 ARC 依然正确（域不再迁移），只是失去「万级并发连接」的能力——这是服务端主场的核心卖点，故实际不可砍 |
| 5 | 包管理器（先用 git 子模块） | 生态建设本质是社会工程，不是技术 |
| 6 | 跨平台（只做 Windows 或只做 Linux） | 单平台可行，多平台是线性成本 |
| 7 | 汇编内核（先用朴素循环） | 性能后期专项，正确性优先 |
| 8 | comptime（只留 const） | 泛型特化可硬编码 |
| 9 | **Profile 系统**（只留 `server`/`desktop` 两档） | 六领域需求冲突在「只做两主场」的路线下不存在，可退化为「一套运行时 + 编译开关」。但 `kernel` 档一旦放弃，x-os 就回不到 X |
| 10 | 解释档（只留 AOT） | **可砍但代价明确**：失去差分测试的参照标准、失去 < 3 ms 的调试回路、失去无符号文件的断点调试。若砍，必须另找正确性验证手段 |

**绝不砍**：错误处理（异常）、空安全、可点击诊断、fmt、test、lint。这五项是「语言是否让人愿意用」的真正分界线，比任何语言特性都重要。

注意第 10 条与前面九条性质不同：前面九条砍掉是「少个功能」，第 10 条砍掉是「失去质量保障机制」。砍它之前先想清楚替代方案。

## 5. 与既有工程的关系

| 工程 | 关系 |
|---|---|
| `x-os` | X 语言是其用户态首选语言。L0 层（`std.mem`/`std.ptr`/`std.sys`）必须支持 `--freestanding`，可直接编进内核。建议 x-os 的内核模块在 P3 之后用 X 重写，此前用 C |
| `x-enterprise-erp` | 可作为 X 的第一批真实业务验证项目（P5 之后）。但**不建议**在语言稳定前迁移——业务项目不该承担语言早期风险 |
| `x-safe-meeting-mgr` | 其中 ASR 相关的高性能音频处理可作为 `std.num` 的 SIMD 内核验证场景 |

| 1 | 定稿词法（45 关键字 + 运算符优先级表） | `spec/lexer.md` |
| 2 | 定稿语法（EBNF 全文） | `spec/grammar.ebnf` |
| 3 | 写 token 定义 + 词法器 | `src/lexer.c` |
| 4 | 写 AST 定义 + 递归下降 parser | `src/parser.c` |
| 5 | 写 Core IR 定义 + 降级（仅 Int/Float/Bool/String） | `src/ir.c` |
| 6 | **栈式字节码生成器 + switch 分派解释器** | `src/bc.c`, `src/interp.c` |
| 7 | `x run` / `x script` 命令可用 | `src/main.c` |
| 8 | 20 个手写测试程序 | `tests/p0/` |

第 3-7 步的代码量约 7000 行（比树遍历版本多 1000 行，多出来的是字节码生成与解释循环）。**顺序不能变**：词法 → 语法 → AST → Core IR → 字节码 → 解释器。跳过任一步都会在后面加倍偿还。

**三个具体建议：**

1. P0 阶段就用 `.xle` 文件写测试程序（中文用例写 `.xlc`），而不是先写好解释器再想语法。让「写起来的手感」反过来驱动语法微调，这是语言设计中唯一有效的验证方式。
2. 步 6 先用 switch 分派，不要一上来就线程化。先用最笨的版本把语义跑对，再按 [07](07-高性能解释器.md) §7 换成分派优化版本——两份实现互相对照，是发现 bug 最快的方式。
3. 从第一天就定义 `.xbc` 的版本号与操作码分配表。字节码格式一旦被测试用例依赖，改动成本会陡增。

## 8. 变更记录（决策演化）

记录被推翻的决策，避免后来者重复争论。

| 版本 | 变更 | 原因 |
|---|---|---|
| v0.1 | 三档执行（解释 / 基线 JIT / AOT）；错误双轨（Result + panic） | 初版设计 |
| v0.2 | **移除解释执行**，只留 AOT；错误统一为异常 | 用户要求放弃解释执行 + 要 Java 式可点击异常 |
| v0.3 | **恢复解释执行，并给出七层性能优化方案**；「不提供 REPL」的裁决不变 | 用户要求研究解释执行如何做快 |
| v0.4（当前） | **六领域审查：修 10 个设计缺陷、加 36 个特性、拆 7 档 Profile**；所有权单位从 OS 线程改为**并发域（Domain）**；新增 const 泛型、`asm!`、`union`+位域、原子内存序、`std.dataframe`/`std.ml`/`std.ui` | 用户要求语言能覆盖服务端 / 桌面 / 移动 / OS / AI / 数据分析 |

v0.3 的关键认识：**解释执行与 AOT 不是竞争关系，是分工关系。** 解释档负责开发回路与调试（< 3 ms 启动、无需符号文件的断点、差分测试参照），AOT 档负责交付性能。两者共享同一份字节码，维护成本只比单档高约 30%，拿到的是两个完全不同场景的最优解。

v0.2 的错误在于把「解释器慢」当成了「解释器不可用」。实际上慢的原因很具体——分派不可预测、栈流量、装箱、运行时类型检查——每一项都有成熟解法，叠加起来能到 native 的 1/5。CPython 慢是因为**它是动态语言**，不能归因于「解释」这件事本身。X 是静态类型语言，这一条就抹掉了 CPython 最贵的那部分开销。

v0.4 的关键认识：**六个目标领域的需求不是叠加关系，是互相排斥关系。** 「OS 需要 300KB 运行时且不许堆分配」与「AI 需要 autodiff 图与张量算子」无法共存于一个二进制。硬要统一，结果是每个领域都拿到一个臃肿怪。裁决是把运行时拆成「一份核心 + 七档装配」（Profile），核心薄到能进内核，其余按档位链入。这不是工程妥协，这是唯一能同时成立的架构。

第二个认识：**把 ARC 定为原子操作是致命错误。** 原本「所有权单位 = OS 线程」的假设与「协程可跨线程迁移」直接矛盾——迁移瞬间计数器的读-改-写跨了两个线程，非原子就丢更新。修复不是把计数器改成原子（那会让每次引用增减付出总线锁代价），而是把所有权单位改成**并发域**——一组协程 + 它们独占的对象图，等价于一个可迁移的单线程。迁移发生在挂起点，此时域内无代码在执行，整域搬家只是指针切换。这个改动把一个会导致随机崩溃的设计，变成了零成本的正确设计。

## 9. 变更记录（v0.6 · 引入语法与别名）

| 项 | 决策 | 否决的替代 |
|---|---|---|
| 引入目标形态 | **永不使用字符串字面量**：包带 `@`、模块是裸路径、标准库以 `std` 开头 | JS 式 `from "xxx"`——包名/路径/字符串三者字面同形 |
| 语法基准 | **对标 Python**：`import X` / `from X import a` / `as` 别名，全裸标识符 | 对标 JS / Cargo / Go 的任一形态——都要么带引号、要么带大括号、要么名字要转换 |
| 包前缀符号 | `@`（与注解、模式绑定位置互斥，见 [01](01-语言设计.md) §11.2） | `:` `#` `$` `<>` `::`、靠 `x.toml` 登记隐式区分 |
| 包名字符集 | `[a-z][a-z0-9_]*`，**禁连字符** | 允许 `-` + 自动转下划线（多一条隐式规则，grep 断链）/ 强制别名（罚太重）/ 引号包裹（把字符串请回来） |
| 具名引入语法 | **Python 式前缀** `from path import a, b as c` | `import path.{a, b}`（来源与 import 挤一行，长列表时被埋）；JS 式 `import {a, b} from path`（来源跑最后一行） |
| 关键字 `from` | **加入**（44 → 45） | v0.5 曾否决，依据是 JS 式的问题，不适用于 Python 式 |
| **别名 `as`** | **一等语法**，四种位置全部支持：`import X as Y` / `from X import a as b` / `pub from X import a as b` / `use` 已并入 import | 只允许包级别名（具名符号不能改名会让中文化被迫改包）；不允许别名（长路径被迫缩短只能靠重命名模块） |
| 别名语义 | **纯编译期改名**：`db` 与 `mysql` 在符号表里是同一实体，`db.Pool` 与 `mysql.Pool` 生成完全相同代码；`x fmt` 不展开、不提示 | 包装类型 / 生成代理 / 运行时间接——三者都有开销，而别名本应零成本 |
| 别名可见性 | 别名**仅在本编译单元有效**，不导出（`pub import X as Y` 导出的是 `Y` 这个新名字，不是别名机制本身） | 别名随重导出传播——会形成「同一个包在不同文件里叫不同名字」的追踪地狱 |
| 关键字 `use` | **移除**，引入与重导出统一由 `import` / `from` 承担（`pub import` / `pub from`） | 保留 `use` 专做重导出——留下「import 和 use 该用哪个」的永久疑问 |
| 关键字总数 | 45 → 44（v0.5 去 `use`）→ **45**（v0.6 回加 `from`） | — |
| 路径首段关键字 | `std` / `crate` / `self` / `super` 为**上下文关键字**，不进关键字表 | 保留为硬关键字——会让 `let std = 1` 变成语法错误 |
| 歧义处理 | 本地目录与同名包冲突时**报错**，要求改一行 | 按优先级静默选一个 |
| 引入名冲突 | 报错，要求显式 `as` 别名 | 自动重命名 / 后到者覆盖 / 静默加前缀 |
| 函数内局部引入 | **禁止** | Python 允许函数内 `import`——那是它的历史包袱，会让依赖图依赖控制流 |
| 条件依赖 | 引入名固定，`x.toml` 按 target 换实现包 | 条件引入语法 / `comptime` 守卫内 `import` |

**这一轮的核心认识**：一门语言里凡是「同一个字面可以有两三种解释」的地方，都是后期无法修复的债。JS 的 `"lodash"` 之所以是问题，不在于它用了引号，而在于**引号在别处表示字符串**——于是同一串字符在两种语境下含义不同，工具链必须带上语境才能判断。把包改成 `@name`、把模块改成裸路径，本质是让**每个名字自带它是什么**，任何一段代码被单独摘出来（日志、grep 结果、issue 里的片段、喂给模型）都还能读懂。

**关于别名的第二个认识**：别名不是「语法糖」，是**可读性工具**。`from @mysql.types import Connection as Conn` 让调用点变短，`import @very_long_package_name as vlp` 让长路径不占两屏——这些收益不来自编译期，来自**人读代码的时间**。所以别名必须是零成本的：一旦它带来包装类型或运行时间接，用户就会在大循环里纠结「用别名会不会慢」，那时别名就从工具变成了陷阱。

**v0.5 → v0.6 的修正**：v0.5 把「不用 `from`」写成了裁决，依据是「拆行后来源跑出可视区」。这个判断只对 JS 式（`import {a} from X`）成立，对 Python 式（`from X import a`）不成立——后者把来源放在行首。用户提出「对标 Python」后，这个前提被推翻：**Python 的 import 从来不用字符串，所以「消灭字符串」与「对标 Python」是同一件事，不该分两次做对**。教训是：否决一个语法特性前，先确认否决的是它本身，还是它的某一种排版形式。
