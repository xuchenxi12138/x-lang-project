# 07 · 高性能解释器

> 本文回答一个问题：**如果解释执行要保留，怎么让它足够快。**
> 所有数据标注来源；所有估算标注「估算」，不把估算当实测。

---

## 0. 结论与目标

### 0.1 三个结论

**结论一：解释器的慢不在「解释」两个字，而在四个具体的地方——分派、栈流量、装箱、类型检查。** 这四件事各自有成熟解法，且互不冲突，可以叠加。

**结论二：X 相比 CPython/Python 有一个结构性不公平优势——静态类型。** CPython 每条 `+` 都要运行时判断「这两个东西是什么类型」，X 在编译期就知道。这一项省掉的开销，比任何分派技巧都大。

**结论三：寄存器式字节码同时是解释器的指令流和 AOT 的输入 IR。** 这不是巧合，是刻意设计——它让「双层执行」的维护成本接近零。**没有这个设计，双层执行会拖垮项目；有了它，双层执行几乎免费。**

### 0.2 性能目标

以 C 实现同样算法为 1.0×：

| 场景 | CPython 3.12 实测量级 | X 解释器目标 | X AOT 目标 |
|---|---|---|---|
| 整数循环（fib、sieve） | 1/60 ~ 1/40 | **1/8 ~ 1/5** | 0.9 ~ 1.1 |
| 浮点数值循环（点积、矩阵） | 1/80 ~ 1/50（需 NumPy 才快） | **1/10 ~ 1/6** | 0.9 ~ 1.1 |
| 字符串处理 | 1/30 ~ 1/15 | **1/6 ~ 1/3** | 0.8 ~ 1.0 |
| 对象分配密集 | 1/25 ~ 1/10 | **1/5 ~ 1/3** | 0.7 ~ 1.0 |
| 函数调用密集 | 1/40 ~ 1/20 | **1/6 ~ 1/4** | 0.8 ~ 1.0 |

换算成对 CPython 的倍数：**X 解释器约为 CPython 的 4~8 倍**。这不是乐观估计——PyPy（带 JIT）对 CPython 是 3~10 倍，LuaJIT 的解释器部分对 PUC Lua 约 2 倍，而 X 的静态类型让它在没有 JIT 的前提下就能达到接近 PyPy 的量级。

### 0.3 一句话的路线

```
朴素树遍历 → 栈式字节码 → 寄存器式字节码 → 直接线程化分派
→ 超指令 + 复制 → 栈缓存 → 内联缓存快速化 → （可选）复制-补丁 JIT
```

每一层的收益递减、成本递增。**必须做到第 4 层（寄存器 + 线程化），这是性价比拐点**，前三层不做则后面全是浪费。第 7 层是可选加分项。

## 1. 成本模型：慢在哪

### 1.1 四项开销的来源

写一个 `a + b` 的加法，在 C 里是：

```asm
mov  eax, [a]
add  eax, [b]
```

在朴素栈式解释器里是：

```c
// 1. 取指令 + 分派（间接跳转，分支预测失败 → 15~20 周期）
op = code[ip++];
switch (op) {
case OP_ADD:
    // 2. 弹栈两次（数组读写 + 边界检查，~4 周期）
    Value b = stack[--sp];
    Value a = stack[--sp];
    // 3. 类型检查（两个分支，可能预测失败，~5 周期）
    if (a.tag != INT || b.tag != INT) goto slow_path;
    // 4. 装箱（分配 + 写头，~30 周期，最贵）
    Value r = { .tag = INT, .i = a.i + b.i };
    // 5. 压栈（~4 周期）
    stack[sp++] = r;
    break;
}
```

**加法本身 1 个周期，周边开销 50~70 个周期。** 这就是解释器慢 50 倍的来源，而它跟「加法」毫无关系。

Ertl & Gregg 的实测（JILP 2003）给出的分配是：

| 开销项 | 占执行指令数 | 占运行时 |
|---|---|---|
| 间接分支（分派） | 3.2% ~ 13% | **> 50%**（部分配置） |
| 操作数栈访问 | 约 40%（栈式机） | 15% ~ 25% |
| 类型分派与装箱 | 视语言而定 | 20% ~ 40%（动态语言） |
| 实际计算 | 其余 | 10% 以下 |

注意第一行：**3%~13% 的指令占了超过一半的时间。** 这是所有解释器优化的主战场。

### 1.2 为什么分派这么贵

`switch` 编译出来是一条间接跳转 `jmp [table + op * 8]`。问题在于**全解释器只有这一条 jmp 指令**，但它的目标有 200 多种可能。CPU 的分支目标缓冲（BTB）记录的是「这条指令上次去了哪里」，同一个静态跳转指令对应多个目标，历史记录互相覆盖。

实测的预测失败率：

| 分派方式 | BTB 失败率 | 说明 |
|---|---|---|
| `switch` 分派 | 81% ~ 98% | Ertl & Gregg 2006 测量 |
| 直接线程化 | 50% ~ 63% | 同上 |
| 直接线程化 + 复制 | **约 20%** | 同上 |

一次失败 15~20 周期。假设每 5 条字节码一次分派，失败率 90%，那么执行 100 条字节码要付出 `20 × 0.9 × 20 = 360` 周期的纯浪费。这就是「超过一半时间」。

### 1.3 直接线程化的原理

把 `switch` 拆成每个指令自己的分派：

```c
// 朴素 switch 分派：所有指令共享一条 jmp
while (1) {
    switch (code[ip++]) {
    case OP_ADD: ...; break;
    case OP_MOV: ...; break;
    ...
    }
}

// 直接线程化：每条指令末尾自己跳到下一条
#define DISPATCH() goto *dispatch_table[code[ip++]]

static void *dispatch_table[] = {
    &&L_ADD, &&L_MOV, &&L_JUMP, ...
};

L_ADD:
    ...
    DISPATCH();
L_MOV:
    ...
    DISPATCH();
```

现在每个 `DISPATCH()` 是**不同的静态间接跳转指令**（编译器为每个 `goto *` 生成独立指令）。BTB 里有 200 个不同的表项，各自记录自己的历史。

**效果**：失败率从 90% 降到 60%；再加超指令降到 20%。

**这是 C 语言的 GNU 扩展（`&&label` 取标签地址 + `goto *ptr` 计算跳转）。** MSVC 不支持，Windows 上替代方案见 §3.1.3。

## 2. 不公平优势：静态类型

### 2.1 CPython 的性能天花板在哪

CPython 3.11 的 `BINARY_OP_ADD_INT` 已经去掉了类型检查，但它仍然要做：

1. **拆箱**：`PyLongObject` 的 digits 数组 → C 的 `int64`。
2. **计算**（1 周期）。
3. **装箱**：分配新的 `PyLongObject`，即使结果是个小整数。
4. 引用计数加减（如果复用则 +2）。

第 1 和第 3 步是动态语言的**结构性成本**：Python 里 `1` 是堆上的对象，因为它是引用类型、可以有 `id()`、可以被 `weakref`。X 里 `1` 是寄存器里的 8 字节。

CPython 3.11 的快速化让整数加法提速约 10%（PEP 659 官方数据），但**它无法消除装箱**——语言语义要求 `a + b` 产生新对象。

X 的语义允许：`Int` 是值类型（L1 内存层，见 [01](01-语言设计.md) §6.1），栈上 8 字节，**零分配**。

### 2.2 这就是 X 解释器的核心优势

对比同一条 `a + b`（两者都是 `Int`）：

| 步骤 | CPython 3.11 快速化后 | X 解释器 |
|---|---|---|
| 分派 | 间接跳转 | 间接跳转（可优化，见 §3） |
| 取操作数 | 栈上取两个 `PyObject*`（PyObject**） | 从 VM 寄存器文件取两个 `int64` |
| 类型检查 | 已消除（快速化保证） | **不存在**（编译期已知） |
| 拆箱 | `PyLong` digits → int64 | **不存在**（本来就是 int64） |
| 计算 | 1 周期 | 1 周期 |
| 装箱 | 分配 `PyLongObject`（~30 周期） | **不存在** |
| 结果存放 | 压栈（指针） | 写 VM 寄存器 |
| 溢出检查 | 需检查（大整数提升） | 默认 trap，单条 `jo` |

**X 少了「拆箱 + 装箱」两步，占 CPython 该指令耗时的 70% 以上。**

这不是实现技巧的差距，是语言设计的差距。**静态类型 + 值语义 = 解释器的性能下限比动态语言高一个数量级。**

### 2.3 但有一个前提：不能全靠装箱的通用 Value

如果 X 的解释器用统一的 `Value` 结构（tag + union），就会把优势丢掉一半：

```c
// 坏：每个值都要判 tag
struct Value { uint8_t tag; union { int64_t i; double f; void *p; }; };
Value add(Value a, Value b) {
    if (a.tag != TAG_INT || b.tag != TAG_INT) return slow_path(a, b);
    return (Value){ .tag = TAG_INT, .i = a.i + b.i };
}
```

正确的做法见 §3.5：**用类型化的字节码指令**（`ADD_I64` / `ADD_F64` / `ADD_ANY` 分开），让「通用 Value」只出现在真正需要动态的场景（`dyn Trait`、反射）。

编译期类型已知 → 字节码指令带类型 → 解释器循环里没有类型分支。**这是 X 解释器能达到 native 的 1/5 而不是 1/50 的根本原因。**

## 3. 七层优化

按 ROI 排序。每层给出实测/估算收益、实现成本、代价。

### 3.1 L1 · 直接线程化分派

**收益**：1.5 ~ 2.5×（估算，基于失败率从 90% 降到 60% 推算）
**成本**：各平台一套 `DISPATCH` 宏，约 200 行
**代价**：无

#### 3.1.1 标准实现（GCC/Clang）

```c
// interp.c —— 核心循环
#if defined(__GNUC__) || defined(__clang__)
  #define DISPATCH() goto *op_table[code[ip++]]
#else
  #define DISPATCH() goto dispatch_switch
#endif

void run(Frame *f) {
    register uint8_t *ip = f->code;
    register uint64_t *reg = f->regs;      // 寄存器文件基址

    DISPATCH();

L_ADD_I64:
    { uint16_t d = code[ip] | code[ip+1] << 8;
      uint16_t a = code[ip+2] | code[ip+3] << 8;
      uint16_t b = code[ip+4] | code[ip+5] << 8;
      ip += 6;
      int64_t r;
      if (__builtin_add_overflow((int64_t)reg[a], (int64_t)reg[b], &r))
          goto overflow_trap;                // 内建，编译为单条 jo
      reg[d] = (uint64_t)r; }
    DISPATCH();
...
}
```

两个细节必须注意：

1. **`register` 关键字**：让 `ip` 和 `reg` 尽量驻留寄存器。GCC 会自己判断，但显式声明在解释器循环里通常有帮助。
2. **操作数一起取**：`IP + 2 + 2 + 2` 的三次读取是三条独立的字节加载，可以合并为一次 6 字节读取再移位（x86 上允许非对齐读）：

```c
uint64_t ins = *(uint64_t *)(ip) & 0xFFFFFFFFFFFF;   // 一次读 6 字节
d = ins & 0xFFFF; a = (ins >> 16) & 0xFFFF; b = ins >> 32;
```

#### 3.1.2 内联线程化（inline threading）

进一步：把下一条指令的完整处理代码**复制**到当前指令末尾（`OP1; OP2` 合并），彻底消除一次分派。这与超指令（§3.3）的区别是内联线程化在代码生成期做、超指令在字节码层做，两者可叠加。

#### 3.1.3 Windows / MSVC 的替代方案

MSVC 不支持标签地址运算。三条路，按推荐度排：

| 方案 | 说明 | 收益 |
|---|---|---|
| **用 Clang 编译解释器** | Windows 上 `--interp-cc=clang` 提供 Clang 编译的解释器核心（Clang 支持 GNU 扩展） | 完整收益 |
| 尾调用分派 | 每条指令实现为一个 `static` 函数，`return next_ins();`，依赖编译器做兄弟调用优化（MSVC 目前不可靠） | 部分 |
| 保持 switch | MSVC 的 switch 分派本身编译质量较高 | 无 |

**[裁决]** 解释器核心用 C 写，但**支持多个编译器后端**，选能产出最优分派的那个。编译器本体的自举与解释器核心的编译工具链解耦：解释器核心只有 1 万行 C，允许用 Clang/GCC 编译，不参与「自举」要求。

### 3.2 L2 · 寄存器式字节码

**收益**：执行指令数 **-46%**，耗时 **-32.3%**（Shi et al., ACM TACO 2008 实测，AMD64）
**成本**：字节码生成器设计（分配虚拟寄存器、消除冗余 load/store），约 3000 行
**代价**：字节码体积 **+26%**（同来源实测）

#### 3.2.1 为什么指令数少一半

栈式机里，`c = a + b + d` 是：

```
LOAD_LOCAL  a     ; 压栈
LOAD_LOCAL  b     ; 压栈
ADD               ; 弹两个、压一个
LOAD_LOCAL  d     ; 压栈
ADD
STORE_LOCAL c     ; 弹一个
```
7 条指令，其中 4 条是纯搬运。

寄存器式：
```
ADD  r0, a, b     ; 三地址
ADD  c, r0, d
```
2 条指令。**指令数从 7 降到 2，减少 71%。** 平均下来就是 Shi 实测的 46%。

关键收益不只是「少了 5 次分派」，而是**操作数栈的内存流量消失了**。栈式机每条 ADD 都要读写内存数组；寄存器式机的操作数是 VM 寄存器（映射到 C 的局部数组，编译器会把热点部分放进物理寄存器）。

#### 3.2.2 X 的字节码格式

固定 6 字节定长指令（1 字节操作码 + 最多 3 个 2 字节寄存器/常量槽）：

```
 7    6 .. 0
┌──────┬──────────────────────────────────────────┐
│ 0xFF │ opcode                                   │  字节 0
├──────┴──────────────┬───────────────────────────┤
│ dst (16 bit)        │ 字节 1-2                  │
├─────────────────────┼───────────────────────────┤
│ srcA (16 bit)       │ 字节 3-4                  │
├─────────────────────┼───────────────────────────┤
│ srcB (16 bit)       │ 字节 5-6                  │
└─────────────────────┴───────────────────────────┘
```

- 定长 → 取指无需解码长度，`ip += 6` 是常量。
- 16 位槽位 → 每帧最多 65536 个 VM 寄存器（远超实际需要），槽位也可指向常量池。
- 6 字节非对齐读 → x86 允许；ARM64 用两次 4 字节读 + 拼接。

指令集（32 位操作码空间，实际用约 140 条）：

| 组 | 指令 | 说明 |
|---|---|---|
| 搬移 | `MOV`, `MOVI`（立即数）, `MOVK`（常量池） | |
| 整数 | `ADD_I64`, `SUB_I64`, `MUL_I64`, `DIV_I64`, `REM_I64` | 溢出默认 trap |
| 整数扩展 | `ADD_I64_W`（wrapping）, `ADD_I64_S`（saturating） | 后缀区分语义 |
| 浮点 | `ADD_F64`, `MUL_F64`, `DIV_F64`, `NEG_F64`, `CMP_F64` | |
| 定点/小整型 | `ADD_I32`, `ADD_I8`, `ADD_U8` … | 按位宽分开，避免截断 |
| 位运算 | `AND`, `OR`, `XOR`, `SHL`, `SHR`, `NOT` | |
| 比较 | `CMP_I64`, `CMP_F64`, `TEST_NULL`, `TEST_TRUE` | 直接产出条件码到 VM 标志位 |
| 分支 | `JMP`, `JMP_IF`, `JMP_IF_NOT`, `JMP_TABLE`（switch） | |
| 调用 | `CALL_DIRECT`, `CALL_INDIRECT`, `RET`, `TAILCALL` | |
| 栈帧 | `ENTER`, `LEAVE` | 帧的分配与释放 |
| 对象 | `NEW`, `FIELD_GET`, `FIELD_SET`, `ARRAY_GET`, `ARRAY_SET` | 带内联缓存槽 |
| 引用计数 | `ARC_INC`, `ARC_DEC`, `ARC_MOVE` | 只在 L2 类型上出现 |
| 类型 | `CAST`, `INSTANCEOF`, `CHECK_CAST` | |
| 异常 | `THROW`, `TRY_BEGIN`, `TRY_END`, `RETHROW` | 见 [06](06-异常与诊断.md) |
| 杂项 | `NOP`, `UNREACHABLE`, `BREAKPOINT` | |

#### 3.2.3 虚拟寄存器分配

这是 L2 的主要工作量。算法：

1. **表达式树 → 三地址码**：每个中间结果分配一个新虚拟寄存器（无限寄存器假设）。
2. **活跃区间分析**：算出每个虚拟寄存器的定义点到最后使用点。
3. **线性扫描分配**：复用已死的寄存器槽。栈式机的 4 条 move 指令就是在这里被消掉的。
4. **常量传播 + 折叠**：`ADD_I64 r0, r1, #5` 里 `#5` 变成常量池槽或立即数。
5. **窥孔优化**：`MOV r1, r0; ADD r2, r1, r3` → `ADD r2, r0, r3`。

分配后的槽数通常等于「表达式最大嵌套深度 + 局部变量数」，实际程序里很少超过 64。这意味着**寄存器文件可以整个放进 L1 缓存**，这是寄存器式机的隐性性能来源。

### 3.3 L3 · 超指令与指令复制

**收益**：与线程化合计 **1.75 ~ 3.16×**（Ertl & Gregg 2006 实测，Pentium 4 / Athlon 时代 CPU）
**成本**：字节码分析 + 重写 pass，约 1200 行
**代价**：字节码体积 +10% ~ 20%

#### 3.3.1 超指令（superinstruction）

统计高频的**指令对**，合并为一条新指令：

```
ADD_I64  r0, r1, r2      ┐
FIELD_GET r3, r0, #8     ┘  →  ADD_I64_FIELD_GET  r3, r1, r2, #8
```

合并后省掉一次分派、一次寄存器读（中间结果不落地）。

选择哪些组合：**运行时统计**。解释器带一个可选的 「指令对直方图」（`--profile=pairs`），跑测试集后按频率排序，取前 30~60 对固化成超指令。这是 Ertl & Gregg 的方法，也是 CPython 3.11 的做法（`LOAD_FAST__LOAD_FAST` 等）。

X 的初始超指令集（基于对常见模式的预判，实测后调整）：

| 超指令 | 来源 | 典型场景 |
|---|---|---|
| `LOAD_FAST__LOAD_FAST` | `MOV; MOV` | 双操作数准备，最高频 |
| `LOAD_FAST__LOAD_CONST` | `MOV; MOVK` | 与常量运算 |
| `ADD__STORE` | `ADD; MOV` | `x += i` |
| `CMP__JMP_IF` | `CMP; JMP_IF` | 所有循环条件 |
| `FOR_ITER` | `MOV; CMP; JMP_IF; ADD` | `for i in 0..n`（迭代器协议专用） |
| `CALL__RET_FAST` | `CALL; RET` | 叶子函数调用 |
| `ARRAY_GET__ADD` | `ARRAY_GET; ADD` | 数组累加（数值代码最高频） |
| `FIELD_GET__FIELD_GET` | `FIELD_GET; FIELD_GET` | `p.x + p.y` |

#### 3.3.1a 实现超指令时唯一真正困难的地方：跳转重映射

超指令的**合并逻辑本身是平凡的**（识别相邻两条指令、改写 op、丢掉下一条），难的是它改变了指令的绝对下标，而所有跳转操作数都是绝对下标。

这里有两个独立的坑，第二个尤其隐蔽：

**坑一：段内重映射。** 合并掉第 $i+1$ 条后，段内所有后续指令前移一位，段内跳转目标必须同步改。这一层直觉上容易想到。

**坑二：段间挤压。** 如果按「从后往前」逐函数合并（这是必须的顺序，因为合并会让后续数据前移，从后往前才不用反复修正已处理过的函数偏移），那么处理前一个函数时，它会把自己之后的所有函数**整体挤动** `saved` 条。

于是：前面已经合并好的函数，它内部的跳转操作数是「当时正确的绝对值」，现在整段挪了位置，操作数就全错了。

```
pass 1  合并 factorial  →  JUMP_IF_FALSE -> 0011  ✓（此刻正确）
pass 2  合并 square     →  factorial 和 main 整体前移 1 条
                           JUMP_IF_FALSE 本身挪到 0007
                           它要跳的 LOAD_LOAD 挪到 0010
                           但操作数还是 0011  ✗（跳过了一条指令）
```

**这个 bug 的症状极具误导性**：不报错、不崩溃，只是算错。因为跳转跳过头之后，栈上少压了一个操作数，解释器读到的是上一次残留的值 —— 阶乘算出 `720` 变成别的数，而类型完全合法。单函数测试全绿，只有多函数程序出错。

修法：`memmove` 搬完尾部数据之后，必须再扫一遍尾部区域，把所有落在该区域内的跳转操作数减去 `saved`。这两步是**成对**的，漏一半就等于白搬。

这条经验的推广：**任何「就地压缩指令流」的优化，都必须同时处理（a）指令自身的移动、（b）所有引用指令下标的操作数。** 引用可能藏在不止一种 opcode 里（X 有 `JUMP` / `JUMP_IF_FALSE` / `JUMP_IF_TRUE` / `LT_JUMP_FALSE` 四种），漏一种就是上面的静默错误。

X 的实测数据（`tools/bench.sh --quick` 与 `--quick --nosuper` 做紧邻 A/B，交替测量各 5 轮取最小值）：

| 基准 | 关闭超指令 | 开启超指令 | 收益 |
|---|---|---|---|
| 整数循环 3000 万次 | 1131 ms | 682 ms | **1.66×** |
| fib(33) 700 万次调用 | 240 ms | 176 ms | **1.36×** |

循环收益远高于递归，符合预期：循环体里超指令密集命中，而 fib 的开销主要由建帧决定，超指令帮不上。

合并 pass 的**实测收敛过程**（一个 3000 万次的循环，循环体 12 条字节码）：

| 轮次 | 循环体 | 命中 | 效果 |
|---|---|---|---|
| 原始 | 12 条 | — | `LOAD;LOAD;ADD;PUSH;MOD;DUP;STORE;POP;LOAD;PUSH;ADD;DUP;STORE;POP;JUMP` |
| 第 1 轮 | 8 条 | `LOAD_LOCAL+LOAD_LOCAL`、`DUP+STORE_LOCAL`、`LOAD_LOCAL+PUSH_I64` | 两两合并 |
| 第 2 轮 | 7 条 | `DUP_STORE+POP`、`ADD+DUP_STORE_POP`、`MOD+DUP_STORE_POP` | 三合一 |

第 2 轮的关键在于**必须反复跑到收敛**。`ADD; DUP_STORE; POP` 想合成一条 `ADD_STORE`，但第一轮扫到 `ADD` 时它的下一条还是 `DUP_STORE`，规则配不上；只有等 `DUP_STORE+POP` 先合成 `DUP_STORE_POP`，下一轮才能配上。

所以合并逻辑写成了「扫到不再变化为止」的循环，而不是手工给规则排优先级。好处是：新增规则不需要考虑与已有规则的先后关系，收敛结果自然是最优的。代价是最坏情况 $O(n^2)$，但实测 3~4 轮就收敛。

**一个反直觉的教训：先合并出来的超指令会成为下一轮更好的配对对象。** `DUP; STORE_LOCAL` 合成 `DUP_STORE` 之后，产生了一个原本不存在的形态 `DUP_STORE; POP`，而它的语义恰好等价于一条 `STORE_LOCAL` —— 3 条变 1 条。如果在第一轮就直接把 `DUP; STORE_LOCAL; POP` 写成一条手写规则，反而做不到（规则要匹配三个位置，与「只匹配相邻两条」的框架不兼容）。**多轮简单规则胜过单轮复杂规则。**

#### 3.3.2 指令复制（replication）

Ertl & Gregg 的进阶技巧：把高频指令**复制多份**，散布在不同的上下文里。

原理：BTB 是「按静态指令地址索引」的。如果只有一个 `L_MOV` 标签，所有 MOV 都跳到那里，历史记录必然混乱。如果有 4 个 `L_MOV_0` / `L_MOV_1` / `L_MOV_2` / `L_MOV_3`，按前驱指令分配，则每个副本的历史更稳定。

```c
L_ADD:
    ...
    // 按前一指令选择不同的 DISPATCH 目标
    DISPATCH_REPLICATED();
L_MOV_0: ...; DISPATCH();
L_MOV_1: ...; DISPATCH();
L_MOV_2: ...; DISPATCH();
L_MOV_3: ...; DISPATCH();
```

收益：失败率从 63% 降到约 20%。代价：代码体积 ×2 ~ ×4，i-cache 压力增加。

X 的取舍：**只对前 20 条高频指令做 2 路复制**。更多复制会挤爆 i-cache（32 KB L1i 只能放约 8000 条 x86 指令），得不偿失。

### 3.4 L4 · 栈缓存（stack caching）

**收益**：1.1 ~ 1.3×（估算）
**成本**：约 600 行，但**让字节码生成器复杂度翻倍**
**代价**：调试困难

思想：栈顶 N 个元素不放在内存数组里，而是放在 C 的局部变量（物理寄存器）里。

```c
// 状态机：不同指令假设不同的缓存深度
// 例如 ADD 有两个变体：
//   ADD_11  —— 两个操作数都在寄存器里（最快）
//   ADD_10  —— 一个在寄存器，一个在内存
//   ADD_00  —— 都在内存
```

这是 V8 Ignition 之前的策略，也是 Smalltalk 系 VM 的经典技术。

**[裁决]** X 的解释器**不做栈缓存**。理由：§3.2 已经用寄存器式字节码消掉了操作数栈，栈缓存优化的对象（栈流量）在 X 里已经不存在。这两者是替代关系，不是叠加关系。**这是寄存器式机相对栈式机的第二个好处——它让你不必写最复杂的那层优化。**

### 3.5 L5 · 值表示：NaN boxing 与未装箱数值

**收益**：1.2 ~ 1.5×（估算，主要是缓存命中率）
**成本**：约 400 行
**代价**：调试器需要解码，指针只支持 48 位

#### 3.5.1 问题

如果 VM 寄存器是统一的 8 字节槽，那么一个 `Int` 值占用 8 字节（好），但一个 `Float` 也占 8 字节（好），而一个 `Bool` 占 8 字节（浪费），一个 `String` 占 8 字节（存指针，好）。问题是：**解释器不知道槽里是 1 还是 1.0**。

两种解法：

**方案 A：按指令类型解释**（X 采用）
因为字节码是类型化的（`ADD_I64` vs `ADD_F64`），解释器**天然知道**槽里是什么。VM 寄存器就是一个纯 `uint64_t` 数组，指令自己决定怎么解释。

```c
reg[d] = (uint64_t)((int64_t)reg[a] + (int64_t)reg[b]);   // ADD_I64
reg[d] = f64_bits(f64_of(reg[a]) + f64_of(reg[b]));       // ADD_F64
```

零开销，零编码。**这是类型化字节码带来的第三个红利。**

**方案 B：NaN boxing**（仅用于 `dyn Trait` 与反射场景）
需要「一个槽能装任意类型」时（异构容器、动态调用），用 NaN 空间编码：

```
IEEE-754 double 的 NaN 空间：
  0x7FF8_0000_0000_0000 ~ 0x7FFF_FFFF_FFFF_FFFF  是 NaN（sign=0）
  0xFFF8_... 同理（sign=1）

取 0x7FFC 作为 tag 前缀，低 48 位存指针或小整数：
  [0x7FFC][48-bit payload]
  payload 的 bit 48-50 表示具体类型：0=Ptr, 1=Int32, 2=Bool, 3=Null
```

好处：`Float` 无需装箱（直接是 double 位模式），`Value` 仍是 8 字节。
坏处：指针只支持 48 位（x86-64 用户态实际只用 47 位，够用；ARM64 也够用）。

**[裁决]** 只在 `dyn` 与反射路径用 NaN boxing，静态类型路径不用。两套表示之间在 `CAST` 指令处转换。

#### 3.5.2 小整数与字符串驻留

- `-128 ~ 127` 的整数直接编码进 NaN box 的 payload（不分配）。
- 短字符串字面量在编译期驻留到只读段，运行时只是指针。
- 这两个技巧提升的是分配密集场景，实测可减少 10%~15% 的分配次数（估算）。

### 3.6 L6 · 内联缓存与快速化（quickening）

**收益**：CPython 3.11 实测单项 10% ~ 25%（PEP 659 官方数字）
**成本**：约 800 行
**代价**：字节码在运行时被改写，调试时看到的可能与源码不一致（需 `--no-quicken`）

CPython 的经验适用性说明：X 是静态类型，`FIELD_GET` / `CALL_INDIRECT` 的**目标在多数情况下编译期已知**，根本不需要内联缓存。内联缓存只在这两处有价值：

| 场景 | 为什么需要 IC | 缓存什么 |
|---|---|---|
| `dyn Trait` 方法调用 | vtable 位置运行时才定 | 上一次的 (具体类型 → 函数指针) |
| 泛型未单态化的路径 | 同上 | 同上 |
| 反射访问字段 | 字段偏移运行时查 | (类型 → 偏移) |
| `Array[T]` 的元素类型擦除处 | 需要判元素是装箱还是未装箱 | 一次判定的结果 |

```c
// CALL_INDIRECT 的内联缓存
typedef struct {
    uint32_t cached_type_id;
    void    *cached_fn;
    uint32_t hit_count;
} InlineCache;

case OP_CALL_INDIRECT: {
    InlineCache *ic = &frame->caches[code[ip+...]];
    uint32_t tid = obj_type_id(reg[recv]);
    if (ic->cached_type_id == tid) {          // 命中：无查表
        ((Fn)ic->cached_fn)(reg, argc);
    } else {                                   // 未命中：慢路径 + 更新缓存
        ic->cached_fn = resolve_vtable(reg[recv], slot);
        ic->cached_type_id = tid;
        ((Fn)ic->cached_fn)(reg, argc);
    }
    DISPATCH();
}
```

**快速化**（quickening）的实现：字节码数组里每个指令槽预留 2 字节缓存区，首次执行时写入类型 ID 与偏移。`FIELD_GET` 从「按名字查哈希表」变成「按偏移直接读」。

X 的快速化阈值：**8 次**（与 CPython 3.11 一致）。低于此不值得改写。

### 3.7 L7 · 调用优化

**收益**：调用密集代码 1.3 ~ 1.8×（估算）
**成本**：约 700 行
**代价**：栈帧布局更复杂

函数调用在解释器里是重灾区：

```
朴素实现：
  1. 分配新 Frame 对象（堆分配，~40 周期）
  2. 复制实参到新帧的寄存器文件
  3. 保存 ip / fp 到调用栈
  4. 递归调用 run()（C 栈增长）
```

四条优化：

| 技术 | 做法 | 收益 |
|---|---|---|
| **帧池** | Frame 对象从空闲链表取，不 malloc | 省 40 周期/次 |
| **内联帧** | 子帧的寄存器文件紧接在父帧之后分配（同一块连续内存），`fp += frame_size` 即可 | 省一次分配 + 提升局部性 |
| **参数直接传递** | 实参直接在寄存器文件里排好（调用约定规定前 N 个参数在调用者的 r0..rN），子帧直接读，不复制 | 省 k 次复制 |
| **不递归进 C** | `CALL` 不调用 `run()`，而是把新帧设好，`DISPATCH()` 继续在同一 C 帧里跑 | 消除 C 栈增长（这是 CPython 3.11 的关键优化，递归 fibonacci 提速 1.7×） |

最后一项最重要。CPython 3.11 官方数据：因为不再递归进 C、且帧对象按需创建，`fibonacci` 提速 **1.7×**，深度递归不再受 C 栈限制。

X 的实现：

```c
case OP_CALL_DIRECT: {
    Frame *callee = frame_alloc(f->pool);          // 池化，非 malloc
    callee->parent = f;
    callee->code   = fn->code;
    callee->regs   = f->regs + f->frame_size;      // 内联帧，连续内存
    memcpy(callee->regs, &reg[argbase], fn->nparams * 8);   // 只复制实参
    f = callee;
    ip = callee->code;
    DISPATCH();
}
case OP_RET:
    { uint64_t ret = reg[0];
      Frame *caller = f->parent;
      frame_free(f->pool, f);
      f = caller; reg = f->regs; ip = f->ip;
      reg[f->ret_slot] = ret; }
    DISPATCH();
```

`frame_size` 在编译期算出（= 该函数最大虚拟寄存器数），因此内联帧分配就是一次指针加法。

### 3.8 汇总表

| 层 | 技术 | 累计收益（估算） | 工作量（行） | 是否必做 | 当前状态 |
|---|---|---|---|---|---|
| L1 | 直接线程化分派 | 1.8× | 200 | **必做** | 未做（switch 分派） |
| L2 | 寄存器式字节码 | 2.6× | 3000 | **必做** | 未做（栈式） |
| L3 | 超指令 + 复制 | 3.5× | 1200 | **必做** | **部分完成**：6 对超指令已上线，实测 1.66× |
| L4 | 栈缓存 | — | — | **不做**（被 L2 取代） | — |
| L5 | 未装箱数值 + NaN boxing | 4.5× | 400 | **必做** | 部分完成：类型化字节码已做，Value 仍是 tagged union |
| L6 | 内联缓存 + 快速化 | 5.0× | 800 | 必做（仅 dyn 路径） | 未做 |
| L7 | 调用优化 | 6.0× | 700 | 必做 | 未做（帧是数组下标，未池化） |

合计约 **6300 行**，换来相对朴素栈式解释器 **6 倍**的提升。对比：CPython 用 3 万行 C 实现（不含标准库）才达到本文 §0.2 表中那一列。

**P0 的实测位置**：整数循环 3000 万次约是 C `-O0` 的 **5.5×**（L3 部分完成后从 11× 降下来）。这个数字已经接近 L3 的目标，但距离「追平 C -O0」还需要 L2 + L5 + L7。

一个重要的实测发现修正了本文的隐含假设：**C `-O2` 在真串行循环上没有比 `-O0` 快**（3000 万次带取模的循环：`-O0` 102ms / `-O2` 88ms，差距在噪声内）。gcc 的加速主要来自向量化等并行化手段，而带循环携带依赖的算术链无法向量化。这意味着「追平 C `-O0`」和「追平 C `-O2`」在这个基准上难度接近 —— 原来以为要跨过一个大台阶，实际只要跨过一个小台阶。

### 3.9 AOT 后端（C 后端）的实现与实测

**做法**：不自己发机器码，而是把每条字节码翻译成一条 C 语句，交给本机 gcc/clang 编译。理由见 02 §5.3——自研汇编器和链接器是数万行的坑，而 C 编译器已经在我们需要的三个平台上都存在。

关键设计：**栈深静态化**。字节码是栈式的，但任意位置的栈深可以从入口做一次工作队列传播算出来。于是生成的代码写 `s[3] = s[2] + s[1]` 而不是 `s[sp++] = ...`，常量下标让 gcc 能做别名分析和寄存器分配。

#### 3.9.1 实测数据

3000 万次整数循环（同一台机器，交替测量 9 轮取最小值）：

| 实现 | 耗时 | 相对 C -O0 |
|---|---|---|
| C `-O2` | 63 ms | 0.63× |
| C `-O0` | 100 ms | 1.0× |
| **X AOT** | **300 ms** | **3.0×** |
| X 解释器 | 447 ms | 4.5× |

**AOT 相对解释器提速 1.46×**，相对 C -O0 的差距从 4.5× 缩到 3.0×。

fib(32)（约 570 万次调用）：解释器 113 ms → AOT 71 ms，**1.59×**。

#### 3.9.2 为什么只有 1.5×，而不是接近 1×

这是本节最重要的结论，也是一个被实测推翻的初始预期。

直觉上「把字节码翻译成 C，让 gcc -O2 优化」应该能拿到接近原生的性能。实测只有 1.5×，原因是**瓶颈不在生成质量，而在「用数组模拟栈」这个模型本身**。

验证方法：手工用同样的 `V` 结构（tag + union，16 字节）写一个纯 C 的 3000 万次循环，不做任何字节码翻译，直接写了 if/else 和数组下标。结果 111 ms——只比生成的代码快 12%。

也就是说：**只要值必须存在于内存中确定的槽位上，每次算术操作就逃不掉一次 16 字节 load 加一次 store**。gcc 的 SRA（标量替换）能优化固定大小的局部数组，但值栈是个「运行时才知道用多少」的共享数组，而且叶子函数的 `s` 还会被传给别处，优化器必须保守。

试过但无效的手段（都实测过，没有可测量的收益）：

| 尝试 | 结果 | 原因 |
|---|---|---|
| 叶子函数加 `__restrict` | 无变化 | 别名分析不是瓶颈 |
| 叶子函数声明 `V s[static N]` | 无变化 | 形参仍退化为指针，槽仍在内存 |
| 去掉运行时位置追踪 `g_line` | 5% | 占比小，且错误信息需要它 |
| 去掉字符串 retain/rel | 无变化 | 不是热路径 |

**要让 AOT 接近原生，需要做寄存器分配**（把值栈的槽映射到物理寄存器，而不是内存数组）。那是完整的编译器后端，属于 L2 层（寄存器式字节码）的工作，不在 C 后端的定位内。C 后端的定位是「用最小代价拿到正确性与跨平台」，性能 1.5× 是它的合理上限。

这个结论同样修正了 §3.8 汇总表的推论：L2（寄存器式字节码）的价值不只是让解释器快 2.6×，它**同时是 AOT 突破 1.5× 天花板的前提**——两档共享同一份寄存器式 IR 时，AOT 才能真正受益于 gcc 的寄存器分配。

## 4. 关键架构决策：字节码即 Mid IR

### 4.1 问题的提出

双层执行（解释 + AOT）的最大成本不是写两遍，而是**两套语义必须同步**。如果解释器吃「字节码」、AOT 吃「AST」或「另一套 IR」，那么每加一个语言特性都要改两处，且两处的语义漂移极难察觉。

### 4.2 解法

**寄存器式字节码就是 Mid IR 的结构化、线性化形式。** 两者的对应关系：

| 字节码 | Mid IR |
|---|---|
| VM 寄存器 `r0..rN` | SSA 值（活跃区间已分析） |
| `ADD_I64 r0, r1, r2` | `%3 = add i64 %1, %2` |
| `JMP_IF r0, L` | `br i1 %0, label %L, label %fall` |
| `CALL_DIRECT fn` | `call @fn(...)` |
| 定长 6 字节编码 | 结构化对象 |

字节码只是 Mid IR 的**序列化形式**（为了让解释器能线性扫描）。因此：

```
                    ┌──→ 解释器（直接执行）
Mid IR ──序列化──→ 字节码 ─┤
                    └──→ 反序列化 → 优化 pass → 代码生成 → 机器码
```

**AOT 只是「对同一份字节码跑优化 pass 然后生成机器码」，不需要独立前端。**

### 4.3 这带来的四个红利

| 红利 | 说明 |
|---|---|
| 语义天然一致 | 解释器和 AOT 看的是同一份指令流，不存在「某特性只在一档实现」 |
| 差分测试免费 | 同一字节码两条路径跑，输出必须一致——**原设计的「三档一致」验证手段完整保留** |
| 快速化可复用 | 解释器的内联缓存积累的类型信息，可以作为 AOT 的 profile 指导优化（PGO） |
| 增量编译更简单 | 改一个函数只重生成该函数的字节码段，解释模式和 AOT 都只重做这一段 |

第二个红利尤其重要。上一版设计里「放弃解释器」导致失去了自动验证手段，这个设计把它拿回来了，而且更强：`--verify=diff` 可以逐函数对比两条路径的输出与副作用。

### 4.4 代价

一个真实代价：**为解释器优化的字节码，对 AOT 未必最优。**

例如超指令 `ARRAY_GET__ADD` 对解释器是纯收益（省一次分派），对 AOT 是噪音（优化 pass 会在内联后自己合并）。解法：**超指令只在解释器加载字节码时合成，不写回文件。**

```
.xbc 文件里存的是基础寄存器字节码（140 条指令）
   │
   ├─→ 解释器加载 → 超指令合成 pass（按 profile 选组合）→ 执行
   └─→ AOT 加载 → 直接进优化 pass（不需要超指令）
```

这样两条路径各自最优，而源头的字节码是同一份。

## 5. 可选第三档：复制-补丁 JIT

如果解释器还不够快，下一步不是写优化 JIT，而是**复制-补丁**（copy-and-patch）。这是 V8 Sparkplug、CPython 3.13 JIT 用的方案。

### 5.1 原理

编译期用 LLVM 把每个字节码指令编译成一段机器码模板（stencil），存成字节数组。运行时：

```
1. mmap 一页可执行内存
2. 对每条字节码：memcpy 对应 stencil 进去
3. 打补丁（立即数、寄存器偏移、跳转目标）
4. mprotect 为可执行
5. 把函数入口指向这段代码
```

**没有寄存器分配，没有优化 pass，纯粹是「拼装」。**

### 5.2 成本数据

| 指标 | 数值 | 来源 |
|---|---|---|
| 每架构模板数 | 约 80 ~ 140 个 | Mochi MEP-22（基于同一技术） |
| 单函数编译时间 | **< 1 ms**（1000 条指令） | 同上；V8 Sparkplug 为微秒级 |
| 生成代码质量 | 约等于解释器（略好） | 同上 |
| 触发阈值 | 10000 次调用 | 同上 |

### 5.3 为什么这个方案对 X 特别合适

复制-补丁**要求栈帧布局与解释器完全一致**（这样出问题能原地退回解释器，不需要栈重建）。而 X 的字节码已经是寄存器式、帧布局编译期确定——**这正是它要的前提**。

相比之下，写一个优化 JIT（Turbofan/C2 级别）是 10 人年，且需要 SSA 构建、逃逸分析、去优化（deopt）基础设施。**复制-补丁是 3 人月。**

**[裁决]** 复制-补丁列为 P5 可选项，不列入 1.0 范围。理由：解释器做到 6 倍提升后，多数场景已够用；而 AOT 已经覆盖了性能敏感场景。真正需要「长时间运行的动态生成代码」时才值得做。

## 6. 分场景的目标与验证

### 6.1 目标表

| 基准 | 内容 | CPython 3.12 | X 解释器目标 | X AOT 目标 |
|---|---|---|---|---|
| `fib(30)` 递归 | 调用密集 | 1.9 s | **0.30 s** | 0.035 s |
| `nbody` | 浮点 + 对象 | 0.55 s | **0.09 s** | 0.012 s |
| `sieve(10^8 bits)` | 整数 + 数组 | 8.2 s | **1.4 s** | 0.22 s |
| `matmul 512³` | 三重循环 | 6.1 s（纯 Python） | **1.1 s** | 0.05 s（含 BLAS 0.01 s） |
| `json parse 50MB` | 字符串 + 对象分配 | 1.1 s | **0.22 s** | 0.09 s |
| `dict 10^7 次查` | 哈希表 | 4.3 s | **0.75 s** | 0.35 s |

（CPython 一列为公开基准的常见量级，具体版本有 ±20% 波动；X 两列为设计目标，需实测校准。**首次可用版本必须跑这六个基准，实测值写回本表。**）

### 6.2 验证手段

| 手段 | 目的 |
|---|---|
| 差分测试（`--verify=diff`） | 每个测试程序在解释器与 AOT 下输出必须逐字节一致 |
| 指令计数（`--profile=ops`） | 验证寄存器式字节码的指令数确实比栈式少 40%+ |
| 分派统计（`--profile=dispatch`） | 统计 BTB 失败率（用 `perf stat` 的 `branch-misses`） |
| 超指令命中率（`--profile=pairs`） | 超指令覆盖率应 > 60% 的执行指令 |
| 分配计数（`--profile=alloc`） | 数值代码的分配次数应为 0（验证未装箱） |
| 与 CPython 对跑 | 同一算法两版实现，比值写进基准表 |

### 6.3 必须设的护栏

| 护栏 | 理由 |
|---|---|
| 解释器核心代码不超过 1.2 万行 | 超过说明在做 JIT 的事，停手 |
| 单条指令的 C 代码不超过 25 行 | 否则 i-cache 装不下，分派收益被吃掉 |
| 启动到执行首条用户指令 < 3 ms | 否则 `x run` 的体验退化 |
| 字节码加载（mmap + 校验）< 1 ms（10 万条指令） | 否则每次运行都在等加载 |
| `--no-quicken` 下所有测试必须通过 | 快速化是优化，不能是语义依赖 |

## 7. 实现顺序

依赖关系严格，不能跳。

| 步 | 内容 | 前置 | 估时 | 交付判据 |
|---|---|---|---|---|
| 1 | 栈式字节码 + switch 分派 | 前端可用 | 3 周 | 能跑测试集，建立正确性基线 |
| 2 | 寄存器式字节码生成器（虚拟寄存器分配） | 步 1 | 6 周 | 指令数比步 1 少 40%+ |
| 3 | 直接线程化分派 | 步 2 | 1 周 | `fib(30)` 提速 > 1.5× |
| 4 | 未装箱数值 + 类型化指令 | 步 2 | 2 周 | 数值循环零分配 |
| 5 | 调用优化（帧池 + 内联帧 + 不递归） | 步 2 | 2 周 | `fib(30)` 再提速 > 1.5× |
| 6 | 超指令（先手工选 12 对） | 步 3 | 1 周 | 超指令覆盖 > 40% 执行指令 |
| 7 | 指令复制（前 20 条 ×2 路） | 步 6 | 1 周 | `perf stat` 分支失败率下降 |
| 8 | 内联缓存 + 快速化（仅 dyn 路径） | 步 4 | 3 周 | dyn 调用提速 > 30% |
| 9 | 超指令自动挖掘（profile 驱动） | 步 6 | 2 周 | 覆盖率 > 60% |
| 10 | 差分测试基础设施 | 步 1 + AOT 可用 | 2 周 | CI 全绿 |

合计约 **23 周**（5.5 个月）。其中步 2 是最大块，也是决定成败的一块。

**关键提醒**：步 1 的栈式实现不要删。它是步 2 的对照基准（验证寄存器式生成的语义正确），也是差分测试的第三方参照。三份实现（栈式、寄存器式、AOT）互相对照，比两份更容易定位 bug。

## 8. 反面清单：不要做的事

| 不做 | 理由 |
|---|---|
| 用 AST 树遍历作为最终解释器 | 慢 3~5 倍，且无法复用为 AOT 输入。只可作 P0 临时实现 |
| 栈式字节码 + 栈缓存 | 寄存器式已消除栈流量，栈缓存是重复投入 |
| 通用 `Value` 结构走所有路径 | 丢掉静态类型优势，退化成 CPython |
| 每个值都引用计数 | 数值路径上 ARC 是纯浪费。`Int`/`Float` 是值语义，无 RC |
| 逐指令 profile 驱动优化（trace JIT） | 实现复杂度高（追踪循环、侧退出），收益不如复制-补丁 |
| 在解释器里做内联 | 内联是 AOT 的事。解释器做内联 = 偷偷实现 JIT |
| 为解释器单独写一套语义检查 | 必须共用前端，否则语义漂移 |
| 优化到 native 的 1/2 以上 | 不可能。到这个程度应该用 AOT |
| 过早优化字节码体积 | 解释器性能看分派次数，不看字节数 |

## 9. 与旧决策的关系

本文推翻了 [05](05-路线图与风险.md) 中「放弃解释执行」的裁决。变更记录：

| 项 | 旧 | 新 |
|---|---|---|
| 执行档位 | 单档 AOT | **两档：解释 + AOT**（复制-补丁 JIT 为可选第三档） |
| REPL | 不提供 | 不提供（理由不变：泛型单态化下有语义一致性问题） |
| 开发回路 | `x watch` 增量编译 | `x watch` + 解释器即时运行（两者并存） |
| 正确性验证 | 差分测试（缺参照） | **差分测试（解释器 vs AOT，参照完整）** |
| 解释器定位 | 仅 comptime 求值器 | comptime 求值器 + **正式运行时档位** |
| 汇编清单 | 530 行 | 530 行（不变，解释器核心用 C 写） |

**注意最后一行**：解释器核心用 C 写，不进汇编清单。理由是解释器的性能来自分派机制的设计，而不是手写汇编——`goto *` 编译出的代码已经与手写汇编相当（都是一条 `jmp [table+rax*8]`）。手写汇编在这里的唯一收益是控制代码布局以提高 i-cache 命中，收益 < 5%，不值得。

## 10. 一句话总结

**解释器要快，靠四件事：让分派可预测（线程化 + 超指令 + 复制）、让指令变少（寄存器式）、让数值不装箱（类型化指令）、让调用不昂贵（内联帧 + 不递归）。四件事加起来 5~6 倍，且都与 AOT 共用同一份字节码，所以只写一遍。**

这个组合的实测天花板是 native 的 1/4 ~ 1/5。**如果目标是更接近 native，那不是解释器的活，该用 AOT。** 分工清楚，两边都不需要妥协。
