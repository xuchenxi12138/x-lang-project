# X 语言解释器性能诊断与优化

> 诊断对象：`x-lang` 字节码解释器（`src/interp.c`）
> 实测机器：Windows / MinGW-w64 GCC 13，-O2
> 基准口径：程序内 `nowMillis()` 自计时，14 轮取最小值（规避 ToDesk/杀软造成的 1.8 倍抖动）

---

## 一、结论先说

你的语言**语义设计不慢，慢的是解释器的指令密度**。

同一份 10 亿次计数循环：

| 执行方式 | 耗时 |
|---|---|
| AOT 编译成原生 exe | **0.83 秒** |
| 字节码解释执行（第一轮优化前） | 48.3 秒 |
| 字节码解释执行（第二轮完成后） | **约 9 秒** |

AOT 和解释器跑的是同一套前端、同一份语义。两者差几十倍，说明问题不在语言设计，也不在 C 实现质量，而在**每条字节码的平均成本 × 指令条数**。

核心公式：

```
解释执行耗时 ≈ 指令条数 × 单条分派成本
```

实测单条分派成本约 **2.3 ns（≈ 7 个 CPU 周期）**，这个数字已经接近栈式解释器的下限，很难再降。
所以真正的杠杆只有一个：**减少指令条数**。

> 注：本文分两轮写成。第一轮（第二节前三条）定位并修了「减法没有超指令」
> 等三个问题；第二轮（第二节第 4、5、6 条）改用**运算族泛化**，把「一种
> 运算一条超指令」的手工枚举换成数据驱动，并顺手治掉了 `pos` 逐条物化
> 和每次调用扫类表这两个隐藏开销。两轮的数字都保留，便于看出各自贡献。

## 二、已定位的根本原因

### 1. 减法没有超指令 —— 你那个测速脚本慢的直接原因

这是本次最实质的发现。

`compile.c` 的超指令合并只做了 `ADD` / `MOD` 家族，**一条 `SUB` 都没有**。
于是结构完全相同的两个循环，指令数差一倍：

```
s = s + 1   →  ADD_CONST_STORE                     (1 条)
s = s - 1   →  LOAD_CONST                          (4 条)
               SUB_I64
               DUP_STORE_POP
```

实测（3000 万次循环）：

| 写法 | 优化前 | 优化后 |
|---|---|---|
| `s = s + 1` | 331 ms | 224 ms |
| `s = s - 1` | **736 ms** | **221 ms** |

**两者本应完全相同，优化前差了 2.2 倍。**

而你的 `tests/p1/04-test-speed.xle` 里恰好写的是：

```x
count2 = count2 - 1     // 减法，全落在没有合并的那一侧
```

这不是你写错了，而是语言实现的一个**盲区**：计数循环习惯写 `-`，而优化只覆盖了 `+`。
现象上只表现为「解释器就是慢」，极难反推到「少了两条合并规则」。

**已修复**：新增三条指令 `BC_SUB_STORE` / `BC_SUB_CONST_STORE` / `BC_SUB_CONST_STORE_JUMP`，
与 ADD 组逐项对称。循环体从 4 条压到 2 条。

### 2. 槽位释放走了不内联的完整函数

`value_release()` 带 4 个分支和递归，gcc 不会内联（体积太大）。
但热路径上覆盖一个槽位时，99.99% 的情况只是「把一个 Int 槽位标记为 null」——
根本不涉及任何引用计数。

```c
// 每次 `sum = sum + i` 都要走一遍完整的 4 分支函数
value_release(slot);
*slot = v_int(r);
```

**已修复**：抽出 `value_release_slot()`，把「值类型直接返回」这条最短路径放到内联位置。

实测额外收益：ADD 循环 **-26%**，混合循环 **-16%**，SUB 循环 **-6%**。

### 3. `pos` 被逐条指令物化（第二轮已修）

`interp.c` 里原本有这样一段注释：

> 这里仍取一次是为了让下面所有 `rt_error(pos, ...)` 不用改，
> 但编译器会把这个 load 沉到错误分支里做——因为 pos 在成功路径上没有使用者。

**这个假设不成立**。实际生成的汇编（`-O2`，分派循环头部）：

```asm
.L2298:
    movq    %rax, %rcx
    leaq    0(,%rax,8), %r14
    salq    $4, %rcx            ; 算 code_pos[pc] 的地址
    addq    80(%rsp), %rcx
    leaq    0(%r13,%r14), %r15
    movq    (%rcx), %r11        ; ← 无条件读 pos.file
    movq    8(%rcx), %rcx       ; ← 无条件读 pos.line/col
    movq    %r11, 48(%rsp)      ; ← 无条件写回栈（为了随时能给 rt_error）
    movq    %rcx, 64(%rsp)      ; ← 同上
    cmpb    $95, %dl
    ja      .L2298
```

**每条指令多出 2 次 load + 2 次 store**，而只有出错时才用得上。

为什么编译器不敢推迟：`rt_error` 是**可变参数函数**，`pos` 作为实参传进去，
编译器无法证明「这条路径不会用到它」，于是只能老实算出来放在栈上。

**修法**（已实施）：把 `pos` 换成宏 `X_POS()`，展开成 `code_pos[pc]`。
只有真正走到 `rt_error` 那一行才读取，热路径上零 load。

改动前后对比汇编（同一位置）：

```asm
; 改前：循环头无条件读 pos
    movq    (%rcx), %r11
    movq    8(%rcx), %rcx
    movq    %r11, 48(%rsp)
    movq    %rcx, 64(%rsp)

; 改后：循环头只剩真正需要的东西
.L1881:
    movq    48(%rsp), %rcx
    leaq    0(,%rdi,8), %r12
    leaq    (%rcx,%r12), %r14
    cmpq    $0, 56(%rsp)       ; profiling 判断
    jne     .L2854
    cmpb    $97, %al
    ja      .L1881
    jmp     *%rdx              ; 直接分派
```

交替实测（同一份 .xbc，两版二进制轮流跑）：**快约 20%**。

### 4. 新增 opcode 要改 N 处，漏一处就静默出错（第一轮已修）

补减法超指令时踩到一个真实的坑，值得记下来。

`compile.c` 里「这条指令是否带跳转偏移」的判据**硬编码在两地**：
`jtarget` 标注、跳转重映射。加 `BC_SUB_CONST_STORE_JUMP` 时两处都没加，结果：

1. `jtarget` 漏掉 → 合并 pass 不知道它指向别处，把目标指令吞进上一对合并，**指令凭空消失**；
2. 重映射漏掉 → 指令压缩后偏移不更新，跳错位置。

症状：`while i > 0 { ... i = i - 1 }` 第一次迭代就报「值栈下溢」，而单独写 `n = n - 1` 完全正常——
因为只有回边形态才生成带偏移的那条。

**已修**：判据收敛成单一函数 `op_has_jump_offset()`，两处调用它。
以后加跳转类 opcode 只需改这一个 switch。

### 5. 手工枚举超指令不可持续 → 改成运算族泛化（第二轮，收益最大）

第一轮补完减法后我数了一下还剩多少同构运算没覆盖：

```
s = s * 2   →  LOAD_CONST; MUL_I64; DUP_STORE_POP    (3 条)
s = s / 2   →  LOAD_CONST; DIV_I64; DUP_STORE_POP    (3 条)
b = b & 7   →  LOAD_CONST; BAND_I64; DUP_STORE_POP   (3 条)
b = b | 1 … ^ 3 … << 1 … >> 1                        同上
```

而 `s = s % n` 因为恰好有 `MOD_STORE` 只要 2 条 —— **同样是「一次赋值运算」，
指令数却分两档**，纯粹因为上次只挖到了 ADD 和 MOD。

继续一条条补就是 7 × 3 = 21 条新指令，`switch` 膨胀一倍，而且下次加运算类型还会漏。

**改法**：一条指令带一个运算码，覆盖全部十种整数二元运算。

| 指令 | 语义 |
|---|---|
| `BC_ARITH_STORE` | `<OP>_I64; DUP_STORE_POP a` |
| `BC_ARITH_CONST_STORE` | `LOAD_CONST a,b; <OP>_I64; DUP_STORE_POP a` |

配套 `XArithOp` 枚举（`XOP_ADD` … `XOP_SHR`），以及两张表：

- `compile.c: arith_op_of()` —— 运算指令 → 运算码（**唯一映射表**，加运算只改这里）
- `interp.c: arith_eval()` —— 运算码 → 实际计算（**唯一语义实现**）

为什么不用「opcode 偏移」那套（`store = arith + K`）：那要求算术指令在枚举里连续排列，
但 `BC_ADD_I64..BC_MOD_I64` 与 `BC_BAND_I64..BC_SHR_I64` 之间夹着 F64/NUM/DYN/EQ/比较指令，
打乱重排会改变已有 `.xbc` 的指令编号 —— 那些文件立刻无法执行。宁可多一个运算码字段。

**为什么必须收敛成单一语义实现**：同一个运算现在有三个入口（专用指令、`ARITH_STORE`、
`ARITH_CONST_STORE`），各写一遍就有 N 份需要同步的正确性代码，任何偏差都是**静默算错**。
本项目在 `<<` 上真吃过这个亏：`01 §4.3` 规定越界置 0 不回绕，解释器和 AOT 各写了一份判断，
其中一处漏了，`1 << 63` 在解释档得到 0、AOT 档得到 INT64_MIN。

实测（3000 万轮，每轮七种运算）：

| 版本 | 每轮指令数 | 耗时 |
|---|---|---|
| 优化前 | 23 条 | 219 ms |
| 优化后 | 9 条 | **56 ms** |

**提升 74%**，与指令数缩减比（23→9）基本吻合 —— 再次印证「耗时正比于分派次数」。

### 6. 每次函数调用都扫一遍类表（第二轮已修）

`BC_CALL` 里有这一行：

```c
nf->cls_idx = func_owner_class(bc, callee);
```

`func_owner_class` 做的事是：拿函数名找第一个 `.`、取前缀、**遍历整张类表逐名 `strcmp`**。
这是每次调用都执行一遍的字符串扫描 + 线性查找 —— 而结果对确定的函数索引来说是常量。

**已修**：VM 上加了懒填充缓存（`owner_class` + `owner_valid`）。

为什么放 VM 而不放 `FuncProto`：`FuncProto` 是 `.xbc` 磁盘格式的一部分，
加字段就要提升格式版本；而这是纯运行时派生数据，不该进文件。

为什么 `owner_valid` 单独一张表而不是用哨兵值：`-1` 本身是合法值（普通函数），
拿它当「未填充」会让每个普通函数每次调用都重新扫描 —— 恰好是最常见的情况。

实测：500 万次函数调用 **-13%**，300 万次方法调用 **-7%**。

## 三、还有哪些地方值得继续挖

按「预期收益 / 改动风险」排序：

### A. 继续补超指令家族（收益最大，风险最低）

第一轮是「按实测热点手工枚举」，覆盖**天然不完整**。第二轮已经把这个坑填了
（见第 5 条：改成运算族泛化），但还有几类形态没覆盖：

| 缺失形态 | 典型源码 | 现状 |
|---|---|---|
| 比较结果存槽位 | `b = a < c` | 3~4 条 |
| 字符串拼接存槽位 | `s = s + "x"` | 3 条 |
| 浮点运算存槽位 | `f = f * 1.5` | 3 条 |

比较和浮点没有跟着整数一起泛化，是因为它们的语义差异更大：
比较产出 Bool（栈效应不同）、浮点没有溢出 trap（不需要冷路径）。
但**思路是一样的**——照 `XArithOp` 的做法再开 `XCmpOp` / `XFloatOp` 即可，
不要再一条条写规则。

真正的下一步是**数据驱动**：`X_PROFILE=1` 已有「相邻指令对直方图」，
第二轮我加了 `X_PROFILE_TOP=N` 来调输出条数（默认 20 太窄，跑真实程序
看不出全貌）。把它做成脚本——跑一遍标准库 + 应用的负载，把高频对按频率
自动生成合并规则，这样新增运算类型时不会再漏。

另外 `bytecode.c` 的 `has_operand()` 也是同一个毛病的实例：它漏了 SUB 三条，
症状是反汇编里 `SUB_CONST_STORE` 后面什么都不显示 —— 而槽位号正是排查
「存错变量」时唯一要看的东西。第二轮一并补了。

### B. 把 `sp` 提到寄存器（收益中等，改动较大）

现在每条指令都要 `vm->sp` 读写内存（`vm` 是堆上的指针）。虽然编译器会把它缓存在寄存器里，
但 `value_release()` 这类不内联调用会强制回写——形成一条**串行依赖链**，超标量派不上用场。

改法：在 `run_bytecode` 内部用局部变量 `Value* sp` 代替 `vm->sp`，
只在 `BC_CALL` / `BC_RETURN` / 内建调用前后同步。这是解释器优化的标准手法，通常能拿到 10~20%。

### C. 直接线程化分派（computed goto，收益 5~15%）

现在是 `switch` + 跳转表。GCC 支持 `goto *table[op]`，可以省掉 switch 的边界检查和一次间接跳转。
代价是代码可读性下降，且每个 case 结尾要显式 `DISPATCH()`。

### D. 类型特化寄存器（长期）

栈式字节码的天然缺陷：`s = s + i` 要 4 次栈往返。
寄存器式（或用「累加器 + 局部槽」的混合设计）能把 `LOAD_LOAD/ADD/store` 压到 1~2 条。
但这是字节码格式的重构，属于 v1.0 级别的决策。

### E. 启动开销 42ms

空程序 `x run empty.xbc` 要 41.5ms（C 空程序 44.8ms，其中大部分是进程创建）。
X 比 C 多的部分主要是：VM 的 1.28 MB（64K 值栈 × 16B + 4K 帧）`memset`、
以及 UTF-8 控制台初始化。

对长脚本无所谓，但对「跑一个 hello world」体验明显。
可优化点：`VM` 用 `VirtualAlloc`（惰性提交）而不是 `malloc + memset`；
值栈按需增长而不是启动就 64K。

## 四、实测汇总

所有数字为程序内自计时、多轮交替测量取最小值（不含进程启动）。

### 第一轮（减法超指令 + 槽位释放快速路径）

| 基准 | 优化前 | 优化后 | 提升 |
|---|---|---|---|
| SUB 计数循环（3000 万次） | 736 ms | 221 ms | **-70%** |
| ADD 计数循环（3000 万次） | 331 ms | 224 ms | **-32%** |
| 混合循环（3000 万次，6 条/轮） | 717 ms | 635 ms | -11% |

### 第二轮（运算族泛化 + pos 按需 + 类归属缓存）

| 基准 | 优化前 | 优化后 | 提升 |
|---|---|---|---|
| SUB 计数循环（3000 万次） | 341 ms | 132 ms | **-61%** |
| 七种运算循环（3000 万轮） | 219 ms | 56 ms | **-74%** |
| 500 万次函数调用 | 108 ms | 94 ms | -13% |
| 300 万次方法调用 | 84 ms | 78 ms | -7% |
| **你的 10 亿次循环** | **48.3 s** | **约 9 s** | **约 -81%** |

> 第二轮的数字是在机器负载更高时测的（同一程序绝对值比第一轮偏大），
> 所以第一轮和第二轮的「优化后」不能直接横比；每行只跟自己那一行的
> 「优化前」比才有意义。

### 正确性验证（两轮都做）

- **53 个 P0 测试逐字节比对 + 退出码比对，与优化前完全一致**（0 差异）；
- 10 个 `.fail` 预期失败测试，退出码全部匹配；
- AOT 后端输出与解释器逐字节一致 —— 含 `1 << 63`、`>> 64`、`INT64_MIN / -1`
  这些历史上有过漂移的边界；
- 复杂控制流（`continue` / `break` / 嵌套循环 / 位运算与运算赋值交错）逐一对照无差异；
- 引用计数压力测试：字符串 / 数组 / 类实例各 10 万次槽位覆盖，内存无增长；
- 真实标准库负载（8 个函数、字符串 + 数组 + 数学混合）输出一致。

### 一个值得记下的插曲

第二轮往 AOT 生成器里塞 `xa_eval` 模板字符串时，模板里写了 `a %% b` ——
那是 `fprintf` 的格式转义，而这段是**预置模板**（不经 `fprintf` 格式化），
于是生成的 C 代码里留下字面的 `%%`，gcc 报 `expected expression before '%'`。

抓到这个 bug 的不是单测，而是「AOT 输出 == 解释器输出」这条对照 ——
它一次就指出「AOT 根本没编过」。所以那条一致性测试不能省。

## 四·补、第三轮：变量拷贝与比较跳转（v0.22）

第三轮开头做的事，是**先量再改**。前两轮是「读代码看出来缺了什么」，
这一轮改成跑真实混合负载（标准库 + 应用，60 万轮）收 `X_PROFILE_TOP=30`
的相邻指令对直方图，按实测频率挑目标：

| 形态 | 次数 | 对应源码 |
|---|---|---|
| `LOAD_LOCAL → STORE_LOCAL` | 3,150,000 | `y = x` |
| `LOAD_CONST → NE → JUMP_IF_FALSE` | 2,550,000 | `while a != b` |
| `LOAD_LOCAL → DUP_STORE_POP` | 1,950,000 | `x = arr[i]` |
| `MUL_F64 → DUP_STORE_POP` | 600,000 | `x = x * 1.5` |

前两条做成新超指令：`BC_MOV_LOCAL`、`BC_NE_CONST_JUMP_FALSE`。

### 第一个教训：直方图会骗你，因为「同一个源码形态有多种字节码」

`while a != b` 在直方图里是一对 `LOAD_CONST → NE`。我据此做了常量形态，
测出来只有 1~2% 的提升，差点以为「这个方向没收益」。

查反汇编才明白：`while i != n`（n 是**变量**）编译成
`LOAD_LOAD + NE + JUMP_IF_FALSE`，而 `while i != 0`（常量）才是
`LOAD_CONST + NE + JUMP_IF_FALSE`。我的测速程序写的是前者，
新规则根本没命中 —— 直方图里那 255 万次统计的是后者。

补上变量形态（`BC_NE_JUMP_FALSE`）之后：

| 形态 | 关闭 | 开启 | 提升 |
|---|---|---|---|
| `while i != n`（两变量） | 597 ms | 121 ms | **-80%** |
| `while i != 0`（变量 vs 常量） | 800 ms | 273 ms | **-66%** |
| `y = x` 拷贝循环 | 108 ms | 88 ms | **-19%** |
| 真实混合负载（数组+遍历+字符串） | 277 ms | 216 ms | **-22%** |

三条都是 3000 万次/200 万轮的规模，程序内自计时。

**为什么能降 80%**：循环头从 4 条指令（`LOAD_LOAD`/`NE`/`JUMP_IF_FALSE`/
`ADD_CONST_STORE_JUMP`）压到 2 条（`NE_JUMP_FALSE` + `ADD_CONST_STORE_JUMP`）。
省的不只是 2 次分派，还有压在栈上又被弹掉的两个操作数 —— 各 16 字节写入
加一次 `sp` 调整。而这两条正是「一条指令成本 ≈ 2.3ns」那个下限的两倍。

### 第二个教训：怎么隔离「单轮」的收益

一开始我用两个 git 版本对比，得出「10 亿次循环 13.2s → 7.4s，第三轮值 5.8 秒」。
这个结论是**错的**：那 13.2s 的版本里连第一轮的 SUB 超指令都没有，
差值是三轮的合计。

正确做法是同一份二进制、只切换一个编译期开关。于是加了 `X_NO_NEW_MERGE=1`
（跳过第五批规则），编译器其余部分 —— 寄存器分配、代码布局、分支预测器
状态 —— 完全一致。上面那张表全部是这么测的。

顺带说，这个开关现在是长期设施：以后再加超指令，判断「值不值得留」
有了干净的手段。

### 第三个教训：正确性验收不能用「没崩」当标准

`BC_MOV_LOCAL` 是这一轮唯一手动管引用计数的新指令（拷贝一个可能持有
`XStr`/`XArr`/`XObj` 的值到另一个槽位）。漏 `retain` 的症状是**双释放**，
漏 `release` 的症状是**泄漏**，而两者在小规模测试里都不会显现。

普通的「两份二进制输出一致」抓不到这个问题 —— 输出确实一致，内存却错了。

所以给解释器加了 `X_RC_STATS=1`：每建一个对象 +1、每释放一个 -1，
程序结束时向 stderr 打存活数。它比采样进程内存可靠得多 ——
实测过后者：Windows 上一个跑几百毫秒、占十几 MB 的进程，
采样读到的值在 7.8MB 和 11.9MB 之间跳，噪声比信号还大。

用它验证的结果：

```
$ X_RC_STATS=1 ./build/x.exe run t_mov_arr.xle   # 10 万次数组拷贝
[rc] live_str=0 live_arr=2        # 恒为 2（src + dst），不随循环增长
$ X_RC_STATS=1 X_NO_NEW_MERGE=1 ./build/x.exe run t_mov_arr.xle
[rc] live_str=0 live_arr=2        # 关闭新合并，完全一致
```

`live_str=0` 和 `live_arr=2` 都是精确值，不是「看起来差不多」。

### 顺带发现的既存泄漏（与本轮改动无关）

用这个计数器跑「循环体内声明数组」时发现：

```
let i = 0
while i != 1000 {
    let a2 = [1,2,3]
    i = i + 1
}
println(i)
```

`live_arr` 是 **1000**，不是 0 —— 每轮泄漏一个数组。
`X_NO_NEW_MERGE=1` 时数字完全相同，确认与第五批规则无关。

根因是**循环体内块作用域变量在每次迭代结束时没有释放**
（块作用域只在退出作用域时清一次，而不是每轮清）。
它不影响正确性，只影响长循环的内存占用。

这条已记在下面「待修」里，不属于本轮范围，但值得单独修 ——
排查手法（`X_RC_STATS` 看净存活数是否随迭代线性增长）已经留在代码里。

### 第三轮的验证

- 63 个 P0 程序：`X_NO_NEW_MERGE` 开/关**输出、退出码、rc 统计三项全一致**；
- 76 个测试程序（含 p1）：同上，唯一差异是测速脚本里那个自计时数字；
- AOT 与解释器：`MOV_LOCAL` / `NE_CONST_JUMP_FALSE` / `NE_JUMP_FALSE`
  三种新指令的生成代码逐字节一致（含字符串常量、浮点常量、类实例身份比较）；
- `85 通过 / 8 失败` —— 与改动前的基线**完全相同**，那 8 个是包管理
  与网络环境相关的既存失败（`pkg-*`、`reg-*`、`zh-pkg*`、`opt-e2e`、
  `53-net-service-web`）。

### 待修（非本轮范围）

1. **循环体内块作用域变量每轮泄漏**（上面那条）。改法：把块作用域清理
   从「退出作用域时一次」改成「每轮迭代末尾」，或让编译器在循环体尾部
   插入清理指令。注意后者会影响 `continue`（要跳到清理点而不是循环头）。
2. **AOT 侧缺 rc 统计**。`codegen_c.c` 生成的 C 代码没有对应的
   `X_RC_STATS`，所以上面那条泄漏只在解释器档可见。要验证 AOT 同样干净，
   得在生成的运行时里加同样的计数器。

## 四·补二、第四轮：循环融合（v0.23）

第三轮结束时，计数循环已经压到 3 条超指令。继续合并超指令的路走不通了
（`Insn` 只有 3 个 int16，比较+跳转要 4 样信息），于是换方向：
**不再减少指令数，改为减少「指令被解释的次数」。**

### 思路：把整个循环摘出来，用原生 C 跑

关键观察是**解释器自己就是 C 代码**。把循环体展开成一个普通的 `for`，
gcc 会给它做寄存器分配、常量折叠、宏融合 —— 这正是 JIT 想要的全部效果，
而且零外部依赖。

为什么不做真正的 JIT（运行时调 gcc 生成 DLL）：

| 障碍 | 具体问题 |
|---|---|
| 平台层无动态加载 | `platform.h` 既无 `dlopen` 也无 `LoadLibrary`，要新增得同时改两条路径 |
| 跨 ABI 状态 | 生成的代码要访问值栈、常量池、错误报告，胶水比优化本身还多 |
| 编译成本 | 每次 spawn gcc 实测 2 秒，循环不跑几千万次根本不回本 |

### 实现：四个阶段

`lf_translate` 负责识别，`lf_run_int` 负责执行。

**阶段一·识别**：只接受「头部判定」的规整循环：

```
head:  <比较>_JUMP_FALSE -> exit     ; 条件为假就跳出
body:  ...                            ; 只允许 ADD/SUB/MUL_CONST_STORE
tail:  <运算>_STORE_JUMP -> head      ; 自增 + 无条件跳回
```

任何调用、分配、`if`、`break`、浮点、字符串一律拒绝 —— 覆盖率高不等于
收益高，出错一次的代价远大于少优化一万个循环。

**阶段二·解包**：把参与的整数槽位从 `Value` 数组提到局部 `int64` 寄存器。
**阶段三·纯算术循环**：循环体内零 `Value` 访问、零 `switch` 分派。
**阶段四·打包**：结束后写回 `Value`。

### 三个必须记住的坑

**坑 1：分派只是搬了个家，收益几乎为零。**

第一版写成 `for (k...) lf_exec_one(...)`，看起来「没有分派了」，但
`lf_exec_one` 内部又是一个 `switch (op->kind)`。实测：

| 版本 | 耗时 | 倍数 |
|---|---|---|
| 解释执行 | 12.9 s | 1.0× |
| 融合但循环内仍 switch | 7.4 s | 1.7× |
| **融合 + 寄存器化** | **1.9 s** | **6.8×** |

真正拿到数量级的是**数据不再走内存**，不是「少了几次 switch」。

**坑 2：在回边处融合会多跑一轮。**

`lf_try` 在回边指令处调用。此时本轮循环体已由解释器执行完，但**尾自增
还没做**（它本来就是这条回边指令的活）。若不补这一步直接进 `lf_run`，
后者从「判条件」重新开始，本轮的循环体就被执行第二次。

症状：`c` 初值 10000000000、循环 10 亿次 → 得到 `8999999999`，少 1。
这种 off-by-one 只在循环边界暴露，看起来像「融合算错了」，实际是
「重复执行了一轮」。

**坑 3：`LF_MOV` 不能进寄存器化路径。**

寄存器路径只存 `int64`，而 `LF_MOV` 的语义是「拷一个 Value 并维护
引用计数」—— 字符串/数组/实例都要 retain + release。压成
`reg[dst] = reg[src]` 会**静默丢失引用计数**：对象被提前释放，
崩溃点离原因极远。

所以 `LF_MOV` 在阶段一被直接拒掉。整数拷贝本来也几乎不出现
（编译器生成的是 `LOAD_LOCAL + DUP_STORE_POP`，已不在白名单）。

### 实测收益

| 基准 | 解释执行 | 融合后 | 提升 |
|---|---|---|---|
| `while i != n { c = c-1; i = i+1 }`（10 亿轮） | 9.7 s | **1.9 s** | **5.1×** |
| 用户 `04-test-speed.xle`（10 亿轮） | 4.8 s | **1.8 s** | **2.7×** |
| 2 条指令循环（1.5 亿轮） | 1.24 s | 0.35 s | 3.5× |

对比参考：同脚本 AOT 编译版 0.35~0.41 s。**融合后已经进入 AOT 的同一量级**，
而启动开销仍然是 0（不像 AOT 要 spawn gcc）。

### 验证

- 75 个测试程序：`X_NO_JIT` 开/关**输出 + 退出码 + 引用计数统计**三项一致
  （唯一差异是测速脚本里那个自计时数字本身）；
- 85 通过 / 8 失败，与改动前基线完全相同；
- AOT 与解释器（含融合）输出逐字节一致；
- 边界用例专项：零次迭代、一次迭代、递减到负数、两变量比较、
  循环后变量被使用、整数溢出 trap、浮点循环变量、字符串循环变量；
- 引用计数：20 万次循环内拷贝后 `live_str=0 live_arr=0`，无泄漏。

### 开关

`X_NO_JIT=1` 整体关闭融合，退回纯解释执行。保留它的理由与
`X_NO_NEW_MERGE` 相同：判断「这轮优化值多少」必须能在同一份二进制上
切换，而不是对比两个 git 版本。

`X_JIT_MIN_HITS=<n>` 调整融合阈值（默认 10000）。**设成 0 是测试
手段，不是调优手段**：它让循环从第一轮起就走融合路径，于是「融合执行
时的报错位置/文案」可以和解释执行逐字对照。

没有它的话，报错路径基本没法测 —— 阈值 10000 意味着要构造一个
「跑满 1 万轮之后才溢出」的用例，而绝大多数溢出用例第 1 轮就炸，
测到的是解释器而不是融合。第六轮那个「溢出报错到错误的行」的 bug
就是靠它才暴露的。

`X_JIT_STATS=1` 打印覆盖率统计（见第六轮的「先量再改」）。

### 局限（明确的边界）

- **只覆盖计数循环**。`for i in a..b`、遍历数组、含 `if` 的循环体都还在
  走解释器 —— 它们需要真正的控制流图分析。
- **只支持整数槽位**。浮点/字符串循环直接拒绝。
- **函数调用没有 JIT**。跨函数的热点（比如被调用 100 万次的排序函数）
  仍然每次走 `BC_CALL`。那需要函数级的替换机制，是下一步。

## 四·补三、第五轮：先量覆盖率，再补形态（v0.24）

第四轮结束时，融合引擎只覆盖「压测跑出来的那一种循环」：
`c = c - 1` 配 `while i != n`。而压测循环恰好是最罕见的写法之一 ——
真实的循环几乎都在做 `n = n + i`、`while i < n`、`s = s + i * 2`。

这一轮没有先动手，而是**先量**：真实程序里到底有多少循环已经被融合、
多少被拒、拒在哪个原因上。

### 工具：`X_JIT_STATS=1`

在 `lf_translate` 的每条 `return false` 前记一笔拒绝原因，并给
「循环体含不可融指令」额外记一份 **opcode 直方图**。

```
$ X_JIT_STATS=1 x run tests/p0/12-perf.xle
[JIT] 尝试融合的热循环：1 个
  循环体含不可融指令    1
  循环体内的不可融指令：
    LOAD_LOAD              1
```

这一步的价值在于它**推翻了我的预期**。我原以为下一件该做的事是
「给数组遍历加 `INDEX_GET` 支持」，因为那看起来是最大的空缺。实际扫完
一百多个测试程序后，被拒指令的第一名是 `LOAD_LOAD` —— 也就是
`d = a + b` 这个最基本的三地址算术，而不是任何花哨的形态。

**这就是不靠直觉的证据。** 直方图里 `LOAD_LOAD` 以压倒性优势排第一，
而 `INDEX_GET`、`JUMP_IF_FALSE` 一次都没出现 —— 说明「扩展数组遍历」
当时的优先级判断是错的。

### 补上的四种形态

| 形态 | 原始指令序列 | 折成 |
|---|---|---|
| 双变量运算 | `LOAD_LOAD a,b; ADD_STORE d` | `d = a + b` |
| 双变量运算（泛化） | `LOAD_LOAD a,b; ARITH_STORE d,op` | `d = a op b` |
| 变量×常量 | `LOAD_LOCAL a; PUSH k; OP; OP_STORE d` | `d = a op k` |
| **乘加复合** | `LOAD_LOAD a,b; PUSH k; MUL; ADD_STORE d` | `d = a + b * k` |

外加一个条件：`while i < n` 的头部是**两条**指令
（`LOAD_LOAD` + `LT_JUMP_FALSE`），而 `while i != n` 只有一条
（`NE_JUMP_FALSE` 已经三合一）。融合引擎现在识别双条头部。

### 为什么没顺手把 `LT_JUMP_FALSE` 也合成一条

试过了，回退了。`BC_LT_JUMP_FALSE` 已经被两两规则用来承载
「`LT_I64; JUMP_IF_FALSE`」的**纯栈形态**：操作数从栈顶取，指令不知道
自己用了哪个槽位，只有 `a`（跳转偏移）一个字段。

要装下槽位形态就得借用 `b`/`c`，而解释器**无法区分两种形态**：
唯一可能的标记是「`b` 是否为 -1」，但 `bc_emit` 把不识别的操作数一律
清 0，槽位 0 又是完全合法的操作数。更糟的是磁盘上的老 `.xbc` 里
`LT_JUMP_FALSE` 的 `b` 就是 0 —— 会被误判成「从槽位 0/0 取两个值比较」，
**静默算错**。

结论：这种需求应该由解释器内部识别，不该污染字节码格式。改动从
`compile.c` 移到了 `interp.c` 的 `lf_translate`。

### 第二个坑：加了字段就必须清零

给 `LfOp` 加 `d`（目的槽位）字段之后，性能**静默退化**：
`c = c - 1` 从 1.7s 退到 6.5s，**而 85 个测试全部通过、63 个程序输出
逐字节一致**。

原因是各分支只写自己关心的字段，没写 `d` 的就会留下栈上的垃圾值；
而 `d` 被当成槽位号参与寄存器分配 → 拿到一个随机槽位 → 类型检查失败
→ 整条循环退回解释执行。

这个 bug 最阴的地方是：**结果完全正确，只是慢**。所有正确性测试都
指不出来，只有实测能发现。修法是布局时统一 `memset`，不依赖每条分支
自觉。

顺带把这段教训写进了 `lf_translate` 的注释里 —— 以后再加字段的人
会先看到它。

### 实测收益

单进程内交替测量（规避 turbo boost 升/降频），3 亿次迭代：

| 形态 | 第五轮前 | 第五轮后 | 提升 |
|---|---|---|---|
| `c = c - 1`（压测形态） | ~1.2 s | ~1.1 s | — |
| `n = n + i` | 10.9 s | 1.2 s | **9×** |
| `s = s + i * 2` | 9.6 s | 1.3 s | **7.2×** |

三种形态现在同速（1123 / 1246 / 1331 ms），说明它们走的是同一条
寄存器化路径。

`n = n + i` 在 1e9 次下的绝对数字：**36.5 s → 6.5 s**。三分之一是
融合，剩下是这台机器当前的频率（同代码在低温时是 1.2s/3e8 ≈ 4s/1e9）。

### 验证

- **输出逐字节对比**：63 个程序，`X_NO_JIT` 开关前后 stdout 的 md5
  完全一致，不一致 0 个。
- **溢出点专项**：乘加有两个溢出点（乘那步报 `*`、加那步报 `+`），
  分别构造用例确认报错的**算子、行、列**与解释执行完全相同。
- **边界专项**：零次迭代、一次迭代、别名（`d == a`）、递减到负数、
  循环后变量被使用、循环内改上界。
- **引用计数**：`live_str` / `live_arr` 在开关前后数字完全相同。
- **全量回归**：85 通过 / 8 失败，与基线逐项一致（8 个是包管理与
  网络环境的既存失败）。

### 剩下的拒绝（都不是缺陷）

扫完之后剩下的两处拒绝，看字节码都是**正确该拒**的：

- `14-memory.xle`：`acc = acc + "x"` —— 字符串拼接循环，整数融合
  本就该拒绝。
- `53-net-service-web.xle`：`LOAD_LOAD` 后面跟 `CALL`（调用参数），
  不是「算完存回」。

也就是说，**整数算术类循环现在基本已被覆盖完毕**。下一轮的收益点在
别的方向（函数调用、数组遍历），而不是继续在这条路上加形态。

## 四·补四、第六轮：修两个真实缺陷（v0.25）

这一轮没做「更大的优化」，而是做了两件必须先做的事：**验证既存实现
是否真的与解释执行等价，以及修补测出来的偏差**。

起因很偶然：想跑基准看当前水平，发现 `tools/bench.sh` 的循环
`sum = (sum + i) % 1000003` 里含取模 —— 而取模在第五轮的白名单外。
**项目自己的基准曲线从第四轮起就没反映过融合能力**，一直在测纯解释。

### 缺陷一：融合路径把溢出报到了错误的源码行

第一件事是验证「融合执行时的报错」与「解释执行时的报错」是否一致。
之前几轮的验证都只看 stdout，而溢出测试**全都只比了数值或退出码**。

为了测准，加了个开关 `X_JIT_MIN_HITS`（融合阈值，默认 10000）。
设成 0 之后循环从第一轮就走融合路径 —— 这是必须的，否则第 5 轮溢出的
用例在阈值 10000 下根本走不到融合路径，测的是解释器。

一测就发现：

```
$ X_JIT_MIN_HITS=0 x run t1.xle     # 循环体第 7 行加法溢出、第 8 行 i+=1
  位置   t1.xle:8:9      ← 报在尾自增那行
$ x run t1.xle                       # 解释执行
  位置   t1.xle:7:11     ← 正确
```

根因：`lf_try` 在回边处被调用，传给 `lf_run` 的 `pos` 是**回边指令的
位置**。只含一条运算的循环里这没问题（回边就是那条自增），但三地址
形态跨了三条指令，溢出可能发生在 body 那一行。

修法：给每条 `LfOp` 加 `pos`，翻译时从对应字节码取。乘加和链形态有
**两个**可能出错的位置，各记一份（`pos` / `pos2`）。

这个 bug 的隐蔽性值得记一笔：它只在「循环体跨多行 **且** 溢出发生在
非回边那行 **且** 循环跑过阈值」时暴露。三个条件同时满足才会看到。

### 缺陷二：基准循环从未被融合

`sum = (sum + i) % 1000003` 的字节码是

```
LOAD_LOAD  0, 1
ADD_I64                 ← 第一段运算
PUSH_I64   [3] = 1000003
MOD_STORE  0            ← 第二段运算 + 存回
```

第五轮的形态都是「一条运算」，而这里是**两条运算串起来**。

没有为 `%` 单独加一条规则，而是加了一个通用的「二元运算链」形态
`LF_CHAIN_CONST`：`d = (a OP1 b) OP2 k`，两段的算子都用 `XArithOp`
表达。这样一次覆盖 `/ % & | ^ << >>`，而不是修好 `%` 之后又留一堆空缺。

关键决定：**两段都调用 `arith_eval`，不手写算子**。除零、取模除零、
`INT64_MIN % -1`、移位越界置 0 这些语义都在那里实现好了；手写一份就是
第二份需要同步的正确性代码 —— 而这个项目史上 `<<` 恰恰因为解释器和
AOT 各写一份而错过一次（`1 << 63` 一边得 0、一边得 INT64_MIN）。

代价是热路径上多一次函数调用，但 `arith_eval` 是 `static inline`，
`-O2` 下会内联成几个比较 + 一条指令。

### 实测

`tools/bench.sh` 的循环，3000 万次，单进程交替测量：

| 形态 | 融合关 | 融合开 | 提升 |
|---|---|---|---|
| `sum = (sum+i) % 1000003` | 548 ms | 206 ms | **2.7×** |
| `sum = sum + i`（纯加法） | 453 ms | 65 ms | 7.0× |

取模提升小是硬件决定的：`idiv` 比加法贵一个数量级，融合省掉的是分派
开销（约 340ms），而剩下的 206ms 主要是除法电路本身。这与「融合没生效」
无关 —— 纯加法的 7× 说明路径一致。

重复测量 208/204、548/549，无频率漂移。

### 关于函数级 JIT 的判断（本轮**没有**做，结论在此）

顺手量了 `fib`：

- `fib(30)` 约 270 万次调用，**55 ms**；C `-O0` 逐次调用约 3ns。
- X 每次调用约 20ns。
- 1 参数 vs 8 参数：56ms vs 150ms，**每多一个参数约 +6.5ns**。

参数槽位预填 + 释放遍历确实占一部分，但**不是主要矛盾**：主要矛盾是
每条指令仍要走一次 `switch` 分派。而局部变量预填是正确性硬要求（不填
就会读到上一帧残留的指针），释放遍历也不能省（4 次比较已经很精简）。

结论：**函数级优化想拿到数量级收益，必须做内联编译**（把被调函数体
展开到调用点、类型特化、消除分派）。那是一个新工程，不是「顺手优化」。
在没有类型特化基础设施之前，只把 `BC_CALL` 里的几次比较省掉，收益会
在噪声以下。

所以本轮停在这里，把结论写清楚，而不是做一个「看起来在做优化」的改动。

### 缺陷三：基准脚本会把测量噪声算成「1654 倍」

这一条不在编译器里，在 `tools/bench.sh` —— 但它比前两条更值得记，
因为**它会让所有后续决策建立在假数据上**。

跑完基准看到：

```
  基准                           X     C -O0     C -O2    X/C-O0
  整数循环 3000 万次   190.2 ms    77.8 ms    78.5 ms      2.4×
  fib(33) 700 万次调用   165.4 ms     0.1 ms     0.1 ms   1654.0×
```

`C 0.1ms` 是荒谬的。根因是一行：

```sh
sub() { awk -v a="$1" -v b="$2" 'BEGIN{v=a-b; if(v<0.1)v=0.1; printf "%.1f", v}'; }
```

「扣除启动基线」这个想法本身是对的，但 `if(v<0.1)v=0.1` 把
**「差值是负数（测量失效）」伪装成了「0.1ms（很快）」**。

负数怎么来的：原始耗时和空程序基线是两次独立测量，各自受噪声影响。
Windows 上光是加载 CRT 就要 40~60ms，当基线某一轮读高、而被测程序
某一轮读低时，差值就是负的。

修法：差值 < 5ms 时不再静默兜底，而是打 `[!]` 标记、保留原始值，
并让倍数显示 `n/a` —— **宁可显示「测不准」，也不给一个漂亮但假的数字**。
同时把原始值单独打印出来。

### 附带纠正：一处自己犯的测量错误

在判断「X 的 fib 与 C 差多少」时，我手工写了个 `fib(33)` 字面量的
C 程序测出 164ms，据此以为「X 只比 C 慢 1.2 倍」。这**两个判断都错了**：

- 164ms 与 60ms 的差异不是代码差异，是**频率漂移**。交替测量后
  两个二进制都是 60~61ms。
- 真实差距是 **X 157ms vs C -O0 60ms ≈ 2.6 倍**，既不是 1.2 倍，
  也不是脚本错报的 1654 倍。

这条坑 `tools/bench.sh` 顶部早就写着（「同一个二进制连续三轮能差
1.8 倍」），我还是踩了 —— **说明这类坑靠「知道」不管用，只能靠
「每次都用交替测量的脚本」**。手工 `time` 一下得出的数字不要用。

### 验证

- **强制融合 vs 纯解释**：79 个程序（含边界专项），**含 stderr 的全部
  输出 md5 一致** —— 这次比了报错路径，不只是 stdout。
- **链形态专项**：除法、取模、位移、位与、除零、取模除零、负数截断、
  `INT64_MIN % -1` 八种，全部一致。
- **除零文案**：融合路径与解释路径逐字相同（都走 `arith_raise_error`）。
- **全量回归**：85 通过 / 8 失败，与基线逐项一致。

**整数循环从 467ms 降到 190ms（比值 5.6× → 2.1×）** —— 这是本轮

## 四·补五、第七轮：Java 到底靠什么追上 C

这一轮的起点是一个问题：「Java 是解释执行的，凭什么能跑得和 C 差不多快？」

回答这个问题之前先纠正一条**自己的错误结论**，因为它直接决定了后面的
方向判断。

### 先纠错：上一轮那个「C -O0 只要 365ms」是假的

上一轮我写了一个 C 循环，用 `argv` 传次数防止 `fib(33)` 式的编译期求值，
测出 365ms，据此得出「X 融合循环比**不优化的 C** 慢 6 倍」。

但这个防折叠只防住了一半。`gcc -O2` 还能做**闭式解**：面对

```c
while (i != N) { c -= d; i += d; }
```

它能推出「`c` 的终值 = 初值 + (N/i 的步数)·(-d)」，把整个循环消成一条乘法。
反汇编里循环确实只有 5 条指令，看起来很清白 —— 但那是 `-O0` 的产物。
`-O2` 下这个函数**直接返回常量**，循环一条不剩。

正确的对照必须让「步长」也从运行期来，并且两侧都带同样的溢出检查。
重测（同进程交替、取最小值）：

| 实现 | 1e9 次 `c=c-1; i=i+1` |
|---|---|
| C `-O2`，无溢出检查（闭式解已排除） | ~600 ms |
| C `-O2`，带 `__builtin_*_overflow` | ~805 ms |
| **Java 8 HotSpot（同类循环）** | **294 ms** |
| **X AOT（`--emit=exe`）** | **333 ms** |
| X `x run`（融合 JIT 路径） | 2322 ms |

结论有两条，都很重要：

1. **溢出检查几乎不花钱**（600 → 805ms，1.34×）。所以「X 因为要抛溢出
   错误所以必然比 C 慢」这个借口不成立。
2. **X 的 AOT 已经追平 Java 和 C**（333 vs 294 / 600）。差距不在后端，
   在 `x run` 这一条分支上，还有约 7 倍没拿到。

### 那 7 倍丢在哪：`reg[fo->dst]` 的括号里

`lf_run_int` 阶段三的内层循环是：

```c
for (int k = 0; k < nfops; k++) {
    const FastOp* fo = &fops[k];
    switch (fo->kind) { ... reg[fo->dst] ... }
}
```

`nfops` 是运行期值，`fo->dst` 也是运行期读出来的。对 gcc 来说这意味着
**它既不能展开这个循环，也不能证明 `reg[]` 的下标不变** —— 于是整个
数组只能钉在栈上，每轮 4 次内存往返。

隔离测量（每次只改一个变量，`-O2`，用 `argv` 传参防折叠）：

| 写法 | 1e9 次 | 说明 |
|---|---|---|
| `reg[fo->dst]`，`nfops` 运行期 | 2262~3843 ms | 现状 |
| `reg[fo->dst]`，`nfops` 字面量 + 合并分派 `kind*8+dst` | 913~1244 ms | 只消掉一半 |
| `r0/r1` 具名变量，算子与槽位均字面量 | ~250 ms | 天花板 |

也就是说：**「算子个数」和「槽位号」这两个字面量化，值 7 倍。**

这里有一个反直觉的点值得记下来：**把槽位字面量化比把分派合并更值钱**。
单纯把 `switch(kind)` 合并成 `switch(kind*8+dst)` 只从 3843 降到 1244，
因为分派本身还在；而一旦 `dst` 是字面量，gcc 就能让 `r0`/`r1` 常驻
寄存器，分派是否合并就不太要紧了。

### 这也正是 Java 的做法（问题本身的答案）

Java 快**不是**因为「编译成字节码再执行」，恰恰相反，字节码是它的慢路径。
HotSpot 的策略是：

1. **先解释执行**，同时给每个方法和回边（back-edge）挂计数器。
2. 计数过阈值 → **C1 编译**：快速生成机器码，做局部优化，重点是「把
   栈式字节码摊平成寄存器式的机器指令」—— 注意，`iload_1 / iload_2 /
   iadd / istore_1` 这串东西编译后，槽位就变成了**固定的物理寄存器**，
   这正是上表里「槽位字面量」那一档。
3. 更热 → **C2 编译**：全局优化、循环展开、向量化、内联、逃逸分析、
   去虚拟化。C2 的循环优化和 `gcc -O2` 是同一类技术。
4. 编译基于**运行期类型profile**，所以能做 C 做不到的事：例如
   「这个调用点 99.9% 都是 `ArrayList`，直接内联它的 `get()`」。

所以准确的因果是：**Java 快是因为它在运行期把热循环编译成了「槽位
是寄存器」的机器码，而不是因为它有字节码。** 字节码只是它决定「编译
哪一段」的依据。

这一点对 X 的直接含义：X 的 AOT 已经是「生成 C 再交给 gcc -O2」，本质上
和 C2 同构，实测也追平了。**真正缺的是「运行期把 `reg[dst]` 变成
`r0`/`r1`」这一步**，而那一步在 C 里只能靠「穷举展开」。

### 为什么这件事不能靠「再写一个更好的 C 循环」解决

因为 C 是静态语言，`dst` 一旦是运行期值，编译器就无计可施 —— 这是
语言层面的限制，不是优化器不够聪明。要绕过它只有三条路：

1. **穷举展开**：为「N 个算子 × 每种形态 × 每个槽位」各生成一份代码。
   当前 `LfOpKind` 有 10 种形态、`LF_MAX_REG` 8 个槽位、算子数取 1~4，
   组合起来是 10⁴ 量级的代码块。要么靠宏（可读但体积不可控），要么靠
   代码生成（多一个构建步骤）。
2. **运行期生成机器码**：真正的 JIT。需要写 x86-64 编码器，且要处理
   W^X（Windows 上 `VirtualProtect`）。这是新工程，不是本轮范围。
3. **模板 JIT（computed goto）**：把每个 op 写成一个标号块，块内槽位是
   具名变量，块尾直接 `goto *next`。原型实测 **711ms** —— 比现状好一倍，
   但仍是 C 的 3 倍，因为每个 op 仍有一次间接跳转 + 一次 `pc++`。

第 3 条是性价比最高的中间档，但它**不解决问题**，只是把 7 倍缩到 3 倍。
第 1 条才能拿到全部 7 倍，代价是代码体积。

所以本轮的正确结论是：**先不动 `lf_run_int`**。理由是当前 `x run` 的
2322ms 里，AOT 已经证明「语义上限」在 333ms，而模板 JIT 只能到 711ms
—— 花大力气换 3 倍，不如把同样的力气放到 `fib` 那类**函数调用**上
（那里是 11.3×，基数更大）。

### 顺带修掉的两条测量债

- **`bench.sh` 的 `fib` 基线扣除不适用**：短程序的执行时间与空程序启动
  时间同量级，相减得到的是噪声。已在脚本里对该行输出 `[!]` 并保留原始值
  （见前文「测量陷阱」一节），本轮确认该处理正确，不再深究。
- **「同一个二进制测两次差 1.8 倍」再次出现**：本轮同一个 `loop3.xbc`
  先测 2029ms、后测 4626ms。这不是回归，是系统噪声。所有数字必须来自
  **同一次循环里交替测量、取最小值**，跨时间的两次单测没有可比性。

## 四·补六、第八轮：把分派挪到循环外（1909ms → 653ms）

第七轮把差距定位到 `reg[fo->dst]` 的动态下标，但没有动手。这一轮做完了。

### 先纠正第七轮的一个判断

第七轮我写下「展开要 10⁴ 级代码块，不值得」，并据此决定先不动。这个
判断**错在把「数组下标」当成了次要因素**。分离实验把两个变量拆开后：

| 写法 | 1e9 次 | 说明 |
|---|---|---|
| D0 全具名、零分派 | **326 ms** | 天花板 |
| D1 `(kind,dst)` 合并分派 → 具名变量 | 888 ms | |
| D2 **数组下标**、零分派（`nfops`/`dst` 已字面量） | **1473 ms** | |
| D3 `lf_run_int` 现状 | 1547 ms | |

**D2 与 D1 的对比是决定性的：完全不分派的数组访问（1473ms）比有分派
的具名变量（888ms）还慢。** 所以贵的不是分派，是「值落在数组里」——
一旦下标是变量，gcc 就不能把 `reg[]` 提升进寄存器，每轮 4 次内存往返。

这意味着正确做法不是「合并分派」，而是**让槽位落进具名变量**。而一旦
分派被提到循环外（每个 case 跑一份完整的具名循环），实测 **332ms**，
与天花板相同。

### 一个代价惨重的错误：把展开体写进同一个函数

第一次实现是把展开体直接 `#include` 进 `lf_run_int` 的函数体，用
`goto lf2_skip` 回落到通用路径。结果：

| | 二进制 | 性能 |
|---|---|---|
| 展开前 | 0.7 MB | 1909 ms |
| 展开后（同函数） | 5.0 MB | **37928 ms（慢 20 倍）** |

原因不是 I-cache，是**控制流**：gcc 无法证明那 2880 个 case 不会跳到
通用路径，只能把它们全部算作 `lf_run_int` 的一部分来做寄存器分配，
于是**连通用循环本身都退化了**。

验证方式很干净：只把守卫改成 `false && (...)`、其余一字不动，性能立刻
回到 1909ms。这就排除了「展开体算错了」或「I-cache」的解释。

修法是把展开体做成**独立的 static 函数 `lf_run2()`**，通用路径完全
看不见它。同一份展开体，同样 2880 份：

| | 二进制 | 性能 |
|---|---|---|
| 独立函数 `lf_run2` | 4.5 MB | **677 ms** |

### 最终结构

```
lf_run_int()
  ├─ 阶段一/二：槽位收集、解包到 reg[]、解析 FastOp
  ├─ 若 nfops==2 且都是 *_CONST 族 且槽位 <= 4：
  │     lf_run2(reg, fops, cond_kind, cond_r1, cond_r2, c1)
  │       ↳ 一次 switch((d0,d1,k0,k1,c1,c2)) → 2880 份具名循环之一
  │         返回 LF2_OK / LF2_OVERFLOW_* / LF2_NOT_APPLY
  └─ 否则（或 NOT_APPLY）：原有通用循环，一字未改
```

`lf_run2` 的返回值契约：

- `LF2_OK` —— 跑完，`reg[]` 已更新
- `LF2_OVERFLOW_ADD/SUB/MUL` —— 溢出，`reg[]` 已同步成出错那一刻的值，
  出错 op 的源码位置经由 `g_lf2_errpos` 回传
- `LF2_NOT_APPLY` —— 形态不匹配，**没动过** `reg[]`，调用方原样继续

溢出位置必须用出错那条 op 自己的 `pos`，不能用回边的 `pos` —— 这是
第六轮踩过的坑，也是 06 文档规定的诊断契约。

### 生成器而不是手写

展开体由 `tools/gen_loop_jit.py` 生成（`src/loop_jit_gen.h`，31122 行，
2880 份）。手写必然漂移 —— 项目史上 `<<` 就因为两份实现不同步而错过
一次，而且只在热循环上错、冷路径完全正常，极难定位。

`tools/build.sh` 每次构建都重跑生成器。脚本顶部的注释写明了
「`KINDS` 顺序必须与 `LfOpKind` 头三个枚举值一致」—— 这三个值恰好是
0/1/2，如果只看代码不验证，改枚举顺序时会静默算错。本轮就吃过一次：
第一版误以为 `LF_CMP_NE_CONST` 是 0，实际是 9。

### 数字

```
                        改前        改后        AOT
  1e9 次 c=c-1; i=i+1   1909 ms    653 ms     335 ms
  与 AOT 的差距          5.7×       1.95×       1×
  与 Java 的差距         6.5×       2.2×       1.14×
```

`x run` 与 AOT 的差距从 **5.7 倍缩到 1.95 倍**。剩下这 2 倍是 AOT 能
拿到而解释器拿不到的：gcc 在编译整个程序时能看到 `n` 的具体值做类型
特化，而解释器只能在运行期看到「它是 Int」。

### 验证

- **全量回归**：85 通过 / 8 失败，与基线逐项一致（8 个是既有的包管理
  与网络失败）。
- **三条路径一致性**：`tests/p0/*.xle` 全部 **md5 一致**（默认 JIT /
  纯解释 / 强制融合阈值 0）。
- **80 个程序**（tests + examples）强制融合 vs 默认：仅 1 个差异，是
  `04-test-speed.xle` 自己在打印耗时毫秒数（448 vs 436），不是语义差异。
- **8 种循环形态**：加/减/乘 × 常量比较/变量比较 × `<`/`!=` × 三槽位，
  三条路径输出全一致。
- **诊断位置**：溢出报在第 4 行、第 5 行两条不同语句上，三条路径均
  报同一位置（`4:9` / `5:9`），契约未破。

## 五、一句话总结

**慢的不是「解释器」这个选择，是「循环里本来该是 1~2 条指令的地方有 4 条」，以及「每条指令都在做只有出错才需要的事」。**

五轮做完，10 亿次循环从 **48 秒降到 1.8 秒（约 27 倍）**：

| 阶段 | 10 亿次循环 | 主要手段 |
|---|---|---|
| 原始 | 48.3 s | — |
| 第一轮 | 13.0 s | 减法超指令 + 槽位释放快速路径 |
| 第二轮 | 9.0 s | 运算族泛化 + `pos` 延迟 + 归属类缓存 |
| 第三轮 | 4.8 s | 变量拷贝 / 比较跳转超指令 |
| **第四轮** | **1.8 s** | **循环融合 + 寄存器化** |
| 第五轮 | 1.8 s（形态覆盖 ×3） | 三地址 / 乘加 / `i < n` 头部 |
| 第六轮 | 1.8 s（+ 基准纠错） | 运算链 `(a+b)%k` + 诊断位置修正 |
| 第七轮 | 2.3 s（无回归） | **只取证不改码**：确认 AOT 已追平 C/Java，`x run` 的 7 倍卡在 `reg[dst]` 动态下标 |
| **第八轮** | **0.65 s** | **把分派挪到循环外：独立函数 `lf_run2` + 2880 份具名展开体** |

第五轮不降低单形态的绝对耗时，它的收益是**把融合从「只覆盖压测那种
写法」推到「覆盖所有整数算术循环」** —— 真实代码里的 `n = n + i` 从
36.5s 降到 6.5s（约 5.6×），这一条比任何微调都重要。

第六轮修了两个真 bug（诊断位置、基准脚本）并补上运算链形态，
`tools/bench.sh` 的整数循环基准因此从 **467ms 降到 190ms**，
`X/C-O0` 从 5.6× 改善到 2.1×。

第八轮之后，它与 AOT 的差距是 **1.95 倍**（原来是 140 倍），启动开销
保持为 0。

剩下的差距集中在**函数调用**（跨函数热点仍走 `BC_CALL`，`fib(33)` 与
C `-O0` 差约 2.6 倍）与**非计数循环**（数组遍历、含 `if` 的循环体）。
函数那一条需要内联编译 + 类型特化，是新工程，不是继续加超指令能解决的。

## 附录：四个测量陷阱（都实际踩过）

这四条不是理论，是各花掉一次错误结论的坑。

**1. 同一二进制测两次能差 1.8 倍。**
机器常驻 ToDesk / aTrust / 杀软，CPU 抖动极大。同一个程序测得 522ms
和 1400ms 都出现过。对策：程序内 `nowMillis()` 自计时、多轮交替、
取最小值 —— 不要用 `time` 包在进程外面（那还含有启动开销）。

**2. 二进制必须和标准库在同一个相对位置。**
`x.exe` 按 `<exe 目录>/../lib/stdlib` 找标准库。把对照用的二进制拷到
`C:/xtmp/` 跑，读到的是那里的**陈旧 stdlib**，于是 12 项测试出现
「假差异」。对策：两版二进制都放进 `build/` 再对照。

**3. `gcc -O2` 会把循环消成闭式解，「循环只有 5 条指令」可能是 `-O0` 的产物。**
`while (i != N) { c -= d; i += d; }` 能被推成乘法，整段循环消失。
本轮据此误判过一次（「C -O0 只需 365ms」）。对策：步长也必须从
`argv` 进来，并且要**反汇编确认 `-O2` 那个二进制里循环真的还在**。

**4. 「程序立刻退出了」看起来像「很快」。**
`user.xbc` 不存在时程序秒退，测出「79.9ms」这种漂亮数字。
对策：先确认被测量程序真的跑完了 —— 让它输出一个可校验的结果值。
