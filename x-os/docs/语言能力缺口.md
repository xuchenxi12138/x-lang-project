# X 语言能力缺口（写内核时实测出来的）

这份文档只记录**实测确认**的缺口，每条都有验证输出。不写「我觉得应该支持」。

---

## 一、硬缺口：这些直接导致「用 X 写不了内核」

### 1.1 指针 `&x` / `*p`

```
$ x build t.xle
期望一个表达式，实际读到 &

    let a = 1
    let p = &a
            ^
```

**为什么必须有**：内核里到处是「拿一个地址、按某种宽度读写」。虽然本版用 `memRead32(addr)` 这类内建绕过了大部分需求，但一旦要做数据结构（链表、页表遍历、红黑树），没有指针就只能全部靠「整数地址 + 内建」，可读性崩溃。

**当前替代**：`memRead8/16/32` + `memWrite8/16/32`，配合 `const ADDR = 0xB8000` 常量。能工作，但每处访问都要手写宽度。

### 1.2 `unsafe` 块

```
$ x build t.xle
期望一个表达式，实际读到 unsafe
```

**注意**：`unsafe` 在关键字表里（`src/lexer.c`），但**没有实现**。这种「规划了但没做」的状态比「完全没规划」更危险：写代码时会以为能用。

### 1.3 `extern fn` 声明

```
$ x build t.xle
P0 不支持只有签名的声明
```

**为什么必须有**：内核需要调用汇编或 C 写的运行时（`runtime.c` 里的 `xk_serial_init`、`malloc` 等）。没有 `extern fn` 就只能靠链接器的隐式声明，而 X 的类型系统在这里是断的。

**当前替代**：把 C 侧的函数全部包成 X 函数声明在**同一个 .xle 文件**里……不行，X 没有声明语法。实际做法是让生成的 C 代码直接调用 `xk_*`（通过 `PRELUDE` 里的声明），X 源码里不出现这些名字。这也是为什么 `mem` 命令无法报告精确堆用量——`xkHeapPtr()` 在 X 里调不到。

### 1.4 `asm!`

```
$ x build t.xle
未定义的变量 asm
```

**为什么必须有**：`cli`/`sti`/`hlt`/`invlpg` 这几个本版做成了内建，但还有几十个（`lgdt`/`lidt`/`rdmsr`/`wrmsr`/`cpuid`/`invd`/`wbinvd`）。每加一个就加一个内建，是 O(n) 的维护成本；而 `asm!` 是一次性解决。

### 1.5 freestanding 目标

```
$ x build t.xle --target=i386-none
error: 未知目标 i386-none
支持的目标：windows / linux / macos
```

**为什么必须有**：目标表里只有三个宿主 OS。要做裸机目标需要：
- 不生成 `setvbuf(stdout, NULL, _IOLBF, 0)`（连 Hello World 都有这一行）
- 不链接 libc
- 入口是 `_start(void)` 而不是 `main(argc, argv)`

**本轮的临时解法**：加 `-DX_FREESTANDING` 宏，让生成代码走 `#ifdef` 分支。这是可行的（同一份代码两种模式），但**不是语言特性**——它依赖构建脚本传对宏，而不是编译器自己知道「这是裸机」。

### 1.6 kernel profile

```
$ cat src/profile.h
profile: console / desktop / service
```

没有 kernel 档。当前靠 `-DX_FREESTANDING` 绕，效果等价但语义不同：profile 是编译器的概念（影响调用深度、输出缓冲策略等一串参数），宏只是开关。

### 1.7 顶层可变变量

```
$ x build t.xle
给未定义的变量 vgaCursor 赋值

    var vgaCursor = 0      ← 顶层
```

**当前替代**：放在固定物理地址（0x5000），用 `cursorGet()`/`cursorSet()` 包起来。这与 Linux 的 per-CPU 变量、Windows 的 KPCR 是同一思路（内核本来就需要「在某处放可变状态」），但**这是被逼的，不是设计选择**。

## 二、量化证据：Hello World 的依赖链

```
$ cat hello.xle
println("hello")
$ x build hello.xle --emit=c -o hello.c
$ gcc -m32 -ffreestanding -nostdlib -c hello.c -o hello.o
$ nm -u hello.o | wc -l
77
```

77 个未定义符号：

| 类别 | 数量 | 举例 |
|---|---|---|
| libc | 45 | `setvbuf`, `fwrite`, `malloc`, `memcpy`, `strtod`, `pow` |
| Win32 导入 | 30 | `GetStdHandle`, `WriteFile`, `SetConsoleMode` |
| 其他 | 2 | `__main` |

生成的 `main()` 第一行就是 `setvbuf(stdout, NULL, _IOLBF, 0)`——连 Hello World 都无法脱离 libc。

**加了内核内建 + freestanding 模式后**：9 个符号（`malloc`/`free`/`realloc`/`memcpy`/`memset`/`memcmp`/`strlen`/`strncat`/`strpbrk`/`strtod`），全部由 `runtime.c` 提供，**内核镜像未解析符号为 0**。

## 三、已补齐的能力（本轮新增）

14 个裸机内建，两档（解释 / AOT）都实现：

```x
memRead8(addr) -> Int        memWrite8(addr, v) -> Null
memRead16(addr) -> Int       memWrite16(addr, v) -> Null
memRead32(addr) -> Int       memWrite32(addr, v) -> Null
portIn8(port) -> Int         portOut8(port, v) -> Null
portIn16(port) -> Int        portOut16(port, v) -> Null
cpuHlt() -> Null             cpuCli() -> Null
cpuSti() -> Null             cpuInvlpg(vaddr) -> Null
```

**设计取舍：宽度写进函数名**，而不是 `memRead(addr, width)`。理由：宽度参数在调用点永远是字面量，消除后「宽度错误」在代码审查里一眼可见（`memRead8` 与 `memRead16` 是不同函数，不会传错）。代价是内建数量翻三倍，但这 14 个是**封闭集合**，不会增长。

**volatile 不可省略**（写进了生成器注释）：

```c
// 没有 volatile 时：
while ((memRead8(0x3FD) & 0x20) == 0) { }
// 会被优化成 if 或直接删除 → 串口丢字符
// 而且**只在 -O2 下出现**，-O0 测试全绿
```

## 四、对「完整操作系统」还缺什么

按依赖顺序：

| 优先级 | 能力 | 为什么卡住 |
|---|---|---|
| P0 | `&x` / `*p` | 数据结构（页表、链表、红黑树）无法写 |
| P0 | `extern fn` | 无法声明「这个函数在别处」 |
| P0 | `asm!` | 每加一条特权指令就要加一个内建 |
| P1 | `unsafe` | 实现已规划（关键字表里有），缺语义 |
| P1 | kernel profile | 目前靠 `-DX_FREESTANDING` 宏绕 |
| P2 | 顶层可变变量 | 靠固定地址 + getter/setter 绕 |
| P2 | 结构体字段偏移 `offsetof` | 描述符表布局需要算偏移 |

**没有列的**（本轮不需要，但迟早要）：`union`、位域、`volatile` 修饰符、内联汇编的内存屏障语义、链接脚本的段属性控制。

这份文档的作用是：下次有人问「为什么不用 X 写个真正的 OS」时，能给出**具体缺什么、缺了之后卡在哪**，而不是含糊的「语言还不成熟」。
